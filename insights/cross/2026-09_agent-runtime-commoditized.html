      Agent 运行时被商品化 · Runtime as a Utility

      当会话状态、编排、子代理、沙箱、上下文压缩都变成 OpenAI Agents API 的托管原语，我们过去一年半手搓的那层「Agent 框架」正在变成水电煤。

      核心论点：OpenAI 把 会话状态、编排、子代理、沙箱、上下文压缩 这五件事打包成一个托管 Agents API 的那一刻，「Agent 运行时」就从一件要自己造的差异化壁垒，变成了一件按量租用的基础设施。这不是又一个 SDK，而是一次价值形态的下沉：过去一年半，无数团队把工程精力投在「怎么管住一个会跑很久的 agent」——续接会话、并发子任务、隔离执行、把爆掉的上下文压回窗口内。现在这层被平台一次性收编，中间层被抽空，护城河被迫向两端迁移：向上是领域逻辑 / 评测 / 数据与信任，向下是自有模型。预判：进行中——12 个月内，「我们自研了 agent 框架」将不再是卖点，而「我们把运行时选型和退出策略想清楚了」才是。
      一页要点
      • 被商品化的是「运行时」，不是「Agent」：会话管理、编排、subagents、sandbox、context compaction——这五件苦活，正是过去大家自研框架里最费人的部分，如今成了平台默认原语。
      • 中间层被抽空：你自建栈里「模型之上、业务之下」的那层运行时，价值被平台吸走；差异化被迫向上端（领域逻辑 / 评测 / 上下文数据 / 信任与合规）和下端（自有 / 微调模型）迁移。
      • 「造轮子」的边际收益归零：再花三个月写一套会话恢复 + 沙箱隔离，换不来任何客户能感知的差异——那层已经是水电煤。
      • 但商品化 ≠ 免费的午餐：托管运行时带来供应商锁定、黑盒可观测性、数据出域、定价随规模上涨四个新账单，采购与交付要把它们写进合同与架构。
      • Agent OS 之战开打：谁定义运行时原语，谁就定义生态的默认形状——这和当年云厂商用托管数据库/队列收编中间件是同一个剧本。
      • 对 FDE 的意义：停止在运行时层「秀肌肉」，把工程预算移到评测归因、领域上下文、可控性与退出成本；对客户的技术尽调，新增一条「运行时依赖与迁移成本」评估。

      一被商品化的，是「运行时」这层苦活#

      — WHY NOW · 平台把最费人的中间层收编了

      过去一年半，凡是认真做过长任务 agent 的团队都踩过同一批坑：一个会话跑了二十分钟、上下文要续接怎么办？主 agent 想并发拆三个子任务、结果怎么汇总？让模型执行代码，怎么关进沙箱不祸害宿主？上下文快爆窗口了，怎么压缩还不丢关键信息？这些不是业务逻辑，而是「运行时」——模型之上、业务之下的那层管道。大家各自造了一遍，还都以为这是自己的壁垒。

      OpenAI 的 Agents API 把这五件苦活一次性做成了托管原语。它没有让 agent「更聪明」，而是让运行 agent 这件事不再需要你自己搭台子。这就是「商品化（commoditization）」的定义：一件曾经稀缺、要自研、能区分高下的东西，变成随处可得、按量计费、彼此无差别的基础设施——像机房时代的自建 IDC 变成了云上的一行 API。

      二拆开托管运行时：五段流水线#

      — 平台默认原语，逐段对齐你曾经手搓的东西

      把「运行时」这个抽象词落到地上，它其实就是一条流水线：一个请求进来，要开会话、编排步骤、按需拆子代理、在沙箱里执行、把上下文压回窗口，再进入下一轮。下面这条流水线的每一段，都对应你过去可能自己写过的一个模块——现在它们都是平台的一行配置。

      托管运行时的五段流水线The Managed Runtime Pipeline

      每一段旁边标注的是「你以前自己造的对应物」。流水线末端回注，代表长任务的多轮循环——这正是自研时最难稳住的部分。

      注意分辨

      被商品化的是运行这条流水线的能力，不是你在流水线里跑的东西。同一条托管运行时，喂进去的领域工具、系统提示、评测标准不同，产出天差地别。平台抹平的是「台子」，抹不平的是「戏」。——这也是护城河为什么向两端跑，而不是消失。

      三中间被挤空，护城河往两端跑#

      — So what · 差异化的迁移方向

      商品化最直接的后果，是价值的重新分布。当中间那层谁都能一行 API 拿到，靠它拉不开差距，利润和差异化就被挤到栈的两端：向上是越贴近客户、越难被平台标准化的东西——领域逻辑、私有上下文数据、评测与归因、可控性与合规信任；向下是模型本身——自研或深度微调的权重，是平台给不了你的。夹在中间、只会「组装标准运行时」的团队，最先被抹平。

      价值被挤向两端Value Migrates to the Edges

      中间的托管运行时被压成一条薄带（商品化区）；上下两端的色块变厚，代表可防御价值往那里聚集。只做中间层的团队，站在最薄的地方。

      栈的层商品化后的处境该不该投工程
      领域逻辑 / 工作流越贴客户越难被标准化，护城河重投
      评测 / 归因体系平台不做、也做不了你的口径重投
      上下文 / 私有数据你的独占资产，喂进任何运行时都增值重投
      运行时（会话/编排/沙箱/压缩）已商品化，自研边际收益趋零停止自研，改选型
      基础模型要么租平台、要么自研微调视资源，要么向下深挖

      四商品化不是免费午餐：四张新账单#

      — 租来的运行时，代价写在别处

      「不用自己造了」听起来全是好处，但把运行时交给平台，等于把一批风险从工程账转成了依赖账。这四张账单，采购和架构评审时必须提前算清楚——否则省下的三个月工时，会在退出成本上加倍还回去。

      四张新账单
      • 供应商锁定：运行时原语一旦成为你架构的地基，换平台等于重做地基。会话格式、编排语义、sandbox 行为都是私有的，没有可移植标准。
      • 可观测性变黑盒：agent 为什么这么决策、上下文被压缩时丢了什么——托管层的内部状态你未必看得全，而这恰恰是评测归因最需要的证据。
      • 数据出域：会话状态、中间产物、上下文都过平台。金融 / 医疗 / 政务客户的合规红线，可能直接卡在这一条。
      • 定价随规模上涨：托管运行时按量计费，长任务 agent 的调用量是复利级的。规模化后，「租」的总成本可能反超「自建 + 摊薄」。

      五那到底还要不要自己造#

      — build vs buy 的新分界线

      商品化不等于「一律买」。分界线变了：默认买托管运行时，除非你有一条具体、可说清的理由必须自建。下面两张卡把这条线画出来——大多数团队会落在左边，只有少数带硬约束的场景才该往右。

      默认 · 买（租托管运行时）

      大多数团队该站这边

      • 你的差异化在领域逻辑 / 数据 / 评测，不在运行时
      • 规模还没大到「按量计费反超自建」的拐点
      • 没有强数据出域 / 合规红线
      • 想把工程预算集中到能被客户感知的地方
      例外 · 自建（要有硬理由）

      只有带硬约束才往这边

      • 合规要求数据不出域、运行时必须自持
      • 规模巨大，自建摊薄后单位成本显著更低
      • 需要平台不提供的特殊编排 / 隔离语义
      • 把「运行时本身」当作对外售卖的产品

      六对 FDE 的意义#

      — 把预算从「造台子」挪到「演好戏」

      下一步（1–2 周）
      • 盘点自研运行时：列出团队里「会话/编排/子代理/沙箱/压缩」相关的自研代码，标注哪些能被托管原语替代——大概率能砍掉一大块维护负担。
      • 停止在运行时层秀肌肉：对客户的技术方案，别再把「我们自研了 agent 框架」当卖点；改讲领域逻辑、评测归因、可控性。
      • 新增一条尽调项：客户 / 合作方的技术评估里，加「运行时依赖与迁移成本」——问清楚一旦要换平台，地基要重做多少。
      • 把工程预算上移：把省下的运行时工时，投到评测归因体系、私有上下文数据、可控性与合规——这些是平台抹不平的护城河。
      • 算清四张新账单：锁定、可观测性、数据出域、规模定价，写进采购合同与架构评审 checklist。

      七待验证问题#

      1. 托管运行时的可观测性能做到多深？能不能吐出评测归因需要的中间证据（上下文压缩前后、子代理决策）？
      2. 规模定价的真实拐点在哪——什么样的调用量下，「租」会反超「自建 + 摊薄」？
      3. 会不会出现可移植的运行时标准（跨平台的会话/编排格式），把锁定风险降下来？还是各家继续各搞私有原语？
      4. Anthropic / Google 会跟进同款托管运行时吗？如果三家原语不兼容，多云 agent 架构怎么落地？
