      Claude 开始自己写工作流 · Managed Agents · Dynamic Workflows

      Anthropic 把 Durable Workflow 的调度语义塞进了平台 API —— 这是"薄 Agent + 可持久化编排"范式的厂商版落地，不是又一个 subagent 糖衣。

      核心论点：Claude Managed Agents 的 Dynamic Workflows 不是"更多 subagent"，是把"分 phase、可持久化、服务端后台跑"的调度语义做成了平台原语。Agent 从"自己写代码"升级到"自己写工作流" —— 一次写入、服务端 24 小时托管执行、主会话线程只留"报进度"的瘦身入口。这正是我们团队内部一贯主张的"薄 Agent + Durable Workflow"的厂商版落地，对 LIFT 的归因口径将直接造成影响。
      一页要点
      • 核心产品动作：10/9 以 beta header managed-agents-2026-04-01 放出 multiagent_20261001 新类型，lead agent 可以直接"写出一个 workflow 程序"并交由服务端后台执行。
      • 关键配额：单次 run 累计 ≤ 1,000 agent · 并发 ≤ 64 线程 · 默认 24h 寿命 · predefined_agents 最多 20 个。
      • 语义升级：旧 subagent 走"一次性委派、父线程全程占着"；workflow 走"分 phase、程序化传参、服务端 archive"，父线程被瘦身。
      • 观测位：每次 run 在 session event stream 上以 workflow_run.* 事件对外吐进度，不再是单条消息串。
      • 对我们：这件事正面击中我们 L2 定位的静态图分析路径 —— workflow 是"官方给出的因果图"，归因可以直接吃它、不再需要从 trace 推。
      • 战略判断：Anthropic 比 OpenAI 和 Google 更早承认"Agent 没必要承担全部动态逻辑"，把一部分"确定性调度"从模型里剥离给平台。

      一发生了什么#

      — 一次 release note 两句话，但语义是跨级的

      10 月 9 日，Anthropic 在 Claude Platform Release Notes 里加了一条简短条目：允许 Managed Agents 使用 dynamic workflows，beta header 为 managed-agents-2026-04-01。开启方式是把 agent 的 multiagent 字段设成：

      {
  "multiagent": {
    "type": "multiagent_20261001",
    "workflows": { "type": "enabled" }
  }
}

      看上去只是开了一个 flag。但背后的语义变化是：lead agent 不再是"自己边想边一个一个派 subagent"，而是先 写一个 workflow 程序，交给服务端在后台跑；程序会按阶段拉起多个 agent、把前阶段的输出程序化地喂给后阶段，最后合并结果。整个 run 结束时，每一个被拉起的子线程都被服务端自动归档，父会话从始至终只负责"看进度"。

      二subagent 和 workflow 不是同一个东西#

      — 别被"多 agent"这个词骗了

      看懂这次变更的最快方式，是把它和 4 月上线的 subagent 委派摆在一起对照。两者都"多 agent"，但调度模型完全不是一回事：

      before · subagents

      Agent 一边想一边派

      • 父线程全程占着、等每个 subagent 回话
      • 只能一级深、至多 25 个活线程
      • subagent 线程常驻直到你 archive
      • 调度逻辑全在模型"下一步该派谁"里
      after · dynamic workflows

      Agent 先写程序、服务端跑

      • Agent 写 workflow 程序、服务端执行
      • 分 phase，参数程序化传递
      • 父会话瘦身，只接 workflow_run.* 事件
      • 调度逻辑半数搬到平台

      这不是"subagent 的升级版"，是 控制流从模型里拆走了一半：模型负责"任务怎么切、分几 phase、每 phase 拉几个 agent"的生成，服务端负责"按程序跑完、把输出串起来、archive 子线程、往 session stream 吐事件"的执行。

      三典型使用场景：什么样的任务配得上 workflow#

      — 不是"更多 agent"场景，是"多件 + 长 + 可并行"场景

      Anthropic 官方文档给出的四个标签场景，可以在工程口径上归为"多件 · 长时 · 可并行"的任意组合。单条消息一轮就能回的任务不该用 workflow，用 subagent 甚至 single-agent 都更划算。

      batch · 多件

      批量 Audit / 文档审查

      数百份合同 / 代码仓 / 研报的合规检查、风险打分、合规项抽取。P1 并发扫描 → P2 聚类 → P3 产生报告是典型三段式。官方点名"review hundreds of documents"就是这类。

      migration · 迁移

      代码库 / 配置批量迁移

      跨仓库大规模 refactor、框架升级、依赖替换。P1 盘点影响面 → P2 并发改写 → P3 跑测试并回报失败清单。节点天然同构，适合 inline agent。

      research · 深研

      Deep Research / 竞品摸排

      一个主题拆成几十个子问题各自展开检索与阅读。P1 展开子问题 → P2 并发检索 → P3 交叉验证 → P4 综述。父会话瘦身后，用户还能继续聊天不被阻塞。

      cross-check · 交叉核对

      Cross-checking / 多视角打分

      一份产出让 N 个不同 persona / 不同模型角色独立评审，再合并出共识打分。这正是 LIFT 想做的"品菜师团" —— workflow 是现成的裁判阵型容器。

      parallel · 并行加速

      长任务被切成可并行的几片

      单线程要跑一下午的任务，拆成 10 组子任务并发跑再合流。瓶颈从"模型吞吐"变成"预算 + 并发 64 格栅栏"。

      long-run · 后台托管

      需要几小时的生成 / 回填任务

      传统 agent 跑超时就断，workflow 服务端托管 24h 默认寿命，父会话随时断线、重连继续看 workflow_run.* 事件。离线数据回填、长链路报告生成都吃这个口径。

      不该用 workflow 的反面
      • 单轮能答的问答：根本不需要多 agent，白白吃一笔调度开销。
      • 强顺序依赖的短链路（A→B→C 一分钟能走完）：subagent 顺序委派反而更快、调试也简单。
      • 需要用户频繁打断干预的任务：workflow 一旦跑起来父线程只能看，不能回头给某个 phase 内的 agent 补充提示。
      • 每一步都要人审批的流程：审批点和 workflow 的"程序化传参"是冲突的，这类该走 subagent + 显式 approval 链。

      四Workflow 的调度语义：一个 run 的生命周期#

      — lead 写程序 → server 跑 phase → 父会话收事件

      Inline agent workflow 自己定义的"临时工"：复用 workflow 的 model / tools / MCP / skills，不占预定义位。
      Predefined agent 事先创建的 agent id，带自己完整配置；workflows.predefined_agents 最多 20 个。
      Session budget 所有 agent 共吃一个 session token 预算，run 结束后统一结算。

      可以把 workflow 理解成"Agent 版的 Durable Task 图"：节点是 agent（inline 或 predefined），边是数据流，相位是栅栏，服务端是 scheduler，父会话退化成监听者。

      五配额栅栏：Anthropic 替你画好的边界#

      — 1000 不是并发，是累计

      1,000
      cum. agents / run
      单次 run 累计可启动的 agent 上限。注意不是同时在跑。
      64
      concurrent threads
      同一时刻真正并发的 agent 线程数，超了排队等。
      24h
      default lifetime
      单次 workflow run 的默认存活时长，到点被服务端收走。
      20
      predefined slots
      workflows.predefined_agents 列表的最大长度，可以配 20 个带自己 config 的 agent 版本。

      这组数字其实是一张"Anthropic 替你定好的 SLA"：它既是上限，也是产品承诺 —— 你用这个 beta，就可以指望平台至少把 24 小时、64 并发、1000 累计这件事扛起来。相比之下，自己拿 Temporal / Prefect 搭 agent 的团队要花掉一个 quarter 才做出这组保障。

      六为什么这件事比看上去大#

      — "薄 Agent + Durable Workflow" 终于有厂商版了

      L1模型层

      Claude 模型本身

      做"生成一个工作流程序"的能力。还是语言模型，只是输出目标多了一个 schema：workflow DSL。

      L2平台层

      Managed Agents 的 scheduler

      新原语，吃 workflow 程序、按 phase 执行、把事件流回父会话。workflow_run.* 是观测位，managed-agents-2026-04-01 是开关。这就是 Anthropic 把 Durable Workflow 做进 Platform 的那一步。

      L3Agent 层

      你的 lead agent

      系统提示里加一句"遇到以下情形时启动 workflow run"，剩下交给平台。Agent 变薄了，承担的是判断"该不该开 workflow、分几 phase"的 meta 决策。

      过去一年我们在 LIFT 立项时反复讲的"薄 Agent + Durable Workflow"（Scheduler 管 DAG、局部重试、状态持久化）—— Anthropic 这个 beta 是现成的厂商版。它把"控制面"和"数据面"做了初步切分：模型管"下一步 workflow 怎么写"（控制面决策），平台管"workflow 怎么被跑完"（数据面执行）。

      和竞品的位置对比

      OpenAI Dot：仍是"主 agent + 后台任务队列"的架构，没有把 workflow DSL 暴露给模型自己写。
      Google Gemini Vertex Agent Builder：有 workflow，但由开发者手写、Gemini 不写 workflow 代码。
      Anthropic 这一步独特的点：让模型自己产出 workflow 程序、再由平台执行 —— 这是"模型即编译器 (model-as-compiler)"的早期雏形。

      七对 LIFT 归因框架的直接冲击#

      — L2 定位的"静态因果图"今天变成免费的

      LIFT 的三层栈里，L2 定位依赖"从 trace 推因果图"。dynamic workflow 的出现，意味着 Anthropic 直接把这张图给你 —— workflow 程序本身就是一张可读的 DAG，workflow_run.* 事件把 phase 推进、分支、合并明确标出。LIFT 要做的事情从"推图"变成"吃图"：

      LIFT 层没有 workflow 时的做法有 workflow 后的做法
      L1 · 分类 按 agent 单条 trace 判错误类型 新增一类错误："workflow 结构缺陷"（相位切错 / 节点缺失 / 合并不收敛）
      L2 · 定位 从 trace 事件序列倒推因果图 直接吃 workflow_run.* 事件 + workflow 程序本体做静态图分析，剪枝工作量砍半
      L3 · 归因 A2P / CHIEF / Re-Ex 在 trace 上论证 把 "workflow 版本"视作天然反事实变量：同任务换 workflow 就是现成的对照组
      注意新错误类目

      以前"擅自决策"是模型层问题；现在要拆成两件事：(a) 模型写错了 workflow（控制面错误）；(b) workflow 没错但某个 agent 节点越权（数据面错误）。两者归因方法完全不同 —— 前者要重放"写 workflow 的那次推理"，后者只要查节点 trace。

      八我们接下来要做什么#

      — 两周内可以落地的 3 件事

      行动
      1. 把 managed-agents-2026-04-01 这个 beta header 加进 LIFT 的接入 skill —— 让评测 agent 优先用 workflow 模式跑，以便我们先于客户遇到 workflow 结构缺陷。
      2. Trace schema 增加 workflow_run_id / phase_id / agent_role（inline vs predefined）三个字段。这是 L2 静态图分析能直接吃 Anthropic 事件流的前提。
      3. L1 错误库新增两条：workflow-structural（相位/分支/合并层面）与 workflow-escape（节点越权，与"擅自决策"的 agent 层错误区分）。

      九待观察问题#

      1. workflow DSL 会不会外泄？目前 workflow 是服务端私有执行格式，开发者只能通过事件流看到。如果 Anthropic 把 workflow DSL 文档化、变成跨厂商可移植格式，它就成了"Agent 版 BPMN"。
      2. 24h × 1000 agent 的真实成本曲线？一次 run 可能烧掉几十到几百美金，预算越界的归因策略要重新设计（现在的 session budget 粒度太粗）。
      3. 并发上限会往哪涨？64 是一个"看起来是单机 scheduler 的数"，如果下一阶段跳到 512 / 1024，意味着 Anthropic 已经把 workflow 跑在分布式调度器上。
      4. Managed Agents 会不会向第三方模型开放？如果有一天你可以用 Claude 做 lead、Gemini 做 phase 节点，Anthropic 就从模型厂商升级成 agent 操作系统厂商 —— 这是"模型接入商品化"叙事的终局。
      5. failure replay 的权限边界：现在服务端 archive 掉子线程后，replay 能到什么粒度？如果只能 replay 事件、不能 replay 子线程推理，L3 的论证性归因还得继续靠 CHIEF / Re-Ex 兜底。
