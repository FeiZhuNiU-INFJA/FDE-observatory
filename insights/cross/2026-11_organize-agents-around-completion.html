      核心论点 · 本文推论：Fable 5.2 让更多复杂技术任务值得交给 Agent 尝试。我的判断是，随着模型能够承担更长、更模糊的工作，系统的瓶颈会更多落在“完成机制”上。基于这一判断，我建议把目标写成可验收的结果，保存可恢复的工作事实，为探索设置预算，再用独立证据确认完成。模型负责判断和推进，系统负责让工作有边界、有记录、有交付，是本文建议的职责分工。
      一页要点
      • 本文设计建议 · 改变工作单位。用一个带范围、预算和验收条件的目标组织会话与工具执行。
      • 原文数据 → 本文建议 · 按收益买推理。AA 中 high 与 xhigh 同分，成本相差约 63%；我建议用实际任务的额外收益决定是否升级。
      • 原文事实 · 千 Agent 的分工。模型动态协调，SQL 保存事实，独立 VM 隔离执行，Git 与 Lean 验证提交。
      • 本文推论 · 长上下文与外部状态互补。要跨恢复、跨模型、跨责任人继续工作，我认为还需保存可复查的业务事实。
      • 本文建议 · 按实际路径评估安全与成本。主模型、fallback、advisor、子 Agent 和失败尝试都应纳入评估。
      • 本文设计建议 · “薄 Agent + 持久工作流”。保留模型的动态判断，将持久化、权限与验证交给可靠机制；是否划算尚需实测。

      一能力变强之后，什么变得更稀缺#

      — 原文信号 → 本文推论 · 工作组织的变化

      Fable 5.2 最值得关注的信号，是它开始覆盖更大的工作单元。Anthropic 将其定位于模糊需求、长期工程、深入研究与科学计算；发布表中，Remote Labor Index 从 5.1 的 17.9% 升到 41.3%。这个指标只说明特定评测条件下的专业项目完成表现，无法换算成可替代的岗位比例。独立机构 Artificial Analysis 的综合评测也支持能力提升这一方向。[1][2]

      当模型经常只能完成几步，工程师需要不断补充指令、拆小任务、接管执行。当它可以连续工作数小时，新的问题会显现：是否仍在解决原来的目标？子任务的进度可信么？该继续探索，还是交付已有成果？一次中断之后，下一轮究竟从哪里接上？

      我的推论是：能够继续做下去，会增加“该怎样收口”的价值。这一判断还包含一个前提：复杂任务的需求偏移、恢复和验收成本，确实会成为瓶颈。在这个前提成立的场景中，我预计 FDE 将更多精力用于把模糊诉求变成可检验的交付约束。这个工作变化尚未由上述模型评测直接验证。

      二买更多推理之前，先定义收益#

      — 原文评测数据 + 本文投入建议

      只看每百万 token 的价格，很难判断这次升级是否值得。Fable 5.2 标准输入 / 输出单价为 $8 / $40，Opus 5.5 为 $4 / $20；前者单价更高，却可能通过减少失败与返工降低交付成本。与此同时，在同一个模型内部，effort 会显著改变消耗。[5]

      AA 的原文数据是：high 和 xhigh 的综合分都为 62，每题加权成本分别为 $9.08 和 $14.83；max 升到 65 分，成本达到 $26.54。根据这些数值计算，xhigh 比 high 贵约 63%，max 的成本约为 high 的 2.92 倍。[2]我的投入建议是：用目标任务的额外完成收益，判断更高 effort 是否值得。

      三千 Agent 的关键，是事实能够汇合#

      — 原文实验做法 · 协调、状态与验证

      费马形式化实验很容易被概括成“1,000 个 Agent，约 30 小时”。工程正文展示了更有价值的分工：一个 lead 与 999 个 helpers 分别运行在独立轻量 VM 中，通过 Git 汇合代码，通过共享 Postgres 认领任务、交换发现和记录完成。模型决定怎么拆、谁来做；程序提供隔离、并发一致性与证明检查。[8]

      Lead 在开始十分钟内自行创建了五张协作表。SQL 的价值在于共享事实与事务，官方材料没有说明数据库替模型执行了固定的调度 DAG。把这个案例读成“模型已经无需状态系统”，或读成“固定 Scheduler 完成了一切协调”，都会错过它的实际组织方式。

      原文记录了一次难度估计被执行反馈纠正的过程。Helpers 起初将 47 条陈述判断为预算内不可完成；在前十条完成后，Lead 调整判断，继续组织攻关。最后约 750 个 helpers 集中解决 Langlands–Tunnell，而这条任务最初的按时完成概率估计低于 1%。[8]

      我的解读：系统应允许实际进度修正模型的难度判断，并用产物检查核验完成声明。这是我从该实验提炼的工程原则，引用支持的是上面的实验过程。

      这项实验究竟证明了什么

      它证明了特定环境下的大规模协作可行性。使用的是早期 Fable 5.2 快照；输入包含 60 条待证陈述、定义、经典路线和 47 条已证引理，完成的是已有费马证明的 Lean 形式化。Fable 与 Opus 对照各只运行一次，并从 18 小时保存点恢复后再给 12 小时。28.7 小时是一次成功演示的结果，尚不能确定稳定成功率或最优团队规模。[1][8]

      Managed Agents 产品另有边界：其 subagents 在同一 session 中共享沙箱与文件系统，并有最多 25 个 child threads 的限制，包含 idle；advisor 与 workflow run threads 不计入这个上限。它与千 VM 实验的执行隔离方式不同。[9]我的迁移建议是借鉴责任、状态、验证与恢复的分工，再按任务选择具体拓扑。

      四本文设计建议：把“目标”变成系统对象#

      — 从资料到设计 · 这里有一步作者的选择

      本节的“目标对象”和“四个接口”由本文提出。Anthropic 的发布页、千 Agent 工程文章没有提出这套对象模型。资料展示了共享协作状态、程序验证与提前停止等问题；我从目标管理的视角，选择把这些职责组织到一个可恢复、修改和验收的目标周围。

      推导过程：事实 → 推论 → 设计选择
      1. 原文事实：千 Agent 实验用 SQL 记录责任与进度，用 Git 和 Lean 汇合、检查产物。提示指南披露模型会提前停止，鼓励持续完成又会增加 token 消耗。[8][6]
      2. 我的推论：需要跨会话或跨执行者继续的长任务，应保存可恢复的工作事实；判断完成时，应有能复查的验收依据。这里把特定实验经验推广到了企业工作，仍需目标任务验证。
      3. 我的设计选择：用一个 Goal 对象关联验收条件、工作事实、资源边界和交付证据，模型会话、子任务与工作流关联到它。这套封装方式来自本文的设计视角，并非原文提供的方案。

      推论的边界：这些资料并不能推出“必须有 Goal 对象”。任务账本、已有工作流状态和独立交付记录也可能解决同样问题；是否统一成目标对象，取决于恢复、协作和验收的实际收益。

      在这个候选设计里，模型会话是推进目标的一次执行上下文，子任务、工作流、工具权限和产物记录与目标关联。下面的迁移任务是本文构造的示例：“将服务 A 的解析模块迁移到 Rust，保持公开接口与回归样例兼容，交付分支、基准测试和迁移说明；先在约定时间与费用内完成原型，再根据证据决定是否继续。”它用来说明结果、范围、验收和预算怎样组合，模型仍可决定中间路线。

      04 / THE CONTRACT AROUND THE AGENT
      本文设计建议 · 四个接口及控制面均为作者方案
      我建议给目标定义的四个接口

      点击节点查看这个候选设计保存什么、由谁负责。本图不是对 Anthropic 原文架构的还原。

      验收条件：先写清结果

      保存交付物、不可改变的范围、质量门槛与未解决项的处理方式。Agent 可以提出澄清和修订建议，变更后保留版本与原因。

      责任：目标负责人定义；系统保存；Agent 按条件推进。

      迁移示例：公开接口兼容，回归集通过，交付分支与基准报告。

      本文建议的职责分工：确定性机制保存事实并执行约束，模型根据新证据调整路线。原文实验为状态与验证提供启发，没有验证本图的 Goal 对象与控制面设计。

      本文进一步提出的候选架构是“薄 Agent + 持久工作流”。这里的“薄”指将持久化、并发控制、权限和检查交给明确机制，让 Agent 集中处理语义判断。我建议保留模型随结果重新拆解的能力，把清晰的数据处理步骤交给程序。不能据千 Agent 实验推定其采用了固定 Scheduler，原文也没有验证本文候选架构的收益。

      另一个可以直接核对的原文事实是会话协议的限制：Fable 5.2 对 preserved thinking 有 prefix、model、account 绑定；改写旧历史可能返回 400，跨型号或账户也可能丢弃思考块。官方 compaction 返回的签名块需要按协议原样保留。[10][11]

      由此提出的本文设计建议：将可供业务恢复的事实与受协议约束的模型会话分别保存。分支、检查结果、责任和未解决依赖需要能被复查；历史消息与 thinking blocks 则按模型协议保留。官方提供 1M 上下文这一规格，[5]但它没有直接说明企业应怎样组织业务状态。两层保存是否有收益，仍取决于恢复需求。

      五模型说“完成”，还缺哪一步#

      — 原文行为实验 → 本文验收建议

      官方提示指南披露，medium 下加入“持续完成工作”的提示后，留下可做工作的会话约减少一半，但输出 token 约增加 30%。强调“代码归你所有”则使输出约增加到 1.5 倍，并增加未请求的修改。它们来自厂商内部行为实验，适用范围有限，却揭示了同一个张力：更坚持执行，也可能花得更多、做得更宽。[6]

      我的验收建议：在提示行为之外设置产物检查。代码可检查回归、接口兼容和变更范围；研究可检查出处、论证、未确定项与实际文件；数据分析可检查口径、输入完整性与可复算结果。下面对三个事件的划分是本文提出的业务设计，原文未定义这套验收状态。

      事件它实际说明什么确认主体
      一轮生成结束当前响应到达停止条件；也可能是长度上限、拒绝或其他终止。客户端解析响应与 stop reason。
      Agent 报告完成模型认为当前工作可以交付，提交自己的判断和产物。Agent；仍属于待核验声明。
      目标被验收产物符合已保存的约束，证据完整，未解决项已被接受或排除。检查程序与目标负责人；系统记录结果。

      科学案例尤其说明“验证”需要分层。费马形式化可以交给 Lean 检查；电子设计还需要真实制造与测试，三款工作原型不足以覆盖长期可靠性和商业认证；理论物理预印本虽有已知特例核对，仍需要外部研究者全面复核。第二篇物理结果还注明 Opus 5.5 后来也得到了同一结果，不能把所有科研成品都归为 Fable 独占能力。[8][12][13][14]

      本文推论：验证能力可能限制可委派的工作规模。当产物需要审阅才能被接受，而验证资源无法随执行量增长时，并行生成会增加待验收积压。在这个前提下，我建议企业先选择有价值且能验收的任务；上面的案例没有直接测量一般企业的验证瓶颈。

      六系统表现，取决于整条执行路径#

      — 原文回退机制 + 本文可观测性建议

      Fable / Mythos 5.2 是同一底层模型的不同安全配置，但允许处理的工作不同。系统卡执行摘要还提供了一个反例：Fable 自身处理提示注入时很稳健，更频繁的 Opus 4.8 fallback 却使整体攻击成功率上升。主模型的得分无法覆盖完整系统的风险。[1][4]

      原生 API 的 server-side fallback 需要 opt-in，只处理指定的 classifier refusal；429 或 overload 不是同一种回退事件。拒绝也可能返回 HTTP 200，需要检查 stop_reason: "refusal"。记录请求模型、实际响应模型、拒绝类别和各次 iteration，才能判断一次任务到底走了哪条路径。[15]

      本文设计建议：将回退前后的工作状态、权限与检查要求分别记录。采用目标对象时，可以保留目标状态，再按实际模型确认本次执行是否仍满足约束。若无法满足，就暂停并记录原因。这个恢复策略由本文提出，官方文档提供的是回退协议与模型限制。

      多 Agent 监控同样要看具体配置。费马实验当时使用 action-based 实时监控，helper 被拦截只移除该 helper；后来才增加 CoT monitor，并加强为任一拦截停全队等待复核。无互联网、严格沙箱中的数学实验，不能直接证明连接企业凭据与开放网络后的表现。[8]

      本文设计建议 · 控制面的观察项

      目标状态、模型路由和权限状态应能够分别观察。至少回答：本次谁在执行，继承了哪些工作事实，使用哪些工具权限，花了多少，哪些检查已通过。这些信息既用于定位失败，也用于最终验收和成本核算。

      七FDE 应卖出可完成的工作#

      — 本文产品判断与核算建议 · 尚未实测

      这篇文章对产品的判断是：企业客户会越来越在意“我交出的目标，有多大概率按约束完成”。一个能讲清责任、进度、费用和验收的交付界面，会比只展示更多 Agent 正在工作更有价值。并行数量与模型档位可以成为实现选择；目标与产物应成为客户能理解的对象。

      同样，经济性应按被验收的目标核算。一次成功前的失败尝试，helper 的重复劳动，advisor 的判断，合并和验证的费用，都属于完成这份工作的成本。人工审阅时间与严重回归需要另列，避免一个更高通过率掩盖更重的审核负担。

      05 / WHAT YOU SHOULD COUNT
      本文建议 · 非 AA 或 Anthropic 定义的指标
      把账本从“调用”移到“交付”
      单次调用成本

      回答这一次多贵；看不见失败、恢复和协作。

      整次运行成本

      所有尝试、子 Agent、advisor、工具与验证共同计入。

      每个被验收目标的成本

      对齐业务收益；再结合交付时长、审核时间与回归风险。

      任务 API 成本 = 全部尝试及协作 API 费用 ÷ 被验收的目标数 用于同一任务集合的方案比较。工具、基础设施和人工成本分别披露；若没有目标被验收，该指标无有效有限值，应报告失败与总投入。

      本文建议的核算口径，不是现有 Fable 实测结论。目标的粒度与验收规则必须一致，才能比较不同模型和协作方式。

      实施时，可以把 Fable 放到当前模型经常失败的关键判断位置，例如复杂计划、卡住后的重规划和交付前的审查。较便宜模型或程序承担清晰步骤。是否采用 advisor、是否并行、是否让 Fable 全程执行，应由同一批任务的验收与全量成本决定。官方 advisor 机制支持 executor 咨询更强模型，但不能直接保证这种组合一定省钱。[16]

      八两周内，把判断变成可比较的证据#

      — 本文试验建议 · 尚未执行

      建议从现有失败记录中挑选一组有价值且可验收的任务，覆盖跨模块迁移、多源研究交付、复杂数据分析等场景。包含简单任务作为参照，避免只选强模型容易展示优势的难题。以下是试验方案，尚未执行。

      时间工作责任主体需要留下的证据
      第 1–3 天统一输入、工具权限、范围、预算与验收条件；准备可运行检查。FDE + 目标负责人固定任务集、验收清单与可复现环境。
      第 4–7 天比较现有模型与 Fable medium / high；重要任务重复运行。评测程序 + 审阅人验收率、失败原因、全部费用、总时长、人工审核时间。
      第 8–10 天在共同的目标记录上比较单 Agent 与小规模并行，核对相同总预算。Agent / 工作流工程师重复工作、冲突、整合错误、并行收益与恢复结果。
      第 11–14 天检查困难任务的 effort 升级，并单独演练中断、拒绝和回退路径。平台工程师 + 目标负责人额外验收收益、实际模型、状态延续和约束执行记录。

      先固定 harness 比较模型，再固定模型比较组织方式，避免把模型、提示、工具和并行方案一起更换后无法归因。小样本用于筛选设计与发现失败模式，不能包装成稳定的总体胜率。

      什么时候继续投入

      如果 Fable 在重要任务上减少返工与人工接管，且每个被验收目标的总投入符合价值预期，就扩大使用。如果小规模并行同时增加冲突与审核负担，就先改善任务边界和提交机制。如果主要失败来自缺失数据与无法验收，下一笔投入应优先补这些条件。

      我的当前判断是：更强模型会扩大可委派工作的范围，围绕目标组织、恢复和验收的能力会随之增值。信心设为“中”，因为目前证据支持能力与工程机制的重要性，仍缺乏目标中文任务、正式发布模型和真实企业工具链上的稳定对照。

      这个判断也允许被修正。如果实际任务中，直接升级模型已经解决绝大多数问题，额外目标管理只增加维护成本，方案应简化；如果验证成本始终超过执行收益，自治范围就应收缩。最终需要回答的是：客户关心的那份工作，是否更可靠地完成了。
