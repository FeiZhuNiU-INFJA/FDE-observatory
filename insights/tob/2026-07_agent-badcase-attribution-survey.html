      Agent Badcase 归因 · 方法论调研

      当客户只愿意交出「轨迹 · 产物 · 打分 · 维度」四类数据时，学界与工业界能为「badcase 归因报告」提供什么样的方法论底盘？

      2026-07-28 ToB Agent 评测 归因分析 方法论调研 草案 时机：进行中 信心：中
      3层
      L1 分类 / L2 定位 / L3 归因
      4类
      客户约定交付的数据：轨迹 · 产物 · 打分 · 维度
      3同心圆
      客户 agent / 开源载体 / 归因服务
      15+
      值得复用的学界工作与开源方案

      起点：一位团队负责人在会上抛出一个具体的方法论问题——「我们要给客户输出 badcase 归因报告，学界现有的方法论都有哪些？我们该抄哪几条？」本文是围绕这个问题的一次调研整理。

      核心论点：「Agent badcase 归因」不是一个方法，而是一条三层堆叠的栈——先把错误分类（L1）、再把错误定位到步（L2）、最后回答为什么错、怎么改（L3）。这三层各有成熟方法论，且都不必依赖对 agent 的 replay 能力。真正的分野不在"能不能重跑"，而在**报告结论到底是「论证」还是「证明」**——这两条 L3 路径都成立，只是可信度不同。
      一页要点
      • 问题栈化：Badcase 归因 = 「L1 是哪类错？」+「L2 是哪一步先错？」+「L3 为什么错、怎么改？」——把三个问题拆开，每一层都能独立落地。
      • L1 不用自己发明：AgentErrorTaxonomy（Memory / Reflection / Planning / Action / System）+ Future AGI 五分类（Planning / Tool / Retrieval / Reasoning / Safety）交叉即可覆盖 80% 场景。
      • L2 有两条主流：反事实回放（AgenTracer / AgentDebug）需要能重跑;Agent-as-a-Judge + 依赖图（GraphTracer / FALAT / AgentEval DAG）纯静态即可做。
      • L3 的关键分野：不是"能不能 replay"，而是"结论是论证还是证明"。A2P / CHIEF / Re-Ex 三样搭起来就是能交付的论证性 L3；CausalFlow / CAR 才是可选的验证性升级。
      • 业界工具留了缺口：Langfuse / LangSmith / Braintrust / Phoenix 都要"上传全量数据"，正好卡在客户拒绝的门槛上——「只要打分和轨迹」的归因方案是差异化窗口。
      • 产品结构：三层同心圆——L1 客户资产不动、L2 开源评测框架（LIFT 通用化）分摊接入成本、L3 归因分析作为付费服务承接分析价值；skill 是这套结构的胶水。
      • 一句判断：方法论 GO、载体 GO、变现 GO——但落地次序是「先做 skill wedge → 拿真实反馈 → 再做通用化」，不要闭门造车。

      一用户故事：为什么要现在做这件事#

      — The evaluation chain and why we enter from the last stage

      先讲清楚问题的来源。团队正在承接客户侧 Agent 系统的评测工作，链路很长——从跑数据、打分、到最后的归因报告，中间夹着人工评审、多模态判官、跨实验对比等一大串环节。团队内部的讨论围绕着一个问题：作为交付方，我们从哪一段切入最有价值？

      共识是把整条链路拆成三段，然后反过来做——不从"数据"往"报告"推，而从"报告"倒推回"数据"。原因不复杂：报告是客户唯一会拿去汇报的东西，前面所有环节的价值都要靠它来兑现；同时它也是唯一一段可以「不动客户系统、也不要客户全量数据」就能建的能力。

      Evaluation Chain
      三阶段评测链路 · 反向切入
      采样阶段客户主导（我们不介入）；打分阶段有共创空间（多模态判官设计）；归因阶段最后交付，但反过来是第一个动手的地方——因为它只要打分产物就能做，不需要重跑 agent、不需要客户全量数据。
      从"能不能做"来看，第 3 阶段成本最低；从"客户是否愿意配合"来看，第 3 阶段门槛最低——两个信号指向同一个入口。

      输入侧同样收敛：只要客户交付四类数据——agent 运行轨迹、产出产物、打分结果、打分维度——不要全量原始数据、不要重跑权限、不要模型底层日志。这既是团队自己给客户的产品承诺（降低对接门槛），也是一个学术意义上的问题约束：在这个约束下，学界的哪些归因方法能用、哪些必须放弃、哪些能改造后用？这就是本次调研要回答的问题。

      调研问题（精简版）
      1. Agent badcase 归因在学界如何被结构化？有没有公认的问题分层？
      2. 每一层有哪些代表方法论？它们各自的输入门槛是什么？
      3. 在「只有轨迹 · 产物 · 打分 · 维度」的约束下，哪几条方法能拼成一个可交付的第一版？

      二把「归因」拆成三层#

      — L1 classify / L2 localize / L3 attribute

      把学界十多年做过的相关工作（从 debugging → error analysis → causal attribution → agent tracing）梳理到一张纸上，最干净的结构是把「归因」拆成三个独立的原子问题，每一层回答一个不同的问题、输出不同的粒度。这三层可以独立设计、独立评测、也独立落地。

      L1Classify
      这条 trace 属于哪类错误？
      失败分类（Failure Taxonomy）
      把 badcase 归到一个词表里——是 Planning 出错、Tool 调用错、还是 Reflection 不足？这一层不追究原因，只做分类学：给每条失败一个标签，让跨实验、跨客户的失败可以被汇总、可以被对比。
      典型输出
      Planning Error · Tool Selection · Retrieval Gap · Reasoning Loop · Safety Violation……
      L2Localize
      是哪个 agent / 哪一步先坏的？
      故障定位（Who & When）
      在多步轨迹里指出决定性错误步（decisive step）——不是最后崩掉的那一步，而是让 trace 从"能救"变成"救不回来"的那一步。多智能体系统里还要多回答一个 who：是哪个角色导致了失败。
      典型输出
      Step 7 · agent「searcher」· 用错了 tool（read_file 应为 search）
      L3Attribute
      为什么坏？改哪一处能救回来？
      根因解释 + 修复建议
      L2 只是指认现场，L3 要给出根因和最小编辑（minimum edit）：如果把这一步改成 X，trace 大概率能翻转到成功。这一层的结论可以是「论证性」的（LLM scaffolding），也可以是「验证性」的（真反事实回放）。
      典型输出
      根因：prompt 未明确「优先使用 search 检索」→ 建议：在 system prompt 加入检索优先级规则

      这个分层对本项目最直接的启发是：三层不是"从上到下必须做完"，而是"每一层都能独立交付一份价值"。第一版只做 L1（打标签 + 汇总统计）就已经能给客户提供他们此前没有的东西；加上 L2 就能进入"哪一步"的粒度；再加上 L3 才是完整的归因报告。这也决定了 roadmap 的优先级——先做 L1 覆盖度，再叠 L2 定位，最后攻 L3。

      三L1 · 失败分类学：不用自己发明词表#

      — Reuse taxonomies, don't invent one

      L1 的核心不是算法，而是词表。词表决定了报告页面上每条 badcase 会被贴上什么标签，也决定了跨实验汇总时哪些失败会被"归为同一类"。有意思的是——学界和工业界过去两年已经收敛出了几套主流分类，直接复用就好。

      分类学 来源 核心类别 对本项目的价值
      AgentErrorTaxonomy UIUC / Stanford（2025，AgentDebug 附带） Memory / Reflection / Planning / Action / System 五模块 基于 500 条真实失败轨迹归纳，模块视角最清晰
      MAST Cemri et al.（2025） System Design / Inter-Agent Misalignment / Task Verification 点出"很多故障不是模型不行，是通信协议不行"
      TRAIL Patronus AI（2025） 148 条 OpenTelemetry trace 的人工标注 最贴近工业观测栈（OTel-native）
      Beyond the Leaderboard Oxford 综述（2026） 工具 / 规划 / 长程 / 多智能体 / 安全 / 测量效度 六大簇 回答"跨场景通用共性"最直接的一篇
      Future AGI 五分类 业界工程口径 Planning / Tool / Retrieval / Reasoning / Safety 学术分类去噪后的工程标签，可直接贴到前场报告上

      推荐做法：AgentErrorTaxonomy（模块视角）× Future AGI 五分类（工程视角）做交叉，一级 5–6 类，二级 20–30 子类；每个客户场景保留 1–2 个专属扩展槽。这样做的价值有三个——(1) 客户能听懂（工程标签），(2) 团队能沉淀（学术模块），(3) 跨客户能汇总（同一套词表）。这个正好对应会议里"所有人在同一套语言体系下讨论问题"的目标。

      四L2 · 定位到步：两条主流路径#

      — Counterfactual replay vs static analysis

      L2 要在多步轨迹里指出"决定性错误步"。学界目前有两条主流路径，分野在于：能不能重跑 agent。

      4.1 反事实回放：因果证据强，但门槛高

      核心操作是从失败轨迹的第 1 步开始，逐步用"理想动作"替换、重跑 agent、观察结果是否翻转——第一次翻转的那一步就是 decisive step。代表工作：

      • AgenTracer（2025，arXiv:2509.03312）—— 把反事实回放 + 编程式故障注入做成数据生成管线，训练出 8B 专用归因模型，Who&When 数据集上准确率显著超过通用 reasoning 模型。
      • AgentDebug（2025，arXiv:2509.25370）—— 把"定位 critical error → 生成靶向 feedback → 迭代 refine"闭环，任务成功率提升 26%。
      对本项目的门槛
      反事实回放要求客户开放 agent 重跑能力：能重放 tool 调用、能 mock 环境、能重复评分。在「客户只给四类数据」的约束下，这条路第一版不可用。但它的思想可以退化——同一 query 的多组实验（模型 A vs 模型 B、提示词 A vs B）之间的差异，就是一次天然的反事实实验，只是干预粒度从"单步"退成了"整套配置"。会议里的「双变量对比」需求，本质上就是把这个退化版当能力用。

      4.2 静态分析：Agent-as-a-Judge + 依赖图

      另一条路完全不重跑，只在已有轨迹上做静态推理。三种主流做法：

      • Agent-as-a-Judge（ICML 2025）—— 让 judge 自己也是个 agent，能调用 execute_code / read_file / search 做外部验证，DevAI 上与人工评分一致率显著超过普通 LLM-as-a-Judge。特别适合多模态判官设计（正好接上会议里第二阶段的共创空间）。
      • AgentEval DAG（arXiv:2604.23581）—— 把 agent 执行显式建成 DAG，每个节点挂 judge，仅"加 DAG 依赖建模"就能给 root cause accuracy 带来 +34pp。这篇是最接近本项目要做的产品形态的学术工作。
      • GraphTracer / FALAT（2025–2026）—— 把节点间的信息依赖（不只是时序）建成图，从失败节点反向追溯根因。FALAT 引入 typed dependency，能区分"引入错误的步"和"仅继承错误的步"。

      这些方法的共同特点：输入只需要 trace（可以是打分/日志/工具调用），不需要重跑——正好落在本项目的数据契约里。第一版 L2 就从这条路搭。

      五L3 · 从"哪一步"到"为什么 & 怎么修"#

      — The most misunderstood layer

      L3 是最容易被误解的一层。误解在于——一旦提到"归因"这个词，很多人就直觉觉得非得能重跑（replay）才能做。这不对。L3 有两条完全独立的路径，一条要 replay、一条不要；差别不在"能不能做"，而在结论的可信度类型。

      REFLECT 论文里那句话最能点破："correction is not attribution"——你只是给了一个更合理的解释，不等于你证明了那就是原因。真正的证明要靠反事实实验。但这不等于"没实验就没归因"——把两条路认清楚，第一版就可以理直气壮地只做左边一条。

      路径 A
      论证性 L3 · Argumentative
      在已有轨迹上做静态推理，产出"看起来最合理"的根因解释。

      5.1 论证性 L3 的最小可用套装

      三样组合起来就是一份能交付的 L3 报告——都是纯静态、都不需要 replay：

      Abduce · Act · Predict

      A2P scaffolding

      Westlake 2025 提出的三步 prompting——先反推隐藏根因（Abduction）、再定义最小干预（Action）、再模拟干预后结果（Prediction）。整个过程在 LLM 一次推理内完成，Who&When step accuracy 从 16.67% 拉到 47.46%。是"没有 replay 也能做因果推理"的方法学基石。

      Hierarchical Causal Graph

      CHIEF 三判据

      区分"症状步"与"根因步"的判据非常工程化：local-origin OR earliest data corruption AND irreversibility AND strongest downstream impact。这三条判据可以直接抄进报告 rubric，用来在 L2 定位的候选步里再挑出真正的 root cause。

      Revising after Explanation

      Re-Ex 报告模板

      "先解释错误 → 再基于解释重写"——不仅是一种归因方法，也是报告的最佳输出模板：错误陈述 → 证据 → 修复建议对比对。前场同学交付时天然在同一套语言里，避免"每个人写的报告都长得不一样"。

      5.2 一点诚实：论证性 L3 会在哪儿翻车

      说完能用的，也要说说不能用的。论证性 L3 的结论本质是可辩驳的——你说"因为 step 3 tool 参数错，导致后面 5 步偏"，这个论断没有反事实实验作证，只是在轨迹上找到了最合理的解释。以下场景会翻车：

      • 长轨迹（>20 步）——错误交互复杂，pattern matching 会找错步。
      • Silent failure——trace 表面完全正常，答案却错，这类情况必须 replay 才能暴露。
      • 决策步 vs 执行步分离——比如"是否退款"的决策在早 step、"执行 issue_refund"在晚 step，静态推理容易把归因错误放到执行步。
      推荐做法：给结论标注证据类型
      借鉴 CAR 的做法——每条归因结论在报告里明确标注 "证据类型：静态推理 / 反事实验证"和一个置信度分数。这样：(1) 客户知道结论的可信度，(2) 前场同学交付时"在同一套语言里"，(3) 后期升级到验证性 L3 时不用改报告结构，只改证据类型标签。

      六方法学 × 数据契约 · 匹配矩阵#

      — What we can actually build with what we get

      把上面所有方法学放到一张表里，用"客户只给四类数据"这个硬约束筛一遍——绿色是可以直接用、黄色是能改造后用、红色是必须客户开放更多权限才能用。

      Data Contract
      四类数据 → 三层归因输出
      客户只交付轨迹 / 产物 / 打分 / 维度四类；我方基于此完成 L1 分类 · L2 定位 · L3 论证性归因。不需要重跑 agent、不需要模型底层日志、不需要生产环境访问权限。这是产品对客户的承诺，也是本次调研的约束条件。
      「必须给全量数据才能分析」的门槛对客户是一种风险；「只要四类数据」既是产品差异化，也是对客户的保护。

      七对本项目的落地建议#

      — A stack we can actually ship

      把这次调研的结论压成一份可以直接用的技术栈：

      第一版能力（不需要客户额外配合）
      1. L1 分类学：AgentErrorTaxonomy × Future AGI 五分类交叉，一级 5–6 类、二级 20–30 子类，客户场景保留专属扩展槽。
      2. L2 定位：Agent-as-a-Judge + AgentEval DAG 静态建图，双变量场景加"首个显著分歧步"对齐算法。
      3. L3 论证性归因：A2P scaffolding + CHIEF 三判据 + Re-Ex 报告模板；每条结论标注证据类型 + 置信度。
      4. 报告标准化：Potato trajectory_eval schema 作为最小字段集（correctness / error type / severity / rationale / running score），前场同学"在同一套语言体系里讨论问题"。
      第二版能力（当客户愿意开放更多权限时）
      1. L3 验证性归因：CausalFlow 的 CRS 反事实评分 + CAR 的 Shapley 信用分配——需要客户开放 replay 接口，但只作为高级付费能力，不是基础版准入条件。
      2. Cross-run 共性挖掘：把所有失败步做 embedding 聚类，命名成 named signals（参考 Latitude Signals），报告里输出"top-K 反复出现的失败模式"——这正好对应"越通用越有价值"这条判断。
      3. 自动化评测环节延伸：在打分阶段（第二阶段）加入 Agent-as-a-Judge 的多模态判官能力，与客户共创；这是反向推进的第二个自然落点。

      7.1 差异化的定位

      行业里已有的一堆工具——Langfuse / LangSmith / Braintrust / Arize Phoenix / MLflow——都要客户"上传全量数据"，正好卡在客户拒绝的门槛上。本项目的差异化窗口就在这里：只要打分和轨迹，不要全量数据；输出标准化归因报告，不要客户去平台里点点点。这不是能力更强，是合约更轻——对企业客户来说，合约门槛低于工具能力更重要。

      7.2 需要和算法同学对齐的问题

      下面这些问题是纸面调研解决不了的，得约到相关算法同学一起过一遍：

      1. 客户交付的"打分数据"粒度到底是 trace 级还是 step 级？如果只到 trace 级，L2 定位必须走 judge 二次拆解，方法学要重估。
      2. 客户是否愿意开放 rubric 定义？rubric tree 是把"打分维度"翻译成"归因维度"的关键桥梁。
      3. 双变量对比里"变量"的可枚举范围（模型 / prompt / workflow 节点 / tool 版本）？变量维度决定统计分析的 feature space。
      4. 是否需要复用内部现有的进化 / auto-prompt 框架的对比协议？会议里提到"作为进化框架的延展"，需要看是否共享 experiment schema。
      5. 报告输出形态：纯文本 markdown / 交互式 HTML / 集成到现有平台？这决定了 L3 结论的呈现是否能利用 rubric tree 的层级结构下钻。

      八接入方案：开源框架 + Skill + 归因分析#

      — How this actually reaches customers

      方法论到位了，还剩最后一个问题：怎么把归因能力送到客户手里？方法论本身不是产品，"客户能十分钟接入、跑一次评测就拿到归因报告"才是产品。这一节把接入方案单独拆出来。

      8.1 一条被忽视的路径：借开源框架做载体

      过去做企业交付的默认模式是——写一份 SDK、给一份接入文档、派一个前场工程师帮客户接。这套模式在 Agent 评测这个场景里有个致命的成本：每个客户的 agent 编排框架都不一样（有的是 LangGraph、有的自研、有的走 dify），SDK 每接一个客户就要改一次，前场同学的时间被无限稀释。

      换个思路——如果已经有一个开源评测框架，客户接入它的成本已经被开源社区分摊了；我们只在这个框架之上做归因分析，接入工作量就从"改客户系统"退化成"客户接一个开源工具 + 我们消费它的输出"。这是**我们内部一个已经在做的开源项目 LIFT** 的天然定位——只要把它从"进化增益专用"通用化成"任意 agent 评测框架"，就能作为这条路径的载体。

      关键假设
      本节论证的所有产品结构，前提是 LIFT 可以通用化（从"专门评测进化增益"改造成"通用 agent 评测框架"）。这个改造是可行的（原有的 warmup / holdout 逻辑可以作为一个 preset 模式保留），工作量约 4–8 周，是走这条路径的先决投入。

      8.2 三层同心圆：开源做载体、服务做变现

      Product Layering
      三层同心圆 · 每一层的角色都不一样
      L1 客户资产——客户自己的 agent，我们不动。L2 开源载体——LIFT 通用化后作为接入桥梁，成本被开源社区分摊。L3 变现层——归因分析作为付费服务，消费 L2 产出的标准化 trace 与 scores。三层解耦，客户只用 L2 免费也能走通，升级 L3 才付费。
      L1Own
      客户的 Agent
      Customer Asset
      不动。任何编排框架（LangGraph / 自研 / dify）都可以，通过 skill 引导接入到 L2。
      L2OSS
      LIFT 通用化后的开源评测框架
      Distribution · Free
      承担"跑评测 + 采 trace + 出基础 dashboard"。开源分摊接入成本，也是获客通道。
      L3Paid
      归因分析服务
      Monetization · Core
      消费 L2 的 trace + scores，跑 A2P / CHIEF / Re-Ex 三件套，出标准化归因报告。这是变现层与真正的差异化。

      这个结构最有意思的地方在于——L2 免费也能走通。客户只用 L2 就已经比"什么都没有"好很多（有评测框架、有 dashboard、有 trace）；他要不要升级到 L3 完全是自愿的。不升级也是获客：L2 一直在按我们定义的契约产 trace，未来任何时候升级 L3，数据都是现成的。

      这就是开源做载体、服务做变现的经典结构——类似 LangChain 之于 LangSmith、Ray 之于 Anyscale。**skill 是这套结构的"胶水"**——它让 L1 → L2 的接入变成引导式的十分钟事件，而不是"读一本文档、写一堆胶水代码"的一周项目。

      8.3 差异化在哪：不是评测跑得好，而是 skill × 归因

      要清醒一点——**开源评测框架赛道已经很拥挤**。LangSmith / lm-eval-harness / HELM / Braintrust / OpenAI evals 都在做。LIFT 通用化后想突围，靠的不是"评测跑得比谁好"，而是三件事绑在一起的组合拳：

      Wedge 1 · 接入体验

      Skill 化引导

      行业目前没人这么做。skill 让"接一个评测框架"从"读一份 30 页文档"变成"跑一个引导脚本"。这是接入体验层面的真差异化，不是能力差异化。

      Wedge 2 · 轻数据契约

      只要 4 类数据

      其他平台都要"上传全量数据"，我们只要轨迹 / 产物 / 打分 / 维度。对企业客户，合约门槛低于工具能力更重要——数据安全是他们的第一顾虑。

      Wedge 3 · 分析深度

      L1/L2/L3 分层归因

      其他工具停在 trace viewer + 单条 judge；我们做分类学 + 定位到步 + 论证性根因 + 修复建议。这是从"看板工具"跳到"分析师团队"的定位跃迁。

      如果三样只做一样
      单独做 skill 引导——只是好用的 CLI，无法变现。单独做归因分析——没有获客通道，卖不动。单独做通用评测——直面 LangSmith 的正面竞争。只有三样绑一起才是差异化。

      8.4 落地路径：先做 wedge，再做通用化

      方向定了，落地次序也要清晰。不要一上来就投 8 周做通用化——那是闭门造车。正确的次序是**先用 wedge 拿真实客户反馈，再回过头做通用化**。

      1
      Wedge First
      先把 skill 打磨出来
      即使 LIFT 还是"进化增益"专用框架也没关系。先把 skill 引导接入 + langfuse 采集 + 基础归因报告这三件事做通，拿给 3–5 个真实客户试跑。验证"skill 化的接入体验"是否真的解决问题。
      周期：约 4 周
      产出：skill + demo
      2
      Feedback-Driven
      再基于反馈做通用化
      Runtime 抽象怎么设计、suite 格式要不要兼容 HELM / lm-eval-harness、judge 逻辑要多灵活——这些不是纯技术问题，是产品问题，必须靠真实客户的接入反馈来定。避免"我们以为的通用"变成"没人用的通用"。
      周期：约 4–8 周
      产出：LIFT v2 通用化
      3
      Decouple & Scale
      归因分析先独立起步
      归因分析不要马上和 LIFT 深度耦合。先做成独立服务，输入接口是"任何符合契约的 trace + scores"。等 LIFT 通用化到位，再把 LIFT 作为归因分析的首选默认数据源（不是唯一）。这样即使 LIFT 卡壳，归因分析可以独立活着。
      周期：与 1/2 并行
      产出：独立归因服务 API

      这三步的核心逻辑是解耦风险：任何一步做不成，其他两步都还能独立活着。skill 做不出效果——归因服务还能独立卖；LIFT 通用化卡壳——skill + 归因服务照样能对接 LangSmith / lm-eval-harness 的 trace；归因分析不好卖——LIFT 加 skill 至少还是个不错的开源项目。三条腿走路，比一条腿蹦要稳。

      一句话总结
      LIFT 是评测的锅，我们的归因分析是评完之后的品菜师。锅可以借开源社区的、可以让客户免费用；但品菜师是核心价值，是变现层。skill 是这两层之间的胶水，让接入变成十分钟的事。三层同心圆——L1 客户资产不动、L2 开源分摊接入成本、L3 服务承接分析价值。

      九判断印章#

      Verdict
      • 时机 · 进行中：业界几家工具型平台在 2025-2026 都陆续加入 trajectory-level 分析，但都要求"全量数据 + 平台自主接入"——留出了「轻合约、专注归因报告」的产品缺口。此刻切入正当其时。
      • 信心 · 中：方法论层面已经足够扎实（十多篇成熟工作 + 多个开源实现）；不确定性主要在客户交付的数据粒度与 LIFT 通用化的执行速度——这两条走通了就是完整闭环。
      • 必须记住的第一句：L3 归因不是必须依赖 replay 的；「replay 是验证的前提，不是归因的前提」。第一版就靠论证性 L3 落地，把 replay 作为付费升级预留。
      • 必须记住的第二句：LIFT 是评测的锅，归因分析是品菜师。三层同心圆——开源做载体、服务做变现、skill 做胶水——不是三选一，是三个一起做才能有差异化。
