      二架构：双身份 · 三层落点#

      — 一个应用（Bot 身份）+ 一个 OAuth（用户身份），凭据分两处存

      整个项目的核心难题不是「怎么调 Managed Agents API」，而是怎么把「谁在跟 Bot 说话」和「Bot 代表谁操作资源」两件事拆开。作者用两次扫码解决——这也是给客户教练的关键：

      Bot 身份 → 本地文件；用户身份 → Ark Vault。两条线交汇于 Session：vault_ids: [vaultId] 挂进来后，沙箱内 lark-cli 自动读 $LARKSUITE_CLI_USER_ACCESS_TOKEN 以用户身份跑。

      作者的原话（README 里）：「这两个身份不能混为一谈：Bot 身份可以收发消息，但看不到你的个人资源；用户身份可以访问你授权的办公数据，却不负责承载消息入口。」——这是 FDE 给客户讲多租户设计时最容易被质疑的一句话，这个项目给了实证。

      每一步的关键设计：

      4.1 步骤 1-2：WebSocket 而不是 HTTP 回调

      飞书事件订阅有两种：HTTP 回调（要开公网） / WebSocket 长连接（本地也能跑）。作者选后者——「使用长连接接收事件」在 SDK 层就是 Lark.WSClient。对客户而言，本地开发不需要 ngrok 或公网入口是首次接入的最大摩擦点，这个选择直接解掉。

      4.2 步骤 3：飞书 3 秒响应约束的解法

      飞书要求事件订阅 handler 3 秒内 ACK，否则重试。Agent 通常跑几十秒到几分钟，怎么办？作者的处理：

      // feishu.ts:29 · SDK 的 handler 只做去重与入队，不 await 执行
.register({
  "im.message.receive_v1": async (data) => {
    const message = normalizeFeishuMessage(data);
    if (message) options.gateway.accept(message);  // 立即返回
  }
})

// gateway.ts:49 · accept() 内部 enqueue 后立即返回，实际处理进队列异步跑
accept(message): boolean {
  if (!this.store.claimEvent(message.eventId)) return false;  // SQLite 幂等去重
  this.queue.enqueue(this.store.conversationKey(key), async () => { ... });
  return true;
}

      KeyedQueue 的语义：按 (tenant, chat, thread, user) 分桶串行——同一会话消息按顺序处理，不同会话可并发。见 gateway.ts:18。这是给 FDE 的选型参考：Managed Agents 单个 Session 是串行的，多会话并发要靠客户端 keyed 分桶。

      4.3 步骤 4：Session 复用的关键在四元组

      // gateway.ts:109 · Session 归属的 key
toConversationKey(message) {
  return {
    tenantKey: message.tenantKey,
    chatId: message.chatId,
    threadId: message.threadId,
    userOpenId: message.chatType === "p2p" ? message.userOpenId : ""
  };
}

      思考：群聊里 userOpenId 置空——同一群里不同人 @Bot 会共享一个 Session（有共同上下文）；单聊里带 userOpenId——防止群里的私信被认成群消息共享上下文。threadId 独立分桶——飞书话题群里每条主帖是独立 Session。这个 key 设计客户可以照抄，只需按自己的消息平台替换字段。

      4.4 步骤 5：SSE 消费与 event.id 去重

      // ark.ts:164 · run() 的事件循环
const seen = new Set<string>();
for await (const event of this.streamEvents(sessionId, controller.signal)) {
  if (event.id && seen.has(event.id)) continue;   // 幂等
  if (event.id) seen.add(event.id);
  if (event.type === "agent.message") messages.push(eventText(event));
  if (event.type === "session.error") return { terminal: "failed", messages };
  if (event.type === "session.status_idle") return { terminal: "idle", messages };
}

      SSE 解析器 drainEventBuffer 手写实现（ark.ts:234）：按 \n\n 分块，每块 data: 行拼一起 JSON.parse。兼容 \r\n 归一化，对边缘半块留 rest 下次继续——这是标准 SSE 实现，客户 Java/Python 端可以照葫芦画瓢。

      4.5 步骤 6：最后一条 agent.message 才是最终结果

      // gateway.ts:118 · 关键洞察：一个 run 可能有多条 agent.message
resultToReply(result) {
  // 前面的通常是"让我先检查…"一类工具执行播报
  // 最后一条才是面向用户的完整结果
  return result.messages.at(-1)!;
}

      这一条最容易被忽略——初次接入的客户经常抱怨"为什么每条工具调用前都有一段废话消息，用户端很吵"。答案：Managed Agents 的 agent.message 会包含 Agent 的中间思考陈述，只有最后一条才是最终交付。要么按这个项目取 .at(-1)；要么按 agent.thinking 事件切段。

      五超时兜底：AbortController + 补拉历史#

      — SSE 断开不是终点，事件历史才是真源

      10 分钟到点，如果 Session 恰好在最后一秒完成——SSE 流可能已经被 abort 掉了，但事件已经落库。作者的处理是：

      // ark.ts:195 · 超时后的补救
private async recoverTimedOutRun(sessionId, startedAt) {
  for (let attempt = 0; attempt < 3; attempt++) {
    if (attempt) await new Promise(r => setTimeout(r, 5_000));  // 5s 间隔重试
    const response = await this.request(
      `/sessions/${sessionId}/events?limit=200`       // GET 事件历史
    );
    const events = ((await response.json()).data ?? []);
    const result = resultFromEvents(events, startedAt);   // 按 processed_at 筛本轮
    if (result) return result;
  }
  return undefined;                                   // 真的超时了
}
      这个模式的 FDE 应用

      上一篇厂商拆解讲过"事件 API 全量留存 vs 模型窗口自动压缩"。这个项目实证了这个设计的运行时价值：SSE 是推流层，事件历史 API 是持久层；网络抖动 / 客户端超时 / 甚至进程重启后，都能通过历史 API 恢复。把这段代码抄给客户做他们的 SDK 骨架，能省很多"我的消息为什么丢了"的答疑。

      六进度旁白：不刷屏的一门艺术#

      — 只转发 Agent 主动提供的描述，绝不打印 command 或参数

      这个细节值得单独说。Agent 干活时会产生大量 agent.tool_use 事件——如果全部转发到聊天窗口，用户看到的就是几十条"正在调用工具：bash / 正在读取文件：xxx.md"，非常吵。

      作者的解法（ark.ts:254）：

      eventProgress(event) {
  if (event.type === "agent.tool_result" && event.is_error === true)
    return "工具执行未成功，Agent 正在尝试恢复";
  if (event.type !== "agent.tool_use") return undefined;

  const description = event.input?.description?.trim() ?? "";
  // 只展示 Agent 主动提供的简短描述
  // 绝不转发 command、路径或完整工具参数
  return description
    ? `正在执行：${description.slice(0, 120)}`
    : `正在调用工具：${name.slice(0, 80)}`;
}

      关键洞察：内置工具的 bash / edit 等都接受一个可选的 description 参数——这是 Anthropic 早期 Claude Code 就采纳的模式，让 Agent 用自然语言总结即将执行的动作，用于对外展示。这个字段应该出现在 FDE 的客户教程里——教客户在 system prompt 里要求 Agent 每次调工具都填 description。

      此外，Gateway 主流程甚至不订阅 onProgress（gateway.ts:92-94）：

      // 过程事件仍由 ArkClient 消费，但不传 onProgress，
// 避免把 tool_use/tool_result 转成"执行进度：xxx"消息刷屏。
const result = await this.ark.run(sessionId, message.text, timeoutMs);

      取而代之：2.5 秒延迟提示。如果 Session 复用（不是首次创建），2.5 秒内不完成才发一条"已收到，正在处理，请稍候"——低频、够用、不吵。

      八项目边界与不足#

      — 抄之前先看它没做什么

      当前边界
      • 单用户 MVP：只有 init 时授权的 open_id 能驱动 Agent，来自其他人的消息会被拒绝（gateway.ts:67）
      • 不支持 Group Bot 多用户：群里只处理 @Bot 消息，且所有 @Bot 都归给 init 的 open_id——群成员各自不能带自己身份
      • 不支持图片 / 文件 / 富文本 / 卡片：只处理 text 消息类型（feishu.ts 显式过滤）
      • 没有 Multi Agent：mcp_servers: [], skills: []——纯内置工具集起 lark-cli
      • 没有 Outcome 定义：不用自动评估 rubric 迭代
      • 没有 Memory Store：跨 Session 的项目规范 / 用户偏好靠 /new 手动重置来管理
      • 没有 Custom Skill 上传：完全靠 lark-cli 自带的 skill hub

      换个视角：这些"没做"的部分，恰好是客户产品化时要补的能力。可以按这个清单排优先级：多用户 → 文件消息 → Skills → Memory Store → Outcome → Multi Agent。

      九FDE 应答剧本：怎么把这个项目用起来#

      — 不同客户场景的不同用法

      客户诉求用它做什么要改的地方
      「我想快速试一下 Managed Agents 能不能做我们内部 IM Bot」 直接 npx --yes arkagent init——半小时看到效果 无（个人试用）
