      核心论点：Codex Harness 和 dsh 都在解同一道题——「怎么让 agent 的执行层能被无痛改造、又能承接长程任务」。但它们的答案在相反的方向：dsh 把可演化性押在「无特权内核 + 可逆 effect」的内部组合上；Codex 把它押在「一条稳定、向后兼容的客户端协议（app-server）」这个外部边界上。前者是「一切皆插件」的架构纯度，后者是「一切皆协议客户端」的产品化契约。
      一页要点
      • 开源的是执行层，不是模型。Apache-2.0 下放出 codex exec（CLI 一次性作业）、Codex SDK（TS/Python）、app-server（产品嵌入用的协议服务）三层集成面；模型访问与托管服务仍独立。
      • Agent Loop 的骨架很「经典」：prompt 是一个带 role 的 item 列表，发给 Responses API，拿到 SSE 流；模型要么给最终消息、要么发 function_call，工具输出 append 回 input，循环到不再调工具为止。一次「输入→响应」= 一个 turn，多个 turn 组成一个 thread。
      • 状态模型是它最反直觉的取舍：默认 HTTP/SSE 路径每次请求完全无状态（store: false、不带 previous_response_id、始终发 prompt_cache_key）——旧 prompt 是新 prompt 的精确前缀，靠 prompt caching 省成本、靠 encrypted_content 兼容 ZDR；另有一条 WebSocket 路径会复用 previous_response_id 只发增量 item，两条路并存。
      • 可演化性靠协议边界兜底：app-server 是「JSON-RPC lite」（去掉 "jsonrpc":"2.0" 头、JSONL over stdio），围绕 Item / Turn / Thread 三原语，双向、可发审批请求、向后兼容——老客户端能安全对接新服务端。
      • Harness 设计本身就是杠杆：仅靠「保留推理 + 上下文压缩」两项调整，GPT-5.6 Sol 在 ARC-AGI-3 从 13.3% 升到 38.3%，输出 token 少 6 倍。
      • 与 dsh 对照：Rust 生产单体 vs TS 226 包插件树；协议契约解耦 vs 内核组合解耦；无状态 prompt 前缀 vs 事件溯源日志；「已驱动真实产品线」vs「developer preview、明说会破坏兼容」。

      一它到底是什么：驱动所有界面的那层执行框架#

      — 开源的是 harness，不是模型，也不是 Codex 产品

      大多数人通过 App / CLI / IDE 扩展认识 Codex。但按 OpenAI 的说法，这些只是「同一个底层系统」的几种界面。这个底层系统就是 Codex Harness——「模型与真实世界之间的那层脚手架」：它帮模型收集上下文、推理、调工具、在配置的边界内运作、请求审批、把工作跨轮次推进。2026-08-19，OpenAI 把它作为平台开源，落在 github.com/openai/codex，Apache-2.0。

      Codex as a platform · 原文摘引

      「The open-source Codex harness is what powers all these experiences. It helps models gather context, reason through tasks, use tools, operate within configured boundaries, request approval, and carry work forward.」

      「The open-source layer is the harness and integration surface; model access and managed services remain separate.」

      官方把「开发者接入」切成三个层级，覆盖从 CI 脚本到产品级嵌入的全场景——这三层就是本次开源的主体：

      最轻 · codex exec
      一次性、非交互作业
      一条 CLI 命令跑一个有边界的 agent 工作流、返回结构化输出。适合 CI/CD、批量脚本、后台任务，无需管理会话。
      程序化 · Codex SDK
      TypeScript / Python
      在应用代码里启动 / 恢复 / 流式传输 Codex 任务的编程接口；源码在 openai/codex/sdk，是常见程序化工作流的低摩擦入口。
      产品级 · app-server
      长驻进程 + 文档化协议
      当 agent 是产品本身的一部分时用它：应用连到本地 Codex 进程，开线程、流事件、中断、暴露工具、回应审批。源码在 codex-rs/app-server（Rust）。
      载体
      Rust 单体 · codex-rs 工作区
      仓库 96%+ 是 Rust；codex-rs 是一个 Rust workspace，CLI/exec/app-server 等都在其中。另有 openai/skills、codex-universal 两个配套仓库。

      注意这里和 dsh 的第一处根本差异已经浮现：dsh 的 README 第一句是「everything is a plugin」，连 agent loop 都是插件；Codex 的自我定义是「the harness and integration surface」——它不承诺「内部一切可换」，而承诺「接入面（integration surface）稳定可依赖」。前者是内向的架构宣言，后者是外向的产品契约。这条线索会贯穿全文。

      二Agent Loop：prompt 作为 item 列表 · turn / thread#

      — 骨架很经典，值钱的是「怎么组 prompt、怎么续 prompt」

      Codex 官方那篇 《深入解析 Codex 智能体循环》把 loop 拆得很干净：agent 接收用户输入 → 组成prompt → 发给模型推理 → 模型要么给最终响应、要么发工具调用请求（如「运行 ls」）；若是后者，agent 执行工具、把输出 append 回 prompt，再次推理，循环往复，直到模型不再调工具、转而生成一条面向用户的 assistant message。从「用户输入」到「agent 响应」的完整过程叫一个 turn（Codex 里也叫一个对话 thread）。

      骨架不稀奇，稀奇的是 prompt 的构造。Codex 走 Responses API：prompt 是一个 item 列表，每个 item 带一个决定优先级的 role（降序：system > developer > user > assistant）。用户消息之前，Codex 先注入几条固定 item：

      # Responses API 的 input 列表（用户消息之前的固定前缀）
1. role=developer  # 描述 shell 工具的沙箱权限：可写目录 / 网络 / 何时该问用户
2. role=developer  # （可选）config.toml 里的 developer_instructions
3. role=user       # （可选）聚合的 user instructions：AGENTS.md / AGENTS.override.md / skills 元数据…
4. role=user       # <environment_context> cwd + shell </environment_context>
# —— 之后才 append 用户真正的消息 ——

      而 instructions（系统/开发者基指令）读自模型自带的 base_instructions（如 codex-rs/core/gpt-5.2-codex_prompt.md），tools 里则塞进内置工具（shell、update_plan）、Responses API 工具（web_search）和用户经 MCP 提供的工具（mcp__weather__get-forecast）。把静态内容（系统指令、工具定义）放在 prompt 前部——这是刻意的，为的是下一节要讲的缓存。

      与 dsh 对照：谁决定「模型看到什么」

      在 dsh 里，「注入 system.message / 改写模型可见消息」是挂在 agent/pre-step 上的一个 waterfall 可逆监听器——切角色 = 卸旧挂新。在 Codex 里，这件事是组 prompt 的固定装配流程（读 AGENTS.md、拼 developer 消息、附 environment_context）。dsh 把「可变」做成运行时的 effect 组合；Codex 把它做成一条清晰但相对固定的装配线。灵活度 vs 可预测性，各取一端。

      三无状态请求 × prompt 前缀缓存 × ZDR#

      — 长程状态的第一种答案：把它留在 prompt 前缀 + 服务端缓存里

      这是 Codex 最值得单拎出来的工程取舍。随着 loop 迭代和 turn 累积，prompt 会越来越长；Responses API 提供了 previous_response_id 来避免每次重传全量历史。Codex 的默认 HTTP/SSE 路径明确不走这条：请求里写死 store: false、不带 previous_response_id、每次都带上 prompt_cache_key——目的是让每个请求完全无状态（stateless），从而干净地支持 Zero Data Retention（ZDR）。代价是整段 JSON 会随对话二次增长（quadratic），但这个代价被两件事对冲掉：

      「旧 prompt 是新 prompt 的精确前缀」是刻意设计：它让服务端 prompt caching 能命中不变的前缀、只对新增部分算钱，从而把「全量重传」的成本压下来；同时「不依赖服务端存储」换来 stateless + ZDR。这是 Codex 对「长程状态往哪放」的回答——放进 prompt 前缀，靠缓存兜成本。
      一个容易被博客口径带偏的细节：还有第二条传输路径

      「不用 previous_response_id」是默认 HTTP/SSE 路径的取舍，不是全局绝对。源码里 core 客户端还实现了一条 WebSocket 传输：它会先做一次 generate=false 的连接预热，随后复用同一连接的 previous_response_id、只把增量 item（而非全量历史）打进 response.create。也就是说，「无状态 + 前缀缓存」是省 token 的一种策略，「有状态 + 增量发送」是省带宽/延迟的另一种策略——两条路在 codex-rs/core/src/client.rs 里并存，按连接方式择一。本页图示描述的是默认路径。

      这一取舍和 dsh 形成漂亮的对照。dsh 的答案是事件溯源：一切模型可见输入都必须走 append() 落进会话日志，内存里的消息只是日志的投影（deriveMessages）；崩溃后重放日志即恢复，fork / resume / 审计是免费副产品。两者都在解「长程任务的状态一致性」，但——

      维度Codex（源码核对）dsh（已核对）
      状态的「家」prompt 前缀（每次全量重发）append-only 会话日志（单一事实源）
      成本对策服务端 prompt caching 命中前缀内存投影 + 压缩，避免重放全量
      恢复 / fork靠客户端 / thread 持久化重建 input重放日志天然得到，fork/resume 免费
      隐私姿态stateless + ZDR + encrypted_content遥测接缝「捕获→脱敏→单后端」
      本质把历史留在线上（prompt）把历史留在本地日志

      四App Server：把可演化性押在协议边界上#

      — JSON-RPC lite · Item / Turn / Thread · 双向 · 向后兼容

      如果说 dsh 的「可演化性」来自内核（换任意插件是配置动作），那 Codex 的「可演化性」来自协议。App Server 是所有 Codex 界面（CLI / IDE / web / macOS App）共享的那条底层通道：一个双向、客户端友好的 JSON-RPC API。它刻意用了「JSON-RPC lite」——保留 request/response/notification 三种形态，但去掉 "jsonrpc":"2.0" 头、用 JSONL over stdio 而非严格 JSON-RPC 2.0，好让各语言客户端更容易绑定。

      进程内部分四块：stdio reader（读客户端）、Codex message processor（把客户端请求翻译成 core 操作、把内部事件翻译成稳定的 UI-ready 通知）、thread manager（线程生命周期）、core thread（跑核心 agent loop + 持久化）。对外则围绕三个原语：

      Item / Turn / Thread：Item 是输入输出的基本单元（用户消息 / agent 消息 / 工具执行 / 审批请求 / diff），带 item/started → item/*/delta → item/completed 生命周期；Turn 是一次用户输入触发的工作单元；Thread 是可创建 / 恢复 / fork / 归档的持久会话容器。协议双向——服务端能反向发 approval 请求并暂停这一 turn；且向后兼容，老客户端能安全对接新服务端。

      「向后兼容的协议」这四个字，是 Codex 可演化性的真正落点。它意味着：OpenAI 可以在服务端持续优化 harness、修 bug、换实现，而不要求客户端跟着升级；你基于今天的 app-server 建的产品，明天还能跑。为此它甚至提供了从 Rust 协议定义生成客户端类型的工具：codex app-server generate-ts（TS）与 generate-json-schema（其他语言）。这是一种「契约优先」的演化——把稳定性焊在边界上，而不是焊在内核纯度上。

      还有一条更轻的接入：codex mcp-server（已标记 deprecated）

      如果你已有 MCP 工作流，Codex 也能作为 MCP server（codex mcp-server）被当成一个可调用工具——但要注意：源码里这条子命令已打上 deprecation warning（「will be removed in a future release」），官方方向是收敛到 app-server。它只暴露 MCP 定义的内容，拿不到 app-server 那样更丰富的 Codex 专属交互（如 diff 更新）。另有一个独立的 codex mcp 子命令，用途相反——是管理 config.toml 里配置的外部 MCP server 启动器，别和 mcp-server 混淆。要深度嵌入用 app-server，要轻量互操作可暂用 mcp-server——这与 dsh「把 MCP toolset 作为 ctx.tools 的一个 Consumer 挂上去」是两种接法：Codex 把 MCP 当成对外的一个可选门面，dsh 把它当成内部接缝的一个消费者。

      五Harness 设计本身就是杠杆：一组数据#

      — 同一个模型，只改 harness，成绩接近翻三倍、token 省六倍

      OpenAI 用一组数据来论证「为什么值得在 harness 上下重注」：在难度极高的 ARC-AGI-3 上，仅对 harness 做两项调整——保留推理（retained reasoning）与上下文压缩（context compaction）——GPT-5.6 Sol 的得分就从 13.3% 升到 38.3%，同时输出 token 少了约 6 倍。

      「保留推理」= 跨轮次带上模型的推理内容（对应前面 reasoning / encrypted_content 那一环）；「上下文压缩」= 上下文窗口填满时把历史编码成更小的表示，而非简单文本摘要。这两项都是 harness 层的活，模型本身没变——这正是 OpenAI 把 harness 开源当「平台级」动作的底气。

      六安全边界：沙箱只管 shell，审批走策略模板#

      — 边界清晰，但覆盖面与 dsh 的「三接缝全 fail-closed」不同

      Codex 的边界机制诚实而克制。沙箱只作用于 Codex 自带的 shell 工具：初始 prompt 里那条 role=developer 消息描述了文件权限、网络访问、以及「何时该向用户请求权限」。其他工具（如 MCP server 提供的）不受 Codex 沙箱约束，得自己负责安全。审批则由策略模板驱动（如 prompts/templates/permissions/approval_policy/on_request.md，同目录还有 never.md / unless_trusted.md），在 app-server 层则表现为「服务端反向发 approval 请求 + 暂停 turn」。

      对照：dsh 把三条边界都做成 fail-closed 接缝

      dsh 的做法更「拓扑化」：审批（ctx.approval）「没有审批服务时 ask 直接变拒绝」；沙箱（ctx.sandbox）「bash 与 fs 共读同一个 sandboxPolicy，不可能围栏到不同 root」；凭证（ctx.credentials）「配置只存引用、值归 provider、每操作重新 resolve」。它把「不外泄 / 只减权 / 默认关死」编进结构与类型。Codex 的边界更贴合「一个跑在你机器上的编程 agent」这个具体场景——沙箱聚焦 shell、审批面向命令执行——覆盖面窄但意图明确。要把 Codex 嵌进多用户生产系统，沙箱只管 shell 这条得自己补齐 MCP 工具侧的隔离。

      七Codex Harness vs dsh：两种「可演化性」哲学#

      — 同一道题，两个相反方向的答案

      把前面所有线索收束成一句话：它们对「让执行层可被无痛改造」这件事，押注在相反的位置。

      Codex Harness

      一切皆协议客户端

      • 可演化性来自边界：向后兼容的 app-server 协议，服务端随便进化、客户端不必跟。
      • Rust 生产单体：一个经过真实产品线（App/CLI/IDE/web）打磨的 harness。
      • 状态留在 prompt 前缀：无状态请求 + prompt caching + ZDR + encrypted_content。
      • 扩展靠外挂：MCP、skills、SDK、app-server 客户端——从外面接。
      • 边界贴场景：沙箱只管 shell，审批面向命令。
      • 成熟度：已驱动真实产品，协议承诺向后兼容。
      vs
      DeepSeek Harness

      一切皆插件

      • 可演化性来自内核：无特权内核 + 可逆 effect + 依赖图，换任意部件是配置动作。
      • TS 226 包插件树：Cordis 响应式内核，连 agent loop 都是一个插件。
      • 状态留在事件日志：append-only 会话日志作单一事实源，内存是投影。
      • 扩展靠挂接缝：把插件挂到 56 个 ctx.* 服务上——从里面长。
      • 边界成接缝：沙箱/审批/凭证三条全 fail-closed。
      • 成熟度：developer preview，明说「会破坏兼容」。

      这不是「谁更好」，是两种关于「稳定性锚点放哪」的世界观：

      对比维度Codex Harness（源码核对）dsh（已核对）
      稳定性锚点外部协议边界（app-server 向后兼容）内部组合契约（Cordis effect/coeffect）
      载体 / 语言Rust · codex-rs 单体工作区TypeScript · 226 包 pnpm monorepo
      「换部件」的成本换客户端 / 换 MCP 工具 / 改 config；核心是黑盒写一组 Definition/Provider/Consumer 接缝；核心可换
      长程状态prompt 前缀 + 服务端缓存（无状态请求）事件溯源日志 + 内存投影（本地事实源）
      上下文管理保留推理 + 上下文压缩（harness 层）日志投影 + 压缩，避免重放全量
      扩展方向从外接（协议 / MCP / SDK）从内长（挂 ctx.* 接缝）
      心智门槛低：会连协议 / 会写 MCP 工具即可上手高：改包前先啃透 Cordis 心智模型
      生产就绪度高：真实产品线在跑、协议保兼容低：preview、明说会破坏兼容
      最适合的姿势直接嵌入产品，把 agent 带进你的看板/工作流借鉴接缝设计，而非直接 fork 整棵树
      一句话记忆

      Codex 说「别动我的内核，照着我的协议接就行，我保证不改坏你」；dsh 说「没有内核可动，你把插件挂上来，卸载时我保证清理干净」。一个把信任建立在接口的稳定上，一个把信任建立在副作用的可逆上。对 FDE 而言：要快速把 agent 嵌进现成产品，Codex 的协议边界是更短的路；要造一个能被深度改造的自有 harness 底板，dsh 的接缝设计是更值得抄的作业。

      八可借鉴点与取舍#

      — 从 Codex 能直接搬走什么

      可借鉴 · 协议优先

      「用一条向后兼容的进程间协议把 agent loop 和界面解耦」是极强的产品化范式：一个长驻进程 + JSONL over stdio + Item/Turn/Thread 三原语，就能让 CLI/IDE/web/自研产品共享同一个 agent 核。自建 harness 时，这比「大家各调一套内部 API」稳得多。

      可借鉴 · 前缀即缓存

      「让新 prompt 是旧 prompt 的精确前缀」是把 prompt caching 吃满的前提。把系统指令 / 工具定义 / 静态上下文钉在最前面、只在尾部 append，是任何走 LLM API 的 agent 都能立刻抄的省钱技巧。

      取舍 · 二次增长

      默认 HTTP/SSE 路径不带 previous_response_id，换来 stateless + ZDR，代价是请求 JSON 随对话二次增长。长会话下这对带宽和序列化是实打实的负担——不需要 ZDR 就未必照搬（源码另有 WebSocket 增量路径可缓解带宽）。

      取舍 · 边界覆盖面

      沙箱只管 shell、MCP 工具自负其责。嵌进多用户生产系统时，工具侧隔离、凭证多租户、审批审计得自己补——Codex 给的是「编程 agent」的边界，不是「企业平台」的边界。
