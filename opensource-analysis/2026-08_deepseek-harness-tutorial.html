      零全局概览：这是一个什么项目？#

      WHAT IS AN AGENT HARNESS

      本章目标
      • 理解"agent harness"和"聊天机器人"的本质区别
      • 认识 monorepo 布局和核心术语
      • 记住三条贯穿全文的设计铁律

      从聊天机器人到 agent harness

      一个最简单的聊天机器人，伪代码大概 6 行：

      const history = []
while (true) {
  const userInput = readLine()
  history.push({ role: 'user', content: userInput })
  const reply = await llm.chat(history)
  history.push({ role: 'assistant', content: reply })
  print(reply)
}

      但真实产品里的 AI 编程助手远不止如此——它还需要调用工具（shell、文件、网页）、多轮循环（模型说"我要执行命令 X"，执行完结果喂回去）、会话持久化（崩溃后恢复、fork、回放）、安全边界（沙箱 + 审批）、界面（Web UI / CLI / 协议调用）、可扩展性（用户想加一个能力，不应该改核心循环代码）。

      把上面这些打包成一个可运行、可配置、可扩展的框架，就叫 agent harness（字面：给 agent 用的"挽具/支架"）。

      答案：插件化架构

      把每一个能力都做成一个"插件"，插件之间通过统一的机制互相协作、互相替换。

      这个思路叫插件化架构，底层实现框架叫 Cordis（本仓库 vendor/cordis/，是对开源 Cordis 的 vendored 拷贝）。

      一句话记住：DeepSeek Harness = Cordis 插件框架 + 一套 agent 能力插件集 + 启动/配置系统

      三条贯穿全文的设计铁律

      铁律一

      一切皆插件，没有"特权核心"

      连 agent 主循环（agent-loop）都是一个可被换掉的插件。你要扩展产品，不是去改核心，而是"在旁边再挂一个插件"。

      铁律二

      注册即副作用

      插件通过 ctx.effect() / ctx.on() 登记它做的每一件事，这些登记都会返回"撤销函数"；卸载时按相反顺序自动撤销——热更新、卸载、测试清理都是安全可预测的。

      铁律三

      模型可见 ⟺ 已落日志

      凡是会喂给大模型的内容，都必须能从会话日志里重建出来。会话日志是"唯一真相来源"，消息历史是从日志推导出来的，而不是另存一份。

      五个必须记住的术语
      术语一句话类比
      插件 plugin一段可挂载/可卸载的代码，声明它"需要什么、提供什么、监听什么"一块积木
      上下文 context一个"服务仓库"，插件从这里按名字找到别的服务公共插座面板
      服务 service一个挂在 ctx.<名字> 上、有稳定接口的对象面板上的一个插座
      事件 event插件之间广播消息的通道，有 5 种派发模式广播喇叭
      副作用 effect插件做的"可逆登记"，卸载时自动撤销登记表，走时自动划掉

      一先懂 Cordis：整个项目的地基#

      PLUGIN / CONTEXT / SERVICE / EVENT / EFFECT

      本章目标
      • 说出 Cordis 五个核心概念，以及它们在代码里长什么样
      • 看懂一个插件怎么声明"我需要什么、我提供什么、我监听什么"
      • 理解"注册即副作用"为什么让热更新/卸载变得安全

      Cordis 提供了一种"把一堆互相独立、又互相依赖的插件，组织成一棵能增删改查的树"的办法。它只解决五件事：

      概念文件解决什么问题
      上下文 Contextcontext.ts插件从哪儿找到别的服务？
      服务 Serviceservice.ts能力怎么"挂上名字"供人使用？
      插件 Pluginregistry.ts插件长什么样？怎么被加载？
      事件 Eventsevents.ts插件之间怎么通信？
      副作用 Effectfiber.ts插件卸载时怎么干净地撤销自己做过的事？

      Context —— 一个 Proxy 服务仓库

      // vendor/cordis/src/context.ts（节选）
export class Context {
  constructor() {
    this.reflect = new ReflectService(self)   // 反射层：真正存服务的地方
    this.registry = new RegistryService(self) // 插件注册表
    this.events = new EventsService(self)     // 事件总线
    this.logger = new LoggerService(self)     // 日志
    return self  // self 是一个 Proxy！
  }
}

      关键点：Context 的实例是一个 Proxy。 你写 ctx.shell 时，并不是直接读一个字段，而是被拦截、转发到"服务仓库"去查找名为 shell 的服务。这就是 Cordis 的依赖注入（DI）——插件依赖的是"名字"，不是"类"。

      插件 Plugin —— 三种写法

      // ① 函数插件（最常用）
function myPlugin(ctx, config) { /* 干活的代码 */ }

// ② 类插件
class MyPlugin { constructor(ctx, config) { /* ... */ } }

// ③ 对象插件
const myPlugin = { apply(ctx, config) { /* ... */ } }

      它们都可以带上元数据：

      export const name = 'tool-bash'                    // 显示名
export const inject = ['tools', 'shell']           // 我需要这些服务
export const Config = z.object({ ... })            // 配置的校验 schema
export function apply(ctx, config) { /* ... */ }   // 入口

      inject 声明依赖后，Cordis 会等到这些服务都就绪，才真正运行这个插件——"加载顺序"由"依赖关系"自动决定，而不是手动排 boot 顺序。

      Events —— 五种派发模式

      模式方法是否等待有返回值？典型用途
      广播ctx.emit否否通知："某事发生了"
      并发ctx.parallel是否让所有人各自处理，等全部完成
      串行ctx.serial是是依次询问，直到有人给出答案
      短路ctx.bail否是第一个非空返回值即止
      瀑布ctx.waterfall否是环绕式中间件

      瀑布（waterfall）是最重要、也最容易误解的一个——它是"层层套娃的中间件"。每个监听器决定是"自己接管"还是"交给内层"。关键规则：waterfall 监听器必须调 next() 才算委托；不调就短路。 这条规则贯穿全仓库。

      Effect —— "注册即副作用"

      每个插件运行起来，都是一个 Fiber（纤维） 实例，有生命周期状态机：PENDING → LOADING → ACTIVE → UNLOADING → DISPOSED。

      // 概念上等价于：
const dispose = ctx.effect(() => {
  // 这里做的任何"登记"
  return () => { /* 这里是"撤销"逻辑 */ }
})

      Cordis 会把这些"撤销函数"按注册的相反顺序收进一个列表。当插件被卸载（或配置更新触发重启），它就逆序执行所有撤销函数，把插件做过的事全部干净地撤掉。这带来的直接好处：热更新（HMR）安全、可预测的清理、registry 的 register() 直接返回 disposer。

      串起来：一个最小插件

      import { Context, Service } from '@deepseek-ai/cordis'

// ① 定义一个服务（提供能力）
export class Counter extends Service {
  constructor(ctx: Context) { super(ctx, 'counter') }  // 注册为 ctx.counter
  count = 0
  add(n: number) { this.count += n }
}

// ② 给 ctx 补类型
declare module '@deepseek-ai/cordis' {
  interface Context { counter: Counter }
}

// ③ 函数插件：消费服务 + 监听事件
export const name = 'counter-demo'
export const inject = ['counter']            // 依赖 ctx.counter
export function apply(ctx: Context) {
  ctx.counter.add(1)                          // 用服务
  ctx.on('some/event', (data) => {            // 注册监听（副作用，自动撤销）
    console.log('got', data, 'count=', ctx.counter.count)
  })
}
      小结
      概念一句话记忆
      Context服务仓库，ctx.<名字> 取服务，是 Proxy
      Plugin函数/类/对象 + name/inject/Config/apply
      Service抽象基类，super(ctx, 'name') 即注册为 ctx.name
      Eventsemit/parallel/serial/bail/waterfall 五种，waterfall 是中间件
      Effect每次登记都是可撤销的副作用，卸载时逆序撤销

      二启动与配置：从一条命令到一棵插件树#

      PROFILE / BUNDLE / PATCH / CORDIS.YML

      本章目标
      • 敲下 dsh web 后，到真正跑起来，中间发生了什么？
      • profile / bundle / patch / cordis.yml 分别是什么、怎么叠加？
      • dsh 的 home 目录、设置、凭证放在哪？

      dsh 命令（apps/cli/）本身几乎不含业务逻辑，它只做一件事：解析命令行参数 → 选一个 profile → 按 profile 定义的"层"顺序，把若干 bundle 叠成一棵插件树 → 交给 Cordis 跑起来。

      三个核心概念

      profile

      一份命名好的"装配方案"，存在 harness home 里。记录：要叠加哪些 bundle、安装了哪些树外插件、用户自己的 cordis.patch.yml。

      bundle

      Cordis 配置行的分发格式。插进去之后仍可被更高层 patch 掉。三个内置 bundle：dsh-base、dsh-web-app、dsh-headless。

      patch

      对某个配置行的整行替换或新增。按 id 定位某一行，把那一行的 config 整个替换掉（或插入新行）。

      "任何一行都可以被你自己的 patch 替换掉"——这就是"一切皆可配置、一切皆可替换"在配置层的体现。

      cordis.yml：装配图的语言

      • !!js 表达式：让某个字段在加载时求值一段 JS（例如读环境变量、条件判断）。
      • disabled：把某一行关掉（不加载，但仍留在装配里可被覆盖）。
      • overlay：本次运行专用的、最上层的临时覆盖层（--patch 就是干这个的）。

      启动链路全貌

      dsh --profile web
   │  args.ts 只解析自己的 flag，其余透传
   ▼
选 profile「web」
   │  按顺序取 bundle：dsh-base → dsh-web-app
   ▼
叠加 patch 层（profile patch → home patch → --patch）
   │  得到一份完整的 cordis 装配（哪些插件 + 各自 config）
   ▼
交给 Cordis loader 逐个 ctx.plugin(...) 挂载
   │  每个插件声明 inject，Cordis 按依赖自动排序等待
   ▼
一棵活着的插件树开始运行（web 版此时启动 HTTP/WS 服务器）

      home 目录、设置、凭证

      一切都收敛在 $DSH_HOME（默认 ~/.dsh）：

      内容位置 / 机制
      profiles$DSH_HOME/profiles/<name>/
      用户 patch$DSH_HOME/cordis.patch.yml
      设置settings.yaml（ctx.settings 读取）
      凭证四层优先级：env 变量 > .credentials.yaml > 项目 .env > home .env

      凭证用的是"引用"而非"明文"：代码里声明"我需要一个叫 DEEPSEEK_API_KEY 的凭证"，由 provider 在运行时去上面四层里找——插件代码不碰明文密钥。

      三Agent 主循环：这台机器的"心脏"#

      TURN / STEP / INBOX / REACTLOOPAGENT

      本章目标
      • 说出主干 6 个核心包各自管什么
      • 讲清一次"用户发消息 → 模型回复 → 可能调工具 → 再回复"的完整生命周期
      • 理解为什么"会话日志是唯一真相来源"、消息历史是从日志推导出来的

      主干：6 个包一条龙

      包ctx 键职责
      sessionctx.sessions唯一真相来源：追加式事件日志 + 内存存储
      system-promptctx.systemPrompt提示词段落 + 工具 schema 装配
      toolsctx.tools工具注册表 + 受保护执行管线
      agentctx.agentsAgent 接口 + 活体注册表
      agent-loopctx.agentLoop实现上述接口的默认驱动器
      scope（库，无键）每-agent 的作用域注册原语

      关键点：agent 只定义"接口"，agent-loop 是"默认实现"，而且它是可被换掉的——别的插件都依赖 agent（接口），从不直接依赖 agent-loop（实现）。

      Inbox：两个队列的"收件箱"

      agent 的所有待处理输入都进 Inbox，它有两个有序队列：

      • next-turn：等"新开一个轮次"才消费
      • next-step：等"下一个 step 边界"就消费（更紧急，用于 steering/注入上下文）

      Inbox 是"模型循环"和"外部世界"之间的缓冲，外部只管往里塞消息、循环只从里面取。

      step = 一次模型调用 + 它触发的工具；turn = 零到多个 step。主循环用 phase 状态机 + Inbox 双队列驱动，每一步都在 session 上落日志。

      会话日志：唯一真相来源

      上面每一步都在 session 上 append 一条 SessionEvent。日志是 append-only（只追加） 的：

      type SessionEvent = {
  type: 'turn/start' | 'user/message' | 'assistant/message' | 'tool/result' | ...
  seq: number      // 会话内单调递增的序号
  time: number     // 毫秒时间戳
  data: ...
}

      核心思想：模型看得到的，一定记进了日志。 模型历史 deriveMessages() 是从日志推导出来的；fork、resume、transcript、telemetry、persistence 全都派生自同一条日志流。

      两个贯穿全仓库的"类型技巧"

      Map → 派生联合：几乎所有"可扩展的联合类型"都这么写——插件想加一种新事件，不用改拥有包，只需 declare module 扩展 SessionEventMap。

      interface SessionEventMap {
  'turn/start': { turn: number }
  'user/message': UserMessage
}
type SessionEvent = SessionEventMap[keyof SessionEventMap]

      Branded ID：跨包传递的 ID 是编译期打标的字符串——运行时就是普通字符串，但类型上不可互换，防止"把会话 ID 当调用 ID 用"这类低级错误。

      四工具与"能力缝隙"：可插拔的手和脚#

      CAPABILITY SEAM / DEFINITION / PROVIDER / CONSUMER

      本章目标
      • 讲清"能力缝隙"的三角色，并举出 shell 的完整例子
      • 说出一条 tool 是怎么声明的、它的 schema 从哪来
      • 讲清工具执行管线每一步在做什么

      DeepSeek Harness 里每一个"能力"都遵循同一种拆分，官方叫 capability seam（能力缝隙），由三个角色组成：

      三角色规则：Definition = 插座（声明接口）、Provider = 电器（实现功能）、Consumer = 遥控器（模型用的 tool）。三者可以分属不同包，通过 ctx.<key> 解耦。

      完整例子：shell

      Service Definition（dsh-shell）：只声明接口，不实现。

      export abstract class ShellExecutor extends Service {
  constructor(ctx: Context) { super(ctx, 'shell') }
  abstract resolve(request: ShellExecRequest): ShellExecSpec
  abstract run(spec: ShellExecSpec): Promise<ShellRunResult>
  abstract start(spec: ShellExecSpec): ShellProcess
}

      Service Provider（dsh-bash-local）：实现具体逻辑。Provider 是单槽的——一个 context 里只能挂一个 ctx.shell。

      Consumer（dsh-tool-bash）：给模型用的工具，只写 ctx.shell.run(...)，完全不知道 ctx.shell 到底是本机 bash 还是远程沙箱 bash——这就是解耦的威力。

      一条 tool 是怎么声明的

      defineTool({
  name: 'bash',                        // 模型调用的名字
  description: '...',                  // 给模型看的说明（写进 prompt）
  parameters: { /* 输入参数的 schema */ },
  output: { schema: {...}, render },    // 返回值的 schema + 如何渲染成文本
  execute(args, exec) { /* 干活 */ },
  presentCall, presentResult,           // UI 卡片（可选）
})
      重要区分

      模型可见的 tool schema 是手写的类型化 DSL，运行时编译成 JSON Schema。TypeScript 类型是从 schema反向推断的（InferArgs）。Typert 是另一条线（第六章讲）：它在构建期从 TS 源类型生成 Zod schema，服务于前后端 RPC 的类型安全，不生成模型可见的 tool schema。

      工具执行管线：8 个阶段

      ①
      物化参数
      JSON 快照 + 深冻结，分配 token
      ②
      pre-execute
      waterfall：allow / deny / ask
      ③
      单调守卫
      只能"拒绝"或"不改动"
      ④
      tools/execute
      waterfall：环绕分发
      ⑤
      工具体 execute()
      真正干活
      ⑥
      post-execute
      waterfall：accept / block
      ⑦
      finalizeContent
      同步"最后一公里"改写
      ⑧
      tools/result
      emit 通知：冻结的无损结果

      三个 waterfall（②④⑥）都是"套娃中间件"：调 next() 就是放行/委托，不调就是短路改写。这样"权限、沙箱、超时、埋点、结果改写"都能挂在工具外面实现，而不用改任何工具本身。

      五会话日志与持久化：让记忆可恢复#

      APPEND-ONLY / JSONL / SQLITE / PROJECTION

      本章目标
      • 讲清 append-only 日志为什么是"唯一真相来源"
      • 说清 JSONL 落盘、SQLite 查询、projection 三者各自解决什么问题
      • 理解崩溃后会话如何恢复、版本如何管理

      harness 把"会话数据"分成了三个正交的平面：

      层包解决什么特点
      持久化session-persistence + session-persistence-jsonl把日志落盘、崩溃恢复append-only，写时发布
      查询session-query + session-query-sqlite按条件检索历史会话只读、SQLite 全文搜索
      投影session-projection把日志折算成"仪表盘"视图内存中、按需计算

      关键：三者都从同一条日志派生，谁也不是"第二份真相"。

      JSONL 后端

      {"type":"turn/start","seq":1,"time":1700000000000,"data":{"turn":1}}
{"type":"user/message","seq":2,"time":1700000001000,"data":{...}}
{"type":"assistant/message","seq":3,"time":1700000002000,"data":{...}}

      为什么选 JSONL：天然适配 append-only——追加一行就是一次写；崩溃可恢复——即使写到一半崩了，前面的行都完好；后端会做崩溃修复并给"崩溃孤儿 turn"补一个 turn/end；可流式读取——恢复时逐行重放即可。

      版本：SESSION_FORMAT_VERSION = 0

      会话日志的磁盘格式版本号，写进每个新会话头，加载时强制校验。目前项目未发布（pre-release），所以固定为 0。只有"结构性变化"才 +1（header 结构、事件信封、核心事件语义变了才 bump）；单纯"新增一种事件类型"不 bump——因为有 ignorable: true 标记兜底。

      全仓库最高级守恒律

      Model-visible ⟺ logged（模型看得到的 ⟺ 记进日志的）。

      • 任何要进模型请求的内容，都必须能从日志重建
      • 新增一种"模型可见输入"，就必须新增一种 session 事件
      • 运行时还有一个 invariant（不变量）在断言这一点

      这条律是理解"为什么日志设计得这么重"的钥匙：日志不是副产品，它就是产品状态本身。

      六Web UI 与前后端通信：这台机器的"眼睛"#

      HOST / CLIENT / TYPERT / RPC

      本章目标
      • 说清 host（后端）和 client（浏览器）为什么分开、各管什么
      • 讲清浏览器靠什么协议和后端通信
      • 理解 Typert 是什么、解决什么问题（以及它不解决什么）
      整个产品其实是两棵 Cordis 插件树在互相配合——host 干活（Node 能力），client 渲染（React）+ 发 RPC。浏览器是不可信输入，必须隔一道信任边界。

      Typert：给 RPC 自动生成"双语合同"

      构建时，typert-generator 分析 host 的 TypeScript 程序，凡是标了 @Remote / @RemoteScope 的方法，就为它生成三样东西：宿主描述符（方法名、参数、返回类型）、Zod 严格 codec（运行时校验用）、客户端声明合并（让前端 ctx.remote.<namespace>.<method> 有类型提示）。

      于是前端调用 ctx.remote.goals.create(...) 就像调本地函数一样有类型提示；请求到 host 后，gateway 用同一份 Zod schema 校验入参出参。

      端到端：点一下"发送"发生了什么

      1. 用户在浏览器点"发送"
      2. client 的 Session.prompt() 调 ctx.remote，变成 POST /api/session/prompt
      3. host 端 connection 桥接 + 信任检查（loopback/白名单）
      4. 交给 apiproxy，消息进该 session 的 inbox
      5. agent 循环推进：turn/start → pre-step → llm/stream → assistant/chunk* → turn/end
      6. 这些事件经 /api/events.mux WebSocket 推回浏览器
      7. client 的 ConnectionController 收帧 → SessionManager 累积 → UI 按日志渲染

      注意第 5 → 7 步的呼应：UI 不是"拿到最终答案才刷新"，而是持续订阅事件流、按事件增量渲染——界面 = 日志的投影。

      七沙箱与安全：这台机器的"盔甲"#

      SANDBOX / POLICY / APPROVAL / ESCALATION

      本章目标
      • 说清沙箱到底约束什么（以及不约束什么）
      • 讲清三种权限模式，以及"升级权限"的审批流程
      • 理解"策略"和"执行"是怎么解耦的

      沙箱只约束"文件写入"这一类副作用（以及相关的子进程执行边界），而不是笼统地"隔离一切"。

      三种权限模式

      模式能做什么典型场景
      read-only只读，不能写最保守，默认只读
      workspace-write只能写会话工作目录日常编码任务
      danger-full-access完全访问明确需要改系统文件时

      关键是模式是每次调用现场解析的（sandbox-policy 的 resolve()），而不是全局写死——同一台机器、同一个会话，不同时刻可能用不同模式。

      权限升级：deny 不是终点

      1. 模型执行命令，被沙箱拒绝——返回 [sandbox: file access denied under <mode> mode]
      2. 这不是 bug，而是政策拒绝。模型可以在同一次 turn 内，用更宽的模式 + 一句 justification（理由）重试
      3. 重试会触发 ctx.approval（审批）：弹出一个一次性审批给用户
      4. 若会话声明"审批弹窗已禁用"，则拒绝是终局

      设计意图：默认最小权限 + 明确理由 + 用户一次性同意，在"安全"和"能干活"之间取得平衡。

      一句话

      策略层决定"允不允许、允许多宽"，执行层（confine()）负责"怎么真正拦住"。两层解耦，各自可换。后端可插拔：Linux 用 bwrap/Landlock，macOS 用 Seatbelt，Windows 用 ACL。

      八进阶主题：用同一套积木搭出更复杂的机器#

      SCOPE / SUBAGENT / WORKFLOW / GOAL / RALPH

      本章目标
      • 理解"每-agent 作用域（scope）"如何让不同 agent 拥有不同能力
      • 大致说清 subagent / workflow / goal / Ralph 各自是什么、区别在哪
      • 知道还有哪些能力缝隙、以及 Python SDK / native 扩展的位置

      每-agent 作用域

      前面所有注册（工具、提示词段落、变量、监听器）默认是全局的——所有 agent 共享。harness 用 scope（作用域） 解决：每个 agent 有自己专属的 agent.ctx（作用域上下文），通过它做的注册只对该 agent 可见、且随它销毁而撤销。

      • shadowing（遮蔽）：作用域里的同名工具/段落会"盖住"全局那个。
      • restriction（限制）：tools.restrict 能把"全局工具集"对某作用域做交集过滤。

      Subagent：把任务派给"子代理"

      也是一个缝隙：注册表 ctx.subagents 收多个 Provider（in-process 派生的、ACP、Codex、Claude Code 等），Consumer 是 tool-subagent 系列。区分两个维度：spawn（全新子代理）vs fork（继承本对话上下文的子代理）。

      Workflow：把任务编排成"并行脚本"

      让模型能写一段 JavaScript 编排脚本，把工作扇出（fan-out）到多个子代理、分阶段、并发执行、收集结构化结果——适合"审计一堆文件""多角度研究"这类可并行的大任务。

      Goal 与 Ralph：两种"长任务"管理

      goal

      同一会话内的持久完成目标，带 active/paused/blocked/complete 阶段和"目标轮次上限"。会话日志仍是真相来源。

      Ralph

      一个前台、每轮都是全新子代理的循环，朝一个不可变目标反复迭代。每轮子代理看不到父对话或前一轮对话，跨轮状态靠共享工作区 + 结构化交接报告传递。

      其它能力缝隙一览

      能力ctx.一句话
      terminalctx.terminals持久 PTY 终端（跨轮保持的 shell 会话）
      code-runtime—代码执行（worker-thread Provider + Code Mode Consumer）
      fsctx.fs文件读写 + 写前检查事件
      webctx.web网页搜索/抓取
      skill—技能（可复用指令集）注册表 + 目录/加载工具
      lsp—语言服务器能力
      compaction—上下文压缩（长对话瘦身）
      telemetry—OpenTelemetry 遥测
