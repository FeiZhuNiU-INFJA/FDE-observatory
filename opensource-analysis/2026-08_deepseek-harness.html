      一页要点
      • Cordis 是真内核：README——「everything is a plugin, powered by Cordis」，其设计论文 A Programming Paradigm for Spatiotemporal Composability（时空可组合性的编程范式）把动态组合拆成 temporal / spatial 两维（见第二节原文定义）。architecture.md：「没有特权 core 可打补丁；注册是 effect，插件卸载时会 unwind」。
      • 五个观念：插件即 Service · Context 是服务仓库 · 用 inject 声明依赖（载入顺序由依赖表达，非手写时序）· 类型化事件通信 · 注册是可逆 effect。
      • Profile / Bundle 分层组合：dsh-base 是每个 profile 的第一层；web / headless 是模板；一条 --patch 就能按 id 替换任意配置行——「你打印出的任何一行都能被你自己的 patch 替换」。
      • 会话是 append-only 事件日志：append() 写入，deriveMessages() 投影出模型历史；新的模型可见输入 ⇒ 必须新增一个 session event。
      • 工具流水线是「可扩展 waterfall + 单调守卫」：pre-execute → guards → execute → post-execute → finalizeContent → result；守卫只能减权、不能授权，所以监听器顺序无法把一次拒绝翻回允许。
      • Code Mode 是一个可选能力，不是脊柱：ctx.codeRuntime 把「一段模型写的程序」当传输层跑，mode:'code' 时只发 run_code + 生成的 SDK，原生工具只能作为 run_code 的子派发被调用。
      • 凭证只存引用：配置里放的是环境变量名，provider 才持有值；消费者每次操作重新 resolve，所以轮换后的凭证下一个请求就生效、无需重启。

      一它到底是什么：没有特权内核的插件树#

      — everything is a plugin，连 agent loop 也是

      README 的自我定义只有两句：「DeepSeek Harness（dsh）是一个开源 agent harness」，「它用一种『一切皆插件』的架构，由 Cordis 驱动」。关键不在「插件化」这个词本身——很多框架都自称插件化——而在 architecture.md 的这句：

      architecture.md · 原文摘引

      「Every part of the product is a plugin, including the model adapter, the tool registry, the session log, and the agent loop itself, so every part is replaceable from configuration.」

      「There is no privileged core to patch: you extend dsh by mounting a plugin beside the others, and registrations are effects that unwind when their plugin unloads.」

      这句话是整个项目的地基。它意味着：没有一个「主程序」调度所有模块——一个运行中的 dsh 是一棵在启动时由有序分层组合出来的插件树。Profile 与 Bundle 是这棵树的组合语言：profile 是一份命名的组合（列出它堆叠哪些 bundle），bundle 是 Cordis 配置行 + 其挂载代码的分发格式。dsh-base 永远是每个 profile 的第一层（模型适配器、工具、持久化、沙箱与审批策略、设置、凭证、遥测），dsh-web-app 加浏览器应用，dsh-headless 加一个无服务器的一次性 runner。分层按顺序叠加，最后一条 --patch 覆盖层可以按 id 替换任意一行的整段配置：

      # 看你这台机器实际启动的插件树，任何一行都能被你的 patch 替换
dsh --profile web --dump-config

      二Cordis 内核：可逆 effect 与依赖排序#

      — 用服务依赖代替启动时序，用 disposer 代替手写清理

      要读懂 dsh，先读懂 Cordis。primer 把它压缩成五个观念：①插件就是一个实现 Service 的对象（一个带可选 inject / apply(ctx) 的函数，或一个 Service 子类）；②Context 是服务仓库——服务占一个稳定的 ctx.<key>（如 ctx.tools / ctx.llm / ctx.sessions），别的插件按 key 找服务，而不是 import 具体实现；③用 inject 声明服务依赖——命名了所需服务的插件会一直等到那些服务存在，于是载入顺序由依赖需求表达，而非手写启动时序；④类型化事件通信——服务通过 TS 声明合并声明事件名，再按 emit / waterfall / parallel / serial 派发；⑤注册是可逆 effect——prompt 段、工具 schema、适配器、provider、监听器都经 ctx.effect() 或 ctx.on() 安装，重载与拆卸会可预测地 unwind。

      这五点不是随手总结——它们的形式化地基写在 Cordis 那篇设计论文里。README 只说「powered by Cordis」，但论文（A Programming Paradigm for Spatiotemporal Composability，2026-08-13 preprint 草稿）把「一切皆插件」为什么能成立讲清楚了：它把动态组合拆成两个正交维度，并给出精确定义——

      Cordis 论文 · 原文定义（摘引）

      「We identify two orthogonal dimensions of the problem: temporal composability, the ability to completely revert a component's side effects upon removal, and spatial composability, the ability to declare and reactively manage inter-component dependencies.」

      论文把这两维分别落到两个运行时机制上：revertible effects——「every context transformation carries an inverse that the runtime tracks」（每次上下文变换都携带一个由运行时追踪的逆操作）；reactive coeffects——「each change of the context notifies a component against its coeffect specification」（上下文每次变化都按组件声明的 coeffect 规格通知它）。两者被统一进单一 context type，这就构成了那个编程范式；Cordis 自称「a meta-framework of spatiotemporal composability」。

      把论文的词表贴回这一节：时间可组合性（temporal）= 上面第⑤点的「注册是可逆 effect」——组件被移除时其副作用能被完全撤销，也就是下面这张图；空间可组合性（spatial）= 第③点的 inject 依赖声明——用响应式的依赖管理代替手写启动时序。换句话说，dsh 的「无特权内核 + 可卸载插件」不是工程巧劲，而是这套 effect / coeffect 演算的直接落地。（论文为 preprint、仍在修订，此处仅摘其定义句作权威锚点。）

      第五点是这套架构最反直觉、也最值钱的地方。把它画出来就是一条「挂载 → 累积 disposer → 卸载时 LIFO 反向 unwind」的可逆生命周期：

      「注册即 effect」把清理从纪律变成结构：disposer 由 ctx.effect() 累积、卸载时按 LIFO 反向执行。这正是论文说的 revertible effects——「每次上下文变换都携带一个由运行时追踪的逆操作」，也就是 temporal composability 的运行时形态：重载 / HMR / 拆卸都是同一条 unwind 路径，没有手写的 teardown 会漏。

      事件的派发模式是公开契约的一部分：primer 的四模式表——emit（观察、不等待、无返回）、waterfall（有返回、around-中间件）、parallel（并行、等待、无返回）、serial（顺序、等待、有返回）。其中 waterfall 最关键：监听器收到 (...args, next)，调 next() 把（可能被包裹过的）结果委托给下一个服务，不调 next() 就短路。「单决策」事件里短路即设计——策略监听器可以在它拥有决定权时直接返回，只做标注的监听器则必须委托。这正是工具流水线（第六节）和 agent 请求拦截的底层机制。

      落地视角：角色 / 系统消息注入

      要在发给模型的消息里注入 system.message、做角色缓存，在这套架构里本质就是一个 waterfall 监听器：在 agent/pre-step（决定模型看到什么）上挂一个 effect，改写被 claim 的消息再 next()。好处是——它是可逆的：切换角色 = 卸载旧 effect、挂新 effect，无需在主循环里塞 if (role) … 的分支泥团。这比改主流程更符合「不动特权内核」的原则。

      三为什么是这套架构：为「自进化 AI」造的底板#

      — 论文自己的切入点不是「又一个 agent 框架」，而是自进化的底层基础设施

      前两节讲的都是「怎么做的」。但有个更根本的问题值得先回答：为什么要把一个 agent harness 架在「可逆 effect + 反应式依赖」这么重的内核上？直接写死一个主循环不是更简单？答案不在源码里，在那篇论文的立意里——而这一层，恰好是一支第三方解读讲得最清楚的。

      来源 · 第三方视频解读（非源码事实，转述论文立意）

      本节的「立意」层面主要综合自 B 站/YouTube 频道「最佳拍档」对该论文的解读视频（Cordis——DeepSeek Harness 的乐高底板，2026-08-15，13:28），它指出这篇论文是 DeepSeek 与北京大学合作、篇幅约 88 页。以下凡标「论文/解读称」的判断属于论文立意的转述，与本页其余「源码级事实」区分开——立意可以有解读空间，事实（commit 47f9438 的行为）不会。

      论文切入的角度就是「自进化 AI」。解读转述的论文设想是这样一条链：未来的 agent 会根据任务自己生成一个工具、把工具装进运行时、发现有问题再把它替换掉。一旦你认真对待这个设想，一个平时无关痛痒的工程缺陷就会被放大成致命问题——

      论文的问题起点：插件「插上去拔不下来」

      解读引论文的一个具体数据：截至 2026-06-09，VSCode Marketplace 排名前 100 的扩展里有 87 个含可执行代码，一旦激活就无法在运行时单独卸载——禁用/删除后必须重启整个扩展宿主才生效。这不是 VSCode 一家的毛病，是几乎所有主流插件架构的通病。放在普通软件里，重启一下就忍了；放在 agent 语境里则是量级不同的问题：一个 agent 塞满了工具集、执行环境、权限、沙箱、会话状态、记忆系统，如果「模型自己改一行、就得重启整个进程」，那之前积累的上下文缓存会全部崩掉——更糟的是「一不留神 agent 可能把自己给改没了」。

      论文把这个困境拆成正交的两半，正好对应第二节那两个原文定义，而这张图把它们和「自进化」这个动机接上——中间是模型驱动的自我改造循环，两侧是让这个循环安全的两道保障：

      Cordis 不生产「进化」本身——它是让上面这条模型自我改造循环能安全跑起来的底层基础设施：进化的决定在模型，进化的安全由内核兜底。

      这也直接回答了「这跟 LangChain / LlamaIndex / AutoGPT 有什么区别」——解读把这层说得很利落：大多数 agent 框架解决的是「怎么把 agent 搭起来」（给你工具、抽象、现成组件，快速拼出一个能用的 agent）；Cordis 想解决的是「agent 如何自己进化」的底层基础设施问题。二者不在一层：前者是「搭 agent 的乐高积木」，后者是「能热插拔的乐高底板」。要落到自我进化，模型得能自己写工具、自己装、自己升级，而这个过程不能动不动重启、不能一升级就丢上下文、不能依赖一乱就整体崩——这些恰是现有插件系统与 agent 框架「从根上没解决」的问题。

      它不是实验室玩具：四年 · 4000+ 插件的生产验证

      这套设计并非新造的概念，而是从聊天机器人框架 Koishi 里长了四年的东西——已在真实生产环境跑过 4000+ 社区插件。关键细节：这四千多个插件由互不相识的不同作者独立开发，彼此唯一的协调机制就是反应式余效应——这说明这套动态组合规则能在开放生态里成立，而非只在单一团队的受控代码里。解读也如实转述了论文自陈的局限：目前只有 Koishi 一个生态、TypeScript 一门语言的验证，且缺乏与替代架构的直接对比。源起也有迹可循：一作施一凡（北大 + DeepSeek，Koishi 作者）早在 2023 年就为 Koishi 写过一篇《可逆的插件系统》设计文，几乎是本论文的雏形；README 说的「powered by Cordis」，本质就是 Koishi 的 Cordis 升级版。

      把这层接回你读这篇拆解的收益：本页后面所有「源码级事实」——可逆 effect 的 disposer 栈（第二节）、事件溯源日志（下一节）、能力接缝的 provider swap（第五节）——都是这块「自进化底板」的具体承重构件。你不必相信「自进化」这个宏大叙事也能用它：哪怕只是要做多用户化、凭证热更、崩溃回收，你要的其实是同一种东西——能安全地在运行时改造自己的系统。这正是第九节那张复用表的立足点。

      四事件溯源会话：模型可见即已落日志#

      — append-only 日志是单一事实源，模型历史是投影

      dsh-session 把一次会话建模成一条 append-only 的类型化 SessionEvent 日志——它是 agent 整段交互历史的唯一事实源。LLM 消息历史是从日志 投影出来的，从不单独存储；重放就是从同一批事件重新推导。这条设计钉在 architecture.md 的一句不变量上：

      Model-visible means logged（原文摘引）

      「Anything that reaches a model request must be reconstructable from the log, and a runtime invariant asserts it. This is why a new model-visible input requires a new session event: extend SessionEventMap and render from the log.」

      一个 turn 的日志长这样（turn/* / step/* / user/message / assistant/* / tool/* 都是持久事件，其余是活的扩展点）。注意 assistant/chunk——原始流 chunk 也进日志，为的是保住 token 级重放与 UI 保真：

      SessionEventMap 是合并可扩展的：compaction 加 compaction/*、hook 桥加 log-only 的 hook/invoked / hook/result——加持久状态 = 扩 SessionEventMap 再从日志渲染。append() 是唯一写入口；「怎么持久化」是 ctx.sessionPersistence 接缝的兄弟问题（jsonl / sqlite 两个后端并存）。
      落地视角：崩溃回收 / 状态一致性

      这套「事件日志是事实源、内存态是投影」的模型，正好解决长程任务的崩溃回收：崩了之后不需要「恢复内存状态」，只需重放日志重新投影。任何会话只要把「模型看到的每一条」都落成可重建事件，fork / resume / 审计就全是免费的副产品——而不是各写一套。代价见第十节：写入路径的纪律（一切模型可见输入都必须走 append）。

      五能力接缝：一次 provider swap 换整条产品线#

      — Definition / Provider / Consumer 三角色，缺一不成接缝

      「一切皆插件」落到可维护性上，靠的是 capability seam（能力接缝）这个规矩。一个 seam 是一项可换能力，由三个角色构成：Service Definition（声明接口）、Service Provider（实现它）、Consumer（用它，通常是一个模型可见的工具）。一个包可以兼任多角色，但单一角色不成接缝——加一项能力意味着把三者都设计出来。以文件系统接缝 ctx.fs 为例：

      「换一个 provider 就换整条产品线」：architecture.md——文件系统与子进程 provider 共享同一执行世界，把它们指向远程沙箱，Bash / PTY / LSP 一起搬过去，没有 provider 分叉。capability-seams.md 的图谱枚举了全部 56 个 ctx.* 服务及其角色分类。

      接缝的威力在组合：LLM 适配器接缝 ctx.llm 下并存 llm-deepseek / llm-pi-ai / llm-replay（其中 replay 是测试用的确定性回放）；子代理接缝 ctx.subagents 下并存 6 个 provider（进程内 spawn / fork、跨进程 ACP / Codex / Claude Code、以及 dsh-sdk）——它是少数几个允许多实现按名并存的接缝，其余多数（如 bash 执行器）只允许一个。而「加一个模型 provider = 在 ctx.llm 上注册它的适配器」「加一个模型可见能力 = 在 ctx.tools 上注册、其 schema 自动进 prompt 组装」这类「新行为该往哪挂」的对照，被 architecture.md 的一张表钉死了。

      六Turn 循环与守卫式工具流水线#

      — waterfall 可扩展，但守卫只能减权

      一个 step 是「一次模型请求 + 它调用的工具」；一个 turn 是零或多个 step。turn flow 的骨架是：turn/start → 认领输入 → 组装 prompt 段 + 工具 schema → agent/pre-step（可改写或拒绝）→ step/start → agent/request → llm/stream → assistant/chunk* → assistant/message → tool/call* → tools/pre-execute → tools/execute → tools/post-execute → tool/result* → step/end。其中 agent/pre-step、agent/request、llm/stream 和三个 tools/* 都是 waterfall（监听器必须调 next() 委托）。

      工具执行是全项目最见功力的一段。ctx.tools.execute() 把一次调用串过一条五段流水线，每段职责不同、且有一条不可翻转的单调性：

      参数在进策略前一次性物化为无损 JSON 并冻结——因为「历史 / 审计 / UI / 执行必须一致」，所以 pre-execute 不许改写参数，只能 allow / deny / ask（且只有审批返回 allowed-once 才真的放行）。守卫 ToolGuard 的返回类型故意没有 allow 分支：undefined 保持不变，返回理由即拒绝——这是把「安全只能收紧」编进了类型。

      结果类型也贯彻同一克制：成功结果里的规范 value 是执行局部的、故意不进持久事件（日志只存 content / error / meta）——「重放能复现呈现，但无法重建中间的规范值」。未知工具和抛异常的工具都变成结构化错误（UNKNOWN_TOOL），调用失败但不结束 turn。

      七Code Mode：把「模型写的程序」当传输层#

      — 一个可选能力，不是 agent loop 的脊柱

      代码执行接缝 ctx.codeRuntime 的定位很清醒：「Code execution is one optional capability, not part of the agent-loop spine.」它把「一段模型写的程序」跑在宿主提供的异步绑定之上，报告它打印了什么、返回了什么。程序作为一个 async 函数体运行——顶层 await 和 return 可用，完成值成为 CodeRunResult.value；错误是结果上的一个字段，而不是 run() 的 reject（和 ShellExecutor.run 的「失败也 resolve」契约一致）。

      它跟工具流水线的接法很精巧：呈现模式 ToolPresentationMode 有 native / code / both 三种；mode:'code' 时只给模型发一个 run_code 工具 + 一份生成的 SDK，原生工具名只能作为 run_code 程序内部的子派发被调用——一个「模型直呼」（无 parent）的原生工具名会在进策略前就被判 UNKNOWN_TOOL。而且这是按 agent scope 设定的（ctx.tools.presentAs(mode)），所以一个 preset 可以让 Code Mode agent 与原生 agent 在同一进程里并存。

      这对「工具即代码」范式意味着什么

      这和我们之前拆过的「工具即代码」（Prime Agent 的 RLM）是同一股潮流，但 dsh 的处理更「接缝化」：它没有把代码执行升格为唯一入口，而是让它作为一个可换 provider（worker-thread 后端）挂在 ctx.codeRuntime 上，工具注册表作为 Consumer 消费它。好处是——你可以在同一部署里，给需要精细审批的 agent 用 native 模式、给批量自动化的 agent 用 code 模式，切换只是改一个 scope 的呈现声明，不动任何工具实现。

      八安全边界：沙箱 · 审批 · 凭证只存引用#

      — 三条边界都做成接缝，fail closed 是默认

      多用户 / 生产化最关心的三条边界，dsh 都做成了接缝，且默认「关死」：

      审批 · ctx.approval

      一次性权限决定，经 approval/request waterfall 派发；回答者是监听器（如 ACP 桥为它自己的 agent 应答）。关键：「absence fails closed to unavailable」——没有审批服务时，ask 直接变拒绝，而不是默默放行。

      沙箱 · ctx.sandbox / sandboxPolicy

      消费者把「即将 spawn 的确切 argv」交给同世界后端包裹后再执行。sandboxPolicy 是部署默认模式 + workspace root 的唯一家——bash 与 fs 两族都读它，所以两者不可能围栏到不同的 root。permissionPresets 把 workspace-write / danger-full-access 打包成一键切换。

      凭证 · ctx.credentials

      配置里只放引用（环境变量名），provider 才持有值；消费者每次操作重新 resolve、从不跨操作缓存——LLM 适配器每次模型请求都 resolve 一次，于是轮换后的凭证下一个请求就生效、无需重启。web 网关只暴露「无值视图」和只写存储。

      遥测 · ctx.sessionTelemetry

      接缝捕获、脱敏、再把会话记录交给唯一后端；其输出离开进程，进程内没有别的东西消费它。这条「脱敏在接缝、不在调用点」的设计，是把「敏感数据不外泄」编进拓扑而非纪律。

      落地视角：多用户凭证 / 热更

      要支持「每用户不同凭证 + 静态 bearer / OAuth 并存」，在这套架构里本质就是给 ctx.credentials 接缝写一个新的 Provider——把「用户身份 → 凭证值」的解析收进 provider，消费者（LLM 适配器 / MCP toolset）照旧「每次操作 resolve」。这样多用户绑定表不必侵入主流程，凭证热更（轮换 / 过期重取）也天然成立。「配置只存引用、值归 provider」这条，正是把硬编码校验从网关层挖出来后应该落到的形态。

      九可复用范式：四个能直接借鉴的接缝#

      — 从 dsh 的做法反推「同类需求该往哪个接缝挂」

      dsh 的做法它解决的通用问题可复用点
      可逆 effect + waterfall 拦截（cordis-primer） 角色 / 系统消息注入 把「注入 system.message」做成挂在 agent/pre-step 上的可逆监听器——切角色 = 卸旧挂新，取代在主流程里塞 if
      凭证接缝「配置存引用、值归 provider、每操作 resolve」 多用户凭证与热更（静态 bearer / OAuth 并存） 给 ctx.credentials 写新 Provider，把「用户身份 → 凭证」解析收进去；轮换 / 过期重取天然成立，主流程不感知
      事件溯源会话日志 + deriveMessages 投影 长程任务崩溃回收与状态一致性 「日志是事实源、内存是投影」——崩溃后重放日志即恢复；fork / resume / 审计是免费副产品，无需各写一套
      能力接缝三角色 + provider swap（architecture） 执行端解耦、本地 / 远程沙箱切换 把 fs / subprocess / shell 做成共享执行世界的接缝：一次把 provider 指向远程，Bash/PTY/LSP 一起搬，无 provider 分叉

      十取舍与陷阱#

      — 一句话：架构纯度极高，代价是心智门槛与 preview 状态

      亮点

      架构纯度是真·彻底。「没有特权内核」不是宣传——连 agent loop 都是 ctx.agentLoop 上唯一的具体插件，扩展包只依赖 dsh-agent 的事件与服务、不依赖它。这让「换任意部件」成为配置动作。

      亮点

      不变量写进类型与运行时。「模型可见即已落日志」有运行时断言；守卫「只能减权」编进返回类型；凭证「只存引用」是接缝级铁律——安全与一致性靠结构而非纪律。

      存疑

      心智门槛陡。文档第一句就是「改 packages/ 前先懂 Cordis」，并建议「用一个 agent 去探索代码库」。226 个包 + 声明合并的类型化事件 + 依赖排序的隐式载入顺序——二次开发前得先啃透 Cordis 的心智模型。

      存疑

      developer preview，明说会破坏兼容。README 大写强调「THERE WILL BE COMPATIBILITY-BREAKING CHANGES」。现在把它当生产依赖有风险；更稳的姿势是借鉴它的接缝设计，而非直接 fork 整棵树。

      用它/借它时的陷阱
      • 「一切模型可见输入都必须走 append」是硬纪律：想给模型多喂一句上下文，不能直接塞进内存历史，得新增一个 SessionEventMap 成员再从日志渲染——省了 fork/replay 的代价是写入路径不能走捷径。
      • 接缝三角色缺一不可：只写一个 Provider 不算加了能力；不设计 Definition 和 Consumer，别的插件就无法按 key 找到并替换它。加能力的成本被前移到「设计三者」。
      • 依赖排序是隐式的：载入顺序由 inject 表达，不是你写的顺序。漏声明一个依赖，插件可能在服务就绪前激活——排障时要往「谁 inject 了谁」看，而不是往「谁先 import」看。
