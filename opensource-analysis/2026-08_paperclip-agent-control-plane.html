      Paperclip · 给一群 AI 员工建一家「公司」的control plane

      org-chart / 任务 / 预算 / 心跳执行全在控制平面；agent 在哪跑都行，唯一契约是「可被调用」——把编排与执行彻底解耦

      核心结论：Paperclip 不是又一个 agent 框架，而是一层控制平面（control plane）——它管 org-chart、任务、预算、审批、审计和「心跳执行」，但坚决不定义 agent 怎么跑。README 一句话点题：「若 OpenClaw 是员工，Paperclip 就是公司」。真正值得抄的是它把「让一群自主 agent 长时间干活而不失控」拆成了三条硬工程约束：①原子签出——用一条 UPDATE … WHERE … RETURNING 的 compare-and-swap 保证一个任务只被一个 agent 拿走，赢家拿到行、输家拿到 null 直接判冲突；②预算硬停——「起跑前拦截 + 花超后回杀」的两相回路，一旦花销 ≥ 阈值就 pause 作用域并 kill 进程 + 置 cancelled；③活性契约——任何未完成的任务都必须有「活跃 / 等待 / 恢复」三条路之一，否则算 stalled，宁可 surface 也不静默。对我们（OpenClaw → 火山 MA 迁移、arkagent 多用户化）最有价值的，正是这套「单一 assignee 所有权 + 预算硬停 + 崩溃回收」的生产级骨架——它把我们卡点 A/B/D 的「多用户不打架、花销可控、崩了能救」全部代码化了。
      一页要点
      • 控制平面 ≠ 执行平面：PRODUCT.md 原则 5——「Paperclip orchestrates. Agents run wherever they run and phone home.」不绑定任何 runtime。
      • agent 的唯一契约是「可被调用」：每个 agent = 一个 adapter type + config，「the minimum contract is just 'be callable.'」仓库自带 11 个 adapter。
      • 原子签出杜绝双claim：issues.ts 的 checkout 用条件 UPDATE 做 CAS，guard 是 status + assigneeAgentId + checkoutRunId + executionRunId——注意：靠应用层 CAS，不是 DB 唯一约束。
      • 预算硬停是两相：起跑前 getInvocationBlock 拦截；花超后 evaluateCostEvent 在 hardStop && observed≥amount 时 pause + cancel。
      • 心跳是执行引擎：tickTimers 按间隔唤醒 agent；reapOrphanedRuns 回收「进程死了但状态还 running」的孤儿 run。
      • 活性契约（liveness contract）是灵魂：execution-semantics.md §8——「never leave work in a state where nobody is responsible for the next move」，是可见性契约、不是自动完成契约。
      • 数据库：Postgres（本地内嵌 embedded-postgres）+ Drizzle ORM，生产可指向自建 PG。扩展分两类——Platform Module（可信、进程内，adapter 属此）与 Plugin（实例级、经 SDK/host 协议隔离）。

      一它到底是什么：控制平面，不是执行平面#

      — orchestrate here, run anywhere, phone home

      README 的自我定义很克制：「Paperclip is the app people use to manage AI agents for work.」底下紧跟一句极准的类比——「If OpenClaw is an employee, Paperclip is the company.」它提供的是一家「AI 公司」的运营基建：org charts、tasks、heartbeat runs、budgets、approvals、audit logs，而不规定 agent 用什么语言、框架、runtime。

      这条边界在 PRODUCT.md 的产品原则里被反复钉死：原则 1「provides utility infrastructure for heartbeats. It does not mandate an agent runtime」；原则 5「Control plane, not execution plane. Paperclip orchestrates. Agents run wherever they run and phone home」。SPEC 的 Anti-Requirements 甚至直白写「Not an Agent runtime」。这台「公司」的形态可以画成一张控制平面／执行平面的分工图：

      控制平面派发 adapter.execute() 并注入运行期 JWT（落到子进程 PAPERCLIP_API_KEY）；agent 干完活「phone home」回报成本与状态，控制平面据此扣预算、推进生命周期。
      载体
      TypeScript + 内嵌 Postgres
      单个 Node 进程即可跑起来，embedded-postgres + drizzle-orm 自动建库、零配置；生产可指向自建 PG。
      形态
      运营控制平面
      价值 = 组织（org-chart/目标）× 执行治理（签出/预算/心跳/活性）。agent 能力上限仍取决于底层执行端，Paperclip 只保证「不失控」。

      二原子签出：一个任务只被一个 agent 拿走#

      — compare-and-swap，赢家拿行、输家拿 null

      多 agent 并发抢同一个任务是控制平面的头号竞态。Paperclip 的解法不是分布式锁，而是一条条件 UPDATE——issues.ts 的 checkout（核心 CAS 在 8011–8031）。它把「任务是否可被我拿」压进 WHERE，靠数据库的原子性裁决——谁的 WHERE 先匹配谁赢，输家 rows[0] 为 null，直接抛冲突：

      // issues.ts:8011 —— 一条 UPDATE 做完签出（compare-and-swap）
const updated = await db.update(issues)
  .set({
    assigneeAgentId: agentId, checkoutRunId,
    executionRunId: checkoutRunId, status: "in_progress",
    startedAt: now, updatedAt: now,
  })
  .where(and(
    eq(issues.id, id),
    inArray(issues.status, expectedStatuses),          // ① 状态 guard
    or(isNull(issues.assigneeAgentId), sameRunAssigneeCondition), // ② assignee guard
    executionLockCondition,                             // ③ 执行锁 guard
  ))
  .returning()
  .then((rows) => rows[0] ?? null);   // 输家拿到 null → throw conflict

      三重 guard 缺一不可：①状态必须落在调用方声明的 expectedStatuses；②assignee 要么当前无主，要么已经是我自己（同 run 幂等续跑）；③执行锁 executionRunId 为空或等于本次 checkoutRunId。整条竞态画出来就是一条「单赢家」漏斗：

      单一 assignee 靠应用层 CAS 保证——不是 DB 唯一约束。assignee_agent_id / checkout_run_id 上只有普通索引，无 partial-unique；接管孤儿/陈旧签出时再叠 SELECT … FOR UPDATE 事务兜底。
      对 arkagent 多用户化（卡点 A/B）

      这正是你把 arkagent 从「单用户骨架」改成多用户生产时需要的所有权模型：用一条带 guard 的条件写把「谁拥有这条任务/会话」原子化，而不是先 SELECT 再 UPDATE（TOCTOU 竞态）。你的 userOpenId/vaultId 绑定表可以直接借这套「无主或本人才可写」的 WHERE 幂等模式。

      三预算硬停：起跑前拦截 + 花超后回杀#

      — two-phase enforcement，一相都不能少

      自主 agent 最危险的是「烧钱不自知」。Paperclip 的预算硬停是两相回路，缺任一相都会漏——因为「起跑前额度够、跑到一半才超」是常态。作用域只有三个：company / agent / project，各带 soft（告警）/ hard（硬停）双阈值。

      相 A（budgets.ts:718）读作用域的 paused(budget) 态并做实时复核；相 B（budgets.ts:649）由每笔 cost 触发，硬停时 回调 heartbeat 的 cancelWorkForScope——先 pause 作用域（防重启）再 cancelRunInternal：既 kill 进程也置 cancelled。
      设计取舍：为什么必须两相

      只做相 A（起跑前查）会漏「跑到一半才超」；只做相 B（花超回杀）会漏「已经超了还准新 run 起跑」。两相之间靠作用域的 paused(budget) 状态位串起来——相 B 把 agent/project/company 置 paused，相 A 下次起跑前正好读到它并拦截。这是把「预算」做成一个带记忆的状态机，而不是两处独立的 if。

      四心跳执行环：生命周期与崩溃回收#

      — 唤醒 → 认领 → 执行 → 回收孤儿

      心跳（heartbeat）是这台控制平面的执行引擎。tickTimers 每 tick 扫一遍活跃公司里的可唤醒 agent，比较距上次 lastHeartbeatAt 是否已过 intervalSec，到点就 enqueueWakeup(source:"timer")。run 的生命周期是一个 8 态机（HEARTBEAT_RUN_STATUSES）：

      claimQueuedRun 用 WHERE status="queued" 的条件 UPDATE 原子占位（12472–12483）；reapOrphanedRuns 靠「无内存句柄 + 本地 pid/pgid 已死 + 超 staleThreshold（周期 5min）」判定孤儿，置 failed(process_lost) 并至多补一次重试。

      关键工程细节：崩溃回收不靠 DB 租约到期、也不靠 run 上的 lastHeartbeatAt 列，而是「行状态还是 running，但进程内已无句柄、且（本地 adapter）OS pid/pgid 已死、且超过陈旧阈值」三条同时成立才判孤儿。仍活着的 detached 进程会被标记而不误杀。终态写入统一走 setRunStatus，另有 CAS 版本 setRunStatusFromLive（只在当前状态属于允许集合时转，抢输了报 updated:false）防状态回退。

      五活性契约：不静默、不假完成#

      — 每个未完成任务都得有下一步

      前三节都是「机制」，这一节是把它们串起来的「灵魂法则」。execution-semantics.md §8 · Non-Terminal Issue Liveness Contract 给整套执行语义定了一条不可违反的可见性契约：

      Liveness Contract（原文摘引）

      「For agent-owned, non-terminal issues, Paperclip should never leave work in a state where nobody is responsible for the next move and nothing will wake or surface it.」

      「This is a visibility contract, not an auto-completion contract. … It must not silently mark work done from prose comments or guess that a dependency is complete.」

      「An issue is stalled when it is non-terminal but has no live execution path, no explicit waiting path, and no recovery path.」

      换成工程语言：任何「未完成」的任务，必须至少命中八条合法「下一步路径」之一——活跃 run、排队中的唤醒/续跑、类型化的执行策略参与者、待交互/待审批、一次性 monitor、人类 owner、一等公民的 blocker 链，或一条显式的 recovery action。否则它就是 stalled，系统宁可 surface（blocked 态 / 可见通知 / 显式恢复动作）也不会静默地放着或从散文里猜「大概做完了」。第四节的 reapOrphanedRuns 就是这条契约的一个执行器——它保证「进程死了」不会变成「任务永远卡在 running 没人管」。

      六Adapter 契约：唯一要求是「可被调用」#

      — execute(ctx) → result，控制平面注入运行期上下文

      「agent 在哪跑都行」落到代码，就是一个极薄的接口：一个 adapter 只需实现 execute(ctx: AdapterExecutionContext): Promise<AdapterExecutionResult>（+ testEnvironment）。控制平面把一次运行需要的一切打进 AdapterExecutionContext：

      // adapter-utils/src/types.ts:170 —— 控制平面 → adapter 的执行上下文
export interface AdapterExecutionContext {
  runId: string;              // 本次 run 身份（也进 JWT 的 run_id claim）
  agent: AdapterAgent;          // id / companyId / adapterType / adapterConfig
  runtime: AdapterRuntime;      // session 参数 / taskKey
  config: Record<string, unknown>; // env / cwd 等经 config 下发
  context: Record<string, unknown>;
  onLog / onMeta / onEvent / onRuntimeProgress / onSpawn; // 回流管道
  authToken?: string;         // 运行期 JWT，落子进程 PAPERCLIP_API_KEY
}

      注意契约的边界感：环境变量、工作目录不是接口的顶层字段，而是塞进 config（config.env / config.cwd）下发；真正把它们拼成子进程环境的是各 adapter 自己的 execute——例如 process adapter 在第 37 行 if (authToken) env.PAPERCLIP_API_KEY = authToken，且注释明确「PAPERCLIP_API_KEY 永远不接受来自 config——harness 铸造的 run token 是唯一来源」。这条「JWT 只能来自控制平面、agent 用它反向鉴权 API」的单向信任，是多租户安全的关键。

      Adapter vs Plugin（别混）

      仓库自带 11 个 adapter。PLUGIN_SPEC.md 把扩展分两类：Platform Module——「a trusted in-process extension loaded directly by Paperclip core」（adapter 属此，通过 registerAgentAdapter() 注册）；Plugin——「an installable instance-wide extension package loaded through the Paperclip plugin runtime」，经稳定 SDK + host 协议与 core 隔离、能力受门控。简言之：adapter 决定「怎么调 agent」（可信、进程内），plugin 是「实例级加装的能力」（隔离、可选）。

      七对我们的映射（MA 迁移 / arkagent）#

      — 能直接抄的四个生产级范式

      它的做法对应我们的问题可复用点
      原子签出 CAS（issues.ts:8011） arkagent 多用户化：userOpenId/vaultId 绑定与任务归属（卡点 A/B） 「无主或本人才可写」的条件 UPDATE 幂等模式，取代 SELECT-then-UPDATE 的 TOCTOU 竞态
      预算硬停两相（budgets.ts） Creao 大规模视频生成的花销失控风险 「起跑前拦截 + 花超回杀 + 作用域 paused 状态位」的带记忆预算机；company/agent/project 三级作用域直接对标团队/岗位/项目
      心跳生命周期 + reapOrphanedRuns MA 侧长程任务的崩溃回收与状态一致性（卡点 D） 「进程死 ≠ 任务卡死」：无内存句柄 + OS 进程已死 + 陈旧阈值三判定 + 有界重试，是可直接移植的孤儿回收判据
      Adapter 「be callable」契约 + JWT 单向注入 OpenClaw → 火山 MA：如何把执行端解耦、又保证多租户鉴权安全 execute(ctx) 极薄接口 + 「run token 只能由 harness 铸造、不接受 config 注入」的单向信任边界

      八取舍与陷阱#

      — 一句话：执行治理很硬核，代价是控制平面自身很重

      亮点

      执行治理是真·生产级。原子签出、两相预算、崩溃回收、活性契约——都不是 demo 级 if，而是围绕「一群 agent 长跑不失控」写死的不变量，且文档（execution-semantics.md）把契约讲清楚了。

      亮点

      边界感极强。坚决不做 agent runtime，只做控制平面；adapter 契约薄到「be callable」，JWT 单向注入——解耦与安全都靠架构而非纪律。

      存疑

      单一 assignee 靠应用层 CAS，不是 DB 约束。正确性依赖「所有写路径都走 checkout 系列函数」这条纪律；一旦有旁路直接 UPDATE，DB 层没有 partial-unique 兜底。规模化时值得再加约束。

      存疑

      控制平面很重、心跳服务巨大。heartbeat.ts 单文件近两万行，run 生命周期、回收、预算回调、租约全挤在里面——功能强但认知与维护成本高，二次开发前得先啃透状态机。

      用它时的陷阱
      • 别指望它提升 agent 能力：它管「不失控」，不管「更聪明」。执行质量上限仍是你接的 adapter 端模型。
      • 预算作用域没有 run 级：只有 company/agent/project 三级 + calendar_month/lifetime 两种窗口。想按单次 run 卡额度得自己在 adapter 侧加。
      • 内嵌 Postgres 只适合本地/单机：生产必须指向自建 PG，否则单进程内嵌库既是数据库也是单点。
