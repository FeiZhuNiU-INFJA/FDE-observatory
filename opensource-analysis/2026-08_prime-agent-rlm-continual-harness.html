      核心结论：Prime Agent 不是「又一个 Claude Code 复刻」，也不是一个新模型——它是 Prime Intellect 把开源 pi（@earendil-works）打包成的「把 harness 本身当成可编程、可自改状态」的编码智能体。它的赌注写在两处代码里：（1）面向模型只暴露一个工具 ipython——读写文件、跑命令、调技能、派子 agent 全是在一个常驻 Python REPL 里写代码；（2）harness 的 prompt / memory / skill / subagent 被做成能 CRUD、能 /refine 在线改写、能回滚的持久状态。这两件事都不是 PPT，而是 11.6 万行 TS + 一个 ZeroMQ 上的 Jupyter kernel 撑起来的。对我们（LIFT）最有价值的不是它的自我改进叙事，而是它天然产出的结构化全轨迹（append-only JSONL 树 + 子 agent 用量归因），那是现成的 trace 采集面。
      一页要点
      • 它是 pi 的产品化发行版：package.json name = @earendil-works/pi-coding-agent，productName = prime-agent，bin = pi。看 Prime Agent 等于看 pi 的工程内核。
      • RLM = 唯一工具 ipython：allToolNames = new Set(["ipython"])。能力不是「加工具」，是「在 REPL 里 import 包 / await rlm(...)」。
      • Python 只是 shim，权威状态全在 TS host：kernel 里 await rlm(...) / goal.* 走 Jupyter comm 目标 host.request 回到 TypeScript，凭证、provider 调用、落盘、调度都不进 Python。
      • 子 agent 是异步派发：await rlm(...) 到「admission」立刻返回一个 handle，永不返回子 agent 的答案；结果只经 agent_message 或文件回传。默认递归深度 = 1。
      • 持续 Harness 是 CRUD 状态账本：harness_state.json，四类条目（prompt/memory/skill/subagent）+ refinement 事件日志；base system prompt 硬性不可改。
      • /refine 是「plan / apply」两相：规划（后台 LLM 提议 JSON 编辑）与应用（原子写盘）分离，中间重读盘防并发覆盖；每条编辑存 before/after 快照可回滚；有 local / global 双 scope。
      • 不是安全沙箱：kernel 就是 spawn 出来的 python -m ipykernel_launcher，继承宿主环境与 OS 权限——README 自己写明「run untrusted code in an external sandbox」。

      读代码得到、博客没直说的三件事
      1. Prime Agent = pi 发行版。Prime Intellect 的增量在「产品化 + 与自家 RL/评测基建的集成叙事」，而工程内核（RLM 运行时、kernel、持续 harness）是 @earendil-works/pi 这套包。要学机制就直接读这个 monorepo。
      2. 规模是生产级，不是 demo。packages/coding-agent/src 约 11.6 万行 TS / 268 文件，外加 38 篇 docs、240+ 测试目录。
      3. Python 是配角。真正跑 agent loop、调 provider、落盘的是 TypeScript；Python（prime-agent-runtime）只是模型在 REPL 里操作的「手」，官方原话："The Python side does not call providers or implement an agent loop."

      二RLM：面向模型只有一个工具 ipython#

      — 把「更长上下文 / 更多工具 / 多 agent」塌缩成「在持久 REPL 里写程序」

      传统 harness 的隐含假设是「一个能力 = 一个 tool schema」：read_file、write_file、bash、web_search… 模型每一步发一个 tool_call JSON。Prime Agent 把这套推翻——它给模型的内置工具只有一个：

      // packages/coding-agent/src/core/tools/index.ts:46
export type ToolName = "ipython";
export const allToolNames: Set<ToolName> = new Set(["ipython"]);

      模型每一轮就是往一个常驻 IPython kernel 里写 Python。文件操作、跑命令（%%bash）、调技能、派子 agent，全都从这个 REPL 出发。下面这张图是它相对旧 harness 的范式转移：

      旧 harness · fixed schema
      N 个预定义工具
      工具集在设计期写死。加能力 = 加 schema；编排复杂度堆在 LLM 的 token 流里。
      →
      RLM · programmatic
      1 个 ipython + 持久命名空间
      能力靠代码展开：变量跨轮存活、import 技能包、await rlm() 派子 agent。编排复杂度从 token 流转移到 Python 运行时。

      2.1 prompt-as-a-variable：上下文即 Python 状态

      Python 状态跨 tool 调用、跨 compaction 存活。这意味着「工作上下文」可以存成对象而不占 LLM 窗口：

      from pathlib import Path
config_files = list(Path(".").rglob("*.toml"))
large_files = [p for p in config_files if p.stat().st_size > 10_000]
# 下一轮 large_files 仍在命名空间里 —— 不需要重新塞进 prompt

      2.2 subagent 是原生 rlm() 调用，且异步

      子 agent 不是「工具」，是内核里预载的可调用对象 rlm。关键语义：调用到「admission（受理）」就立刻返回 handle，永远不等、也不返回子 agent 的答案。

      handle = await rlm("Review the auth flow for security issues", name="auth-reviewer")
print(handle.rlm_child_id, handle.name, handle.session_dir, handle.model)
# 结果只经 agent_message 或文件回传，不是返回值：
#   子： await agent_message.send(msg, receiver_role="parent")
#   父： await agent_message.send("补充：也看下中间件", receiver_role="child", receiver_name=handle.name)

      为什么「不返回答案」是刻意设计？因为父 agent 要保持自己的上下文干净——它只拿一个 handle，子 agent 拿到隔离的上下文去干活，答案异步回来。这就是博客说的「context 保持 focused」的工程落点。派发实现见 agent-session.ts:9955 runRlmChild()，其序列：

      步骤做什么代码位置
      1. 深度闸RLM_DEPTH < RLM_MAX_DEPTH，超限直接抛（默认 max=1）agent-session.ts:9617
      2. 解析模型用 provider/model 精确选型或继承父模型；选不到就失败，绝不静默回退，含 auth 预检agent-session.ts:9577
      3. 建子目录sub-${randomUUID().slice(0,8)} 挂在父 artifact 目录下agent-session.ts:8884
      4. 受理并返回 handle登记进父作用域注册表，返回 RLMSpawnHandle（不含答案/用量）rlm-runtime.ts:152
      5. 用量归因子 agent 的 token/成本异步折回发起它的父 assistant 轮次，写 child_usage_attributed 条目agent-session.ts:9774

      三进程拓扑：client / daemon / worker / kernel 四层#

      — 奔着「跑几天不崩、断终端不停」去的隔离设计

      这套东西的工程成色不在 prompt，而在进程边界。渲染、协调、执行、模型侧 Python、落盘被拆成互相隔离的进程：

      Client 断开不影响 worker；worker 崩溃后 supervisor 从 JSONL + kernel 快照恢复。worker/kernel 是「生命周期与故障隔离」，不是安全隔离——它们与 client 同 OS 权限运行。
      底层机制：为什么 kernel 要单独一个进程

      AgentSession（TS）经 KernelManager 通过 ZeroMQ 上的 Jupyter 协议（v5.3）驱动一个独立的 ipykernel 进程：shell / iopub / control 三通道，帧用 HMAC-SHA256 签名（kernel/index.ts:372 sign()）。好处：kernel 跑挂/内存膨胀不拖垮 worker；持久会话可把命名空间快照进 kernel-state.dill 供复活。代价：多一层 IPC 复杂度——下一节的死锁规避就是这层复杂度的产物。

      四host_request 桥：Python 是手，TS 是脑#

      — 「模型可编程的东西」与「必须由宿主守护的状态」分层，且巧妙避开死锁

      这是全项目最见功力的一段，也是用户最该关注的「凭证校验 / 数据流转」落点。凭证、provider 执行、落盘、路由、调度全在 TypeScript host；Python 侧只能通过一个 comm 目标 host.request 发起「有类型的宿主请求」。

      # prime-agent-runtime/src/rlm/__init__.py:24
HOST_COMM_TARGET = "host.request"

# :84  Python 侧只发请求，状态转移由 TS host 校验并拥有
async def host_request(request_type, payload=None):
    comm = Comm(target_name=HOST_COMM_TARGET, primary=False)
    # … 打开 comm、await 一个 future，等 TS host 回复 …

# :150  rlm.run 就是一次 host_request：
payload = await host_request("rlm.run", {"prompt": prompt, "kwargs": kwargs})

      TS 侧在 kernel/index.ts:1254 handleHostRequest() 按 type 分发到各 typed handler（rlm.run / goal.* / agent_message.* / refine.* …）。关键细节：回复走的是 control 通道，不是 shell 通道——这是为了防死锁。

      为什么这段值得抄：IPython 串行处理 shell 消息。一个正在跑的 cell 里 await rlm("…")，如果受理回复也从 shell 通道回，那这条 execute_request 要等回复才能结束、而 kernel 要等它结束才处理回复——互锁。Prime Agent 的解法：把 comm 回复注册在 control 通道，用 loop.call_soon_threadsafe() 调度未来完成。凭证边界也在这里划定：provider 凭证由 TS host 解析，只有「有界的模型目录」作为元数据穿进 Python，完整 auth store 不进 kernel。

      5.1 /refine：plan / apply 两相分离

      自我改进的机制核心是 /refine，它像「上下文压缩」的孪生——只不过它不是总结对话，而是从轨迹里提炼出对 harness 的最小 CRUD 编辑。代码把它切成两相，中间有个关键的「重读盘」动作：

      Phase 1 · Plan
      后台 LLM 提议
      读轨迹 + 当前 harness + 历史，让模型输出纯 JSON 编辑数组，不改任何状态。
      planRefinement() refinement.ts:863
      中间 · Re-read
      重读 harness 盘
      LLM 调用耗时数秒，期间 kernel/别的会话可能已写盘——应用前重读并按 baseline 比对，冲突的编辑拒绝。
      "entry changed during refinement planning"
      Phase 2 · Apply
      CRUD + 快照
      逐条 create/update/delete，每条记 before/after 快照；原子 temp+rename 写盘。
      applyRefinementProposal() refinement.ts:707
      可选 · Rollback
      按快照回滚
      逆序回放 appliedEdits，用存下的 before/after 反向生成编辑，撤回坏 refinement。
      rollbackProposal() refinement.ts:804

      几个从代码里读到、值得记下的护栏：

      漂移防护（都在 refinement.ts 里硬编码）
      • base prompt 不可编辑：validateEdit() 显式拒绝 id === "base_system_prompt"（refinement.ts:671）。
      • skill 编辑强校验：必须带 reference.type==="python" + import + 调用式 + arguments，否则整条编辑判失败。
      • local / global 双 scope：默认写会话本地 session-artifacts/<id>/harness/；global 才写 ~/.prime/agent/harness/。局部 refine 时 global 条目只读。
      • 坏文件降级为空：loadHarnessState() 遇到损坏 JSON 返回空态而非抛错（它每次建 system prompt 都跑）。
      • auto-refine 有评审闸：turn 间隔 / compact 触发时先过一个 reviewAutoRefine() LLM 门，拒绝一次性噪声再决定要不要 refine。

      六会话 JSONL：一棵 append-only 树（对 LIFT 最重要的一节）#

      — 全轨迹结构化落盘，天然是 trace 采集面

      会话存成 ~/.prime/agent/sessions/<id>.jsonl，每行一个带 type 的 JSON，靠 id/parentId 构成一棵树——分支/fork/clone 只是移动叶指针，不新建文件。写入是纯 appendFileSync（session-manager.ts:1472）。条目类型很全：

      type含义进 LLM 上下文？
      messageuser / assistant / toolResult / bashExecution是
      compaction压缩摘要 + tokensBefore + firstKeptEntryId摘要进，被压的原文不进
      branch_summary切分支时对被弃路径的 LLM 摘要是
      child_usage_attributedRLM 子 agent 用量折回父轮次（daemon 记账）否（纯记账）
      model_change / thinking_level_change中途切模型 / 调推理档否
      agent_status / git_stateagents 视图状态 / 仓库快照否
      这对我们意味着什么

      LIFT 的硬约束是「归因数据仅限 Trace / Artifact / Scores / Metrics」。Prime Agent 的 JSONL 恰好是一份结构化、可增量、含因果链（parentId 树）+ 含用量归因的 Trace 源：每个 assistant 轮次、每个 tool 结果、每次 compaction、每个子 agent 的用量都可定位。更妙的是 refinements.jsonl + child_usage_attributed 让「同一任务不同处置（子 agent A vs B / refine 前 vs 后）」变成天然的反事实对照样本——正对我们「双变量实验 = 反事实干预」的归因方法论。行动建议：把这套 JSONL schema 评估为 LIFT 的一个 trace 采集适配层。

      七长任务 & 自主模式：它真正的用途是无人值守 runtime#

      — goal · heartbeat · schedule · autonomous 四个调度面

      博客把「长程自主评测的默认 runtime」列为三大用途之一，代码印证了这一点——它有一整套让会话「跑很久、断终端不停、到点自催」的机制：

      带 token 预算的持久目标
      harness 持续催 agent 直到 goal.complete()；记录用量/耗时/续跑次数。创建目标是显式动作，不由每个任务推断。

      Autonomous

      八信任模型：它明说自己不是安全沙箱#

      — 抄之前必须先看清这条硬边界

      这不是我推断的，是 README 第 66 行的原话，也是代码的事实：kernel 就是一个继承宿主环境变量与 OS 权限 spawn 出来的 python -m ipykernel_launcher（kernel/index.ts）。

      README 原文 + 代码事实

      "Prime Agent executes model-generated Python and project commands with your user permissions. Its worker and kernel processes improve lifecycle isolation and recovery; they are not a security sandbox. … Run untrusted code or instructions in an external sandbox or restricted environment."

      叠加上「agent 能自由写 Python」+「能自改 harness」+「能无人值守跑几天」，攻击面很大。安装的 Python 包、skills、extensions 都被当作可信代码。企业接入必须外套沙箱——这点和它「长程自主 runtime」的定位其实是一对张力。

      九判断：亮点、存疑、与我们的关系#

      — 一句话：机制扎实，叙事需打折，trace 面可复用

      亮点

      抽象塌缩很漂亮。把「长上下文/多工具/多 agent」三条扩展线统一成「在持久 REPL 里写程序」，比「MCP + 一堆工具」更彻底。host_request 分层（Python 是手、TS 是脑）+ control 通道防死锁，是成熟工程判断，不是 demo。

      存疑

      「self-improving」名不副实的风险。目前是提示层在线自适应（改 prompt/skill/memory），不是权重更新；天花板仍被底层 frontier model 锁死。且博客未给任何 benchmark，自改 harness 的长程漂移只有工程护栏、无数据背书。

      对 LIFT

      把它当 trace 数据源，不是当竞品。append-only JSONL 树 + child_usage_attributed + refinements.jsonl = 现成的结构化轨迹 + 天然反事实对照。评估做一个 JSONL→LIFT 的采集适配层。

      可直接抄的模式

      control 通道防死锁、plan/apply 中间重读盘、原子 temp+rename 写状态、tick 先 claim 再投递——这四个是任何长程 agent runtime 都会踩的坑，这里有现成的正解。
