      一手源码：deepseek-ai/dsh-superagent-prototype · 固定版本 6337fc823ce2 · MIT · 核查日期 2026-11-02。

      核心判断：Super Agent 将散落在人的脑中、聊天记录和多个 Agent 会话里的协同工作，搬进一个有状态的控制面。公开原型最扎实的部分是任务授权、事件归属、执行隔离和可靠交付；广泛的常驻自主能力仍需要更多实现与验证。
      一页要点
      • 它是基于 DeepSeek Harness 的研究原型。README 明确说，公开代码与内部系统、设计文章并不相同。
      • Router 做接单、路由和结果转交；Worker 在独立会话与目录里执行。重点是多个独立任务跨时间推进。
      • 新任务走 Gate → Eval → Ticket；已有任务走 Subscription → Input → 原 Worker。后者避免重复判断与派单。
      • Mandate 固化“凭什么、在什么范围内做事”。Subscription 只输送上下文，关联信息不会自动变成权限。
      • SQLite 事务、持久化 Effects、Outbox、稳定消息 ID 支持恢复；任意外部执行动作仍有重复窗口。
      • 默认是 observe，主动规则只有文案修正和局部视觉修正。Router 有 bash，Worker 运行在操作者 OS 权限下。
      • 可与“薄 Agent + Durable Workflow”组合：前者管跨任务协同，后者管单项任务内部的 DAG、阶段门槛和局部重试。

      一这次发布，究竟发布了什么#

      — RELEASE IDENTITY & EVIDENCE

      2026 年 10 月 31 日的发布包含 Super-agent 设计讨论和一个公开原型仓库。这里最容易混淆三层对象：文章中的系统愿景、团队日常使用的内部实现、适配后发布的 dsh-superagent-prototype。仓库开头就提醒：它不是正式 DeepSeek 产品，不是生产就绪软件，部分文章设计尚未实现。后文所有实现判断都固定到同一提交，避免把新闻里的能力直接套到代码上。[S1]

      公开原型的定位很具体：为一个 GitHub 仓库工作的主动编码 Agent，通过 GitHub，以及可选的飞书获取消息；有人提出允许执行的请求后，创建工作项，在独立会话和目录里处理，再回到原对话交付，例如一个 PR。管理面板显示哪些事项需要人。它复用 Harness 的会话、工具、插件和模型适配能力，新增跨会话的协同控制层；Harness 的基础机制可先读此前的源码拆解。

      二思想：优化人的注意力，而后才是自主性#

      — CONTINUOUS ENTITY / MINIMUM HUMAN ATTENTION

      docs/000-philosophy.md 的目标非常清楚：“Take as little human attention as possible, and give as much value as possible.” 团队级 Agent 能帮整支团队，也能浪费整支团队的时间。因此它默认安静：只有被明确授权，或团队写下的规则允许时才行动；只有确认接单、交付可用结果、需要人做决定、或说明具体无法推进的原因时才说话。一个新事件并不天然值得开票，观察到模糊问题也不天然值得追问。

      按公开报道对设计文章的转述，四项特征是连续性、效率、主动性、持久性。它们指向一种长时间存在的工作实体：消息来了能接、任务并行能推进、等待外部结果时能让出控制、进程恢复后仍知道哪些事情没做完。实现上采用 Router / Workers、事件驱动、异步通道、计算/状态/环境分离，以及外部 Watchdog 等机制；最后两项在公开原型中只部分落地。[S2–S4]

      这套思想大量借鉴成熟系统设计：控制面与执行面分离，快慢路径，发布订阅，缓存局部性，后台执行和外部监督。它的价值在于把这些机制组织成 Agent 的工作契约。Router 不需要背着全部代码上下文，Worker 不需要反复询问“这条消息到底属于谁”，人也不必负责每次接续。代价是控制面必须明确建模授权、归属、终止和恢复，不能靠一句“请自主工作”代替。

      三实现：同步内核，异步边缘#

      — CLICK A NODE TO FOLLOW THE CODE

      运行时组合 Engine、Store、Effects、SourceRegistry、MasterAssessor、DshExecutor、Sessions 和 Outbox。Engine 的命令同步进入事务，做状态变更并登记效果；网络调用、模型判断、Worker 启动和消息发送在提交后异步执行。外部 Source 保留自己的身份语义和游标，领域内核只处理规范化后的对象。这种接缝让核心不依赖飞书或 GitHub 的具体 SDK。

      数据模型比“Router + Worker”这四个词更有解释力。尤其要把事件、对话、任务、授权和一次执行分开；否则重复消息、任务重开、跨渠道通知和停止指令很快会纠缠在一起。下面的对象定义来自 docs/001-domain.md 和核心实现。

      对象回答的问题由谁维护 / 关键约束
      Trigger发生了哪件不可变的外部事件？Source 生成稳定 ID，Engine 去重；正文视为不可信外部数据。
      Thread这些事件属于哪段对话？Engine 保存待评估批次、历史与订阅；同一线程一次只运行一个 Eval。
      Correlation哪些线程共享同一事件？补充上下文；不会因为相互关联就自动路由。
      Subscription哪些任务应该收到这段对话的后续？多对多；输送上下文，不授予新权限；自有线程与只供上下文的线程有区别。
      Mandate凭谁的请求 / 哪条规则，在什么范围内做事？接单时固化策略版本、来源身份、explicit / inferred 强度、规则和范围；Worker 不能自行扩大。
      Ticket这项已授权工作目前是什么状态？独立于执行会话；拥有输入、通道和多次 Assignment，open ↔ ended。
      Assignment这次执行的启动、运行和结束如何记录？pending → running → ended；任务重开可以新增一次 Assignment，保留原 Ticket。
      Input / Report消息送到了、读到了、处理到了哪一步？投递与读取分别持久化；Report 用结构化 progress / waiting / ready / blocked 等状态表达。

      一个细节很重要：完成任务不会自动撤销 Mandate。人的 stop 会撤回授权，重开时不通过现行策略校验也会撤销；普通完成则保留延续工作的基础。所以“任务已结束”“执行会话不活跃”“授权仍有效”可以同时成立。这正是长期协作系统与一次性工具调用的差别。

      四两条路径：接单慢路径，后续快路径#

      — ADMISSION IS NOT CONTEXT DELIVERY

      外部事件进入 intake.ts 时，先做时间规范化、ID 去重和 Source 范围检查，然后持久化事件与处置记录。系统更新线程关联，并汇总订阅该事件的任务；即使一个 Ticket 经由多个 Thread 与它关联，一次事件也只生成一次任务输入。这一步解决“同一评论从通知、PR 订阅和关联线程重复进来”的常见问题。

      慢路径处理“是否产生一项新工作”。没有既有任务承接时，事件进入线程的待评估批次。确定性 Gate 根据来源身份、是否指向 Agent、接入规则等决定候选强度；没有合格候选便直接忽略，不调用模型。合格候选才产生 Eval，交给 Router 或准入判断。批次选取最强的请求作为授权基础，同强度时取较新的一条；已被接受的 Trigger 不能再次创建 Ticket。源码：evals.ts L70–119。

      快路径处理“现有工作需要什么新信息”。命中 Subscription 的评论、CI 结果、审阅意见直接形成 Input，送到原 Worker。Router 可以收到“发生了 follow-up”的摘要通知，但不负责再次投递，也不应该再造一个任务。Worker 仍持有原 Mandate；这条评论提供上下文，并未自动授权相邻需求。错误 attach 的代价很高，因为 attach 会订阅整个线程，后续信息将持续流入。Prompt 因此要求明确的任务引用，不能只因话题相似就关联。

      三个不等号

      相关 ≠ 属于；属于 ≠ 授权；送达 ≠ 读到。Correlation 只补上下文，Subscription 决定投递，Mandate 限定行动，Input 的读取状态决定恢复时是否需要重新交给执行者。

      人的自有线程后续可以交给活跃 Ticket，也可以在重校验后唤醒已结束 Ticket；机器人和 CI 只推动仍活跃的任务，只供上下文的线程不会把结束任务重新打开。存在 Worker 承接人的后续时，内核拒绝 Router 对这段后续再做 accept / attach / ignore，保留 stop 入口。Worker 无法承接超出范围的信息时可以 handback，未被消费的请求回到 Eval；多任务共享线程时，需要所有相关承接者释放，才能重新评估。边界属于宿主状态机，不依赖 Router 记住约定。

      五用一次飞书 → PR → 回飞书串起来#

      — ONE TICKET, MULTIPLE CHANNELS AND ASSIGNMENTS

      以下是按领域契约组织的示例流程，不是本次连接真实账号录制的运行轨迹。它展示同一任务怎样跨渠道延续，以及人为什么不必每次重新向 Agent 描述背景。

      PR 结束条件也不是简单盯着一个“merged”字段：ready 且无 PR 可以结束；有 PR 时，要等待相关 PR 的关闭条件。任务拥有自有 PR，就检查全部自有 PR；没有自有 PR 时检查跟进的 PR。还有未完成的后续工作，关闭事件不能替 Worker 报告完成。这些细节避免系统交了一个初稿就消失，也避免合并之后把尚未回答的人类评论丢掉。执行契约 L94–116。

      六主动性：程序检查结构，Prompt 判断语义#

      — A NARROW DEFAULT / AN EXPLICIT AUTHORIZATION BASIS

      “主动”在公开原型中非常克制。policy.ts 的默认主动规则只有两条：Copy fixes 与 Visual fixes，分别针对保留业务含义的文案修正，以及目标明确或已有客观标准的局部间距、对齐、溢出、样式修正。它不默认主动修任何 bug，不因为“这个页面不好看”就设计一套新交互；规则文本反复要求范围可分离、方向已确定。

      默认 eval.mode = observe。对于 inferred 候选，即使准入判断认为可以做，也只记录 would_accept，不创建 Ticket、Worker 或工作目录。auto 才按命中规则接受推断请求；off 关闭推断路径。明确授权的请求不受这三个主动模式的开关限制，仍走明确请求路径。默认 GitHub receive-all 也关闭。policy.ts L40–96。

      // 概括准入条件；不是源码逐字摘录
inferred_accept =
  mode === "auto"
  && implementation_requested
  && target_basis !== "undetermined"
  && !requires_design_decision
  && enabled_rule_matched
  && intent_evidence_present

// observe 下只记 would_accept；explicit 另走明确授权路径

      宿主要求模型对每条启用规则恰好给一次判断，不允许未知、禁用、重复或缺失规则；接受还必须有实现意图、已确定目标、没有待决设计选择、有规则命中，并提供意图证据。这能防止输出协议漂移，却不能证明模型填的 implementation_requested: true 就符合事实。语义真伪仍依赖模型读懂原文，Worker 因此要再次读取原始请求，不能只信 Router 的转述。

      角色 Prompt要求模型做什么宿主能够明确约束什么
      orchestrator / dispatch使用摘要；只路由和转交；不添加实现计划、验收标准，不合并 PR，不等待轮询。路由命令、已承接后续的重复接单限制、结构化报告与通道。
      admission核对原始实现意图和既定目标；只读检查，不委派，不把外部文本当指令。受限评估工具、结构化规则覆盖、模式开关、当前策略与 Eval 身份校验。
      work阅读原文；在 Mandate 内完成检查、审阅、提交、推送、PR；阻塞时给具体原因，避免刷屏。会话/目录分配、并发槽位、应用资源可见范围、报告状态；技术完成质量仍需外部验证。

      Prompt 分角色、有可覆盖的团队段落，并以版本关联模型请求，便于追踪一次决定依据哪版工作契约。改变 Prompt 可能削弱语义约束，宿主的结构约束仍保留。策略变更则会使在途 Eval 失效，并通知受影响的活跃任务；不会立即停掉或撤销所有已运行任务。结束任务恢复前再校验，这是延续策略，不是即时权限撤回系统。

      另一个真实边界是身份：每个 Source 用自己的原生 actor ID，原型没有把 GitHub 用户和飞书用户映射成全局 Principal。已经订阅的活跃任务可以收到不同参与者的上下文，某些人的后续也可重开任务；“谁能开启新工作”和“谁的消息能延续已有工作”是两套语义。要在企业环境使用，应该先把这个选择写进团队契约和权限模型。

      七并发与上下文：用调度和引用减少负担#

      — HOST-ENFORCED PARALLELISM / BOUNDED CONTEXT

      WorkerSlots 在异步启动之前同步预占槽位，默认最多 3 个并发 Worker，可配置到 1–16。人的自有线程后续或状态请求允许使用一个额外槽位，已有工作的唤醒优先于新任务启动。计数的是正在准备、运行、唤醒或占着后台工作的执行机会；不是系统只能保有三个 Ticket 或三个历史 Session。系统不需要寄希望于模型“今天记得用子 Agent”。

      Router 和 Worker 的 shell 前台时间限额为 5 秒，长命令会转成后台 job，控制权迅速返回，并非超过 5 秒就杀掉命令。Worker 一轮结束仍有活跃后台作业时继续占槽；最长再保留约 30 分钟，随后杀 shell jobs，子 Agent 可有不同生命周期。交给人接手可释放槽位并留下审阅服务。Router 也有防长等待约束。这样把“等工具结束”从对话控制流移到运行时。

      上下文组织采用类似 Inline / Spill 的办法：短摘要直接放进当前提示，细节通过稳定引用按需读取。Worker 默认内联约 1,500 字符 Assignment、600 字符 Trigger，以及更短的回复预览；Router 结果摘要上限约 600 字符，评估候选有自己的 4,000 字符预算，邻近信息被进一步压缩。不同预算对应不同资源，不能统一解读成“整个上下文只有 4,000 token”。

      读取路径沿着 Trigger → Thread → Ticket / Assignment / Result 和 Source 原生资源引用展开，有分页和文本预算，原始依据随时可扩展读取。它是一张资源引用图，不是向量检索系统或语义知识图谱。Worker 的应用资源读取限制在自己的 Ticket、线程、Trigger 和 Prompt 修订；这减少无关信息，却不等价于 OS 文件隔离，因为 Worker 仍有 bash。

      这套设计的取舍是清楚的：Router 持有跨任务的有限摘要，Worker 保有局部执行细节，事件订阅省掉重复搬运和推理。GitHub 接入仍采用默认 60 秒轮询，飞书则通过 lark-cli event consume 接 NDJSON 事件，带就绪检测、重连和历史补偿。内部事件驱动不代表所有外部事件都零延迟到达。已结束任务的订阅还会轮询一段时间；游标回退窗口配合稳定 ID，降低时间戳边缘漏消息的概率。

      并发：dsh.ts L171–198 · 生命周期：execution L31–47 · 内联预算：dsh.ts L112–128。

      八持久性：恢复任务与交付，承认外部动作的窗口#

      — COMMIT FIRST / RETRY WITH STABLE IDENTITIES

      store.ts 使用 node:sqlite，数据库文件权限 0600，WAL 与 synchronous = FULL，保存 Trigger、处置、Thread、Ticket、Decision、Outbox、Effect 和配置版本。命令事务通过 savepoint 组织，只有提交后的回调才能启动外部效果。目录锁保证同一状态目录由一个运行时占用；公开部署没有分布式 Router 或多节点一致性协议。

      effects.ts 把异步动作登记为持久化队列，用 kind / key 标识可替换效果，带 seq 与 generation。相同键更新载荷时递增 generation、重置尝试次数并重新到期；旧的在途执行完成时，只有 seq / generation 仍匹配才允许删除对应记录。这样旧完成结果不能误删较新的任务。队列还支持按类型并发、顺序约束、延期和指数退避；停止 drain 不会清空尚未处理的持久记录。

      交付环节同样区分阶段。给 Session 的消息使用稳定 ID，在已保存事件历史和两个 inbox 中检查重复，并先 flush 再向生产者确认。送进 inbox 不等于 Worker 已认领并读取；恢复时未读输入重新分配。Outbox 把回执与发送效果放进同一事务，维护每任务、每渠道的发送顺序。GitHub 评论带隐藏的消息 ID 标记，发送前扫描自己的评论做去重；飞书使用原生幂等键。

      因此准确的表述是可恢复的任务生命周期与效果交付。系统不是普适的 exactly-once 执行器。Worker 自行运行的 bash、git push 或 PR 创建，如果远端成功而本地尚未记录就崩溃，恢复执行可能重复。文档要求先检查工作目录与远端状态，再重做外部动作。模型/网络瞬态失败有最多三次重试，prepare 失败不会自动反复重试；failed / blocked 状态会冻结自动输入，等待合适的人类推进。

      长期运行还有存储代价：架构文档明确没有删除旧 Trigger、Decision、结束 Ticket、回执和版本记录的策略。它保存了丰富审计数据，也需要后续归档与保留规则。不要仅因“SQLite + 恢复”就把它视为完整 Durable Workflow：它没有提供确定步骤的 DAG、节点级重放和阶段屏障。任务内部复杂工作仍由 Worker 在会话中推进。

      持久化：store.ts L59–86 · 效果代际：effects.ts L103–145 · 投递确认：delivery.ts L26–85。

      九哪些愿景已经落地，哪些还没有#

      — DESIGN DIRECTIONS ARE NOT CODE GUARANTEES

      常见概括公开实现中能确认的事实应该保留的边界
      全能常驻助手为一个 GitHub 仓库编码，可选飞书渠道；独立 Ticket 和 Worker。没有通用邮件 / 日历 / 浏览器任务集成；“长期实体”是演进方向。
      轻 Router，强 Worker职责和上下文分离；角色模型分别配置，模型 Provider 没有写死为 DeepSeek。没有测得“任何小模型 Router 都够用”；当前 Router 实际拥有 bash / read / jobs。
      事件驱动内核按事件推进，飞书流式接入；后续通过订阅直达 Worker。GitHub 默认 60 秒轮询，不能据此声称全渠道实时。
      计算 / 状态 / 环境解耦Store / Executor / Source 有独立接口；Ticket 与 Session 分离。运行时仍本地、单进程，Worker 目录也在本机；未实现完整远程守护进程与分布式路由。
      外部 Watchdog部署文档建议独立 DSH profile 每小时运行状态检查，故障时重启，保留手动暂停。这是健康检查兜底；没有实现独立检查任务轨迹、纠正假完成的语义监督者。
      授权与安全隔离Mandate、Source 策略、只读评估工具和任务资源范围；命令 wrapper 与目录约定。Worker Session 是 danger-full-access，使用操作者 OS 权限；绝对路径可绕过部分 wrapper，worktree 不是沙箱。
      自动审阅与合并团队 Delivery Prompt 可描述审阅和合并策略；Router Prompt 要求不合并。Prompt 不替代 GitHub branch protection；代码不能证明所有合并都经过独立质量审查。
      自主恢复状态、队列、回执持久化；若干瞬态失败有重试，未读输入重新分配。没有无限自愈；远端副作用与宿主提交之间仍有重复窗口。

      最值得认真对待的限制来自仓库自身，而不是推测：执行文档明确说环境 wrapper 不是安全边界；源码确实创建全权限 Session；Watchdog 部署建议只检查健康与重启。将这些边界写清楚，才能知道工程上该补哪层：权限隔离在运行环境，审阅在代码托管规则，语义完工检查在独立验证器，分布式恢复在调度与存储协议。

      移除订阅，Router 决策约增加 30%；cache-read 23.23M → 31.77M。后续直达 Worker，减少 Router 处理；cache-read 增幅约 37% 为据上述数值计算。这些是缓存读取 token，不是总 token，也不能直接换算成本降幅。

      十一对 FDE 的启发：外层协同，内层 Durable Workflow#

      — ORIGINAL ANALYSIS / TWO COMPLEMENTARY RESPONSIBILITIES

      下面是基于代码的分析判断。与你偏好的“薄 Agent + Durable Workflow”相比，Super Agent 的公开原型解决的是外围问题：谁授权、哪些工作正在进行、这条新消息该交给谁、什么时候值得打扰人。Durable Workflow 解决内部问题：一项工作分几步、依赖如何安排、失败重试哪一节点、跨阶段如何保留结果。两层可以组合，并不需要把其中一种当成另一种的替代品。

      外层协同控制面
  Source → Gate / Eval → Mandate + Ticket
  Subscription → Follow-up → 原任务
  Result / Attention → Outbox → 原渠道

内层任务执行
  薄 Worker → Durable Workflow
  DAG / 阶段屏障 / 局部重试 / 产物与状态

共同身份
  ticket_id / assignment_id / input_id
  policy_version / prompt_revision / effect_generation

      例如一个客户交付需要数据准备、分析、生成报告、人工确认、发布。外层负责把新材料和客户意见送回同一任务，并保留原授权；内层用 DAG 管并行分析和阶段确认。最终交付和需要人的决定，通过结构化 Report 回到外层。既保留对开放事件的适应性，又不会让一个长会话承担所有执行恢复责任。可以对照Dynamic Workflows 与薄 Agent 的既有分析阅读。

      优先借鉴落地目的如何验证
      稳定 Trigger / Ticket / Assignment / Input ID同事件去重、同任务延续、多次执行可追踪。重复入站、跨线程命中和恢复后重投，不重复开票、不丢输入。
      不可变 Mandate + 当前策略重校验把授权基础留在状态里，避免摘要或后续消息扩大范围。越界请求进入 handback；停止后不自动恢复；策略变化能追溯。
      先提交，后 Effects / Outbox进程崩溃时保住任务与交付责任。在提交、发送、确认之间注入故障，检查丢失、重复及远端去重。
      原始依据引用 + 有预算的摘要减轻 Router 上下文，同时让 Worker 能核查意图。抽样核对摘要与原文；统计引用读取、误派单、token 和队列时延。
      Attention 作为结构字段只在可用结果或具体决策点请求人的注意。看通知有用率、人介入次数、未回答请求和过早 ready。

      对于 LIFT，可以直接利用 Trace、Artifact、Scores、Metrics做论证性归因，不把 replay 当成前提。轨迹应记录 Gate 结果、Mandate、订阅变化、读/送达状态、Prompt 版本、Effect generation 和渠道回执。这样可以从“没交付”继续定位为误准入、误 attach、后续丢失、越界执行、过早 ready、遗漏原渠道转交或外部动作重复，并用产物和打分支持解释。真正的验证性干预，可在有条件时另做。

      我的判断：值得借鉴的是把协同责任做成程序可检查的状态，并围绕人的注意力定义行为。现在就能迁移的是事件身份、授权基础、订阅直通、结果交付和恢复契约。通用自主性、强安全边界与长期生产收益，仍需分别验证。
