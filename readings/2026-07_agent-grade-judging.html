      核心论点：Agent 评测的下一站不是"更聪明的 judge"，而是把结构显式化——要么把结构放进 judge 内部（AgentEval 三 agent 分工），要么把结构放进 任务外部（Agent-as-a-Judge 的 requirements DAG）。这两条路径互为镜像，但在企业归因场景里其实是上下游关系：Critic 发现该看哪些维度、DAG 固化维度间的依赖、judge agent 沿图行走、失败节点直接喂给 A2P 溯因——这就是本篇要拼出来的原创视角。

      一为什么 pass/fail 不够#

      过去十年 LLM 评测的默认动作是——给一个任务、跑一次模型、判一个分。Agent 场景把这套动作打碎了：一个 deep agent 完成一次任务可能要经过几十步——规划、工具调用、检索、反思、再规划——最终一个"pass"或"fail"完全掩盖了中间过程的信息。

      问题不是"分数是错的"，问题是分数是不够信息量的。工程师拿到一个 "3/5" 打开 Langfuse 只能一步步翻 trace 猜"这一步是不是就是它扣分的地方"——这套人工归因的成本吃掉了评测的所有收益。

      outcome-only 的信息损失
      Agent trace 是一条 由多个决策组成的因果链，最终分数只反映链的末端。中间任何一步的错、退化、绕路、无效重试——都被浓缩成一个数字。信息损失量随 trace 长度呈超线性增长。

      两篇 2024 年下半年出来的论文，从不同方向回答了这个问题——AgentEval（Arabzadeh 等 · Microsoft AutoGen）与 Agent-as-a-Judge（Zhuge 等 · Meta AI）。两条路径都在 process-aware 评测这个大伞下，但技术选择完全不一样。

      二两条路径的分野：结构放在哪儿#

      先把两条线的本质差异说透：它们对"如何让 judging 变得 process-aware"给出了截然相反的结构性回答。

      Path A · Structure inside judge

      AgentEvalArabzadeh et al. · Microsoft AutoGen · 2024

      结构在 judge 内部——一个不透明的黑箱被拆成 3 个可分工的 agent。

      Critic 提议评分维度、Quantifier 给分并量化解释、Verifier 校验一致性与 bias。三 agent 通过 hand-off 协议流水线协作。对客户 rubric 更宽松——Critic 可以在线发现新维度。

      Path B · Structure outside task

      Agent-as-a-JudgeZhuge et al. · Meta AI · 2024

      结构在任务外部——用户需求先被显式分解成 requirements DAG，judge agent 沿图行走。

      requirements 是节点、依赖关系是边，judge agent 拓扑序遍历每个节点独立判定。上游失败自动短路——归因链免费得到。对客户 rubric 更忠实——直接映射为 DAG 骨架。

      这个分野的本质是"结构在哪"：AgentEval 把结构放进 judge 内部（不同 agent 负责不同判分职能），Agent-as-a-Judge 把结构放进任务外部（DAG 描述任务的分解与依赖）。这不是一个 metaphor——它决定了两条线接下来的几乎所有工程选择：judge 数量、前置成本、判分粒度、归因链的形成方式、动态性、可复现性……都由这个根性差异生长出来。

      三AgentEval · Critic + Quantifier + Verifier#

      AgentEval 发表于 2024 年 5 月，是 AutoGen 团队在多 agent 评测方向的代表作。它的核心动作是：把"给一个分"这个动作分解为三个 agent 的顺序协作——每个 agent 负责一件事、可以独立优化、可以互相校验。

      AgentEval 三 agent 流水线 Path A · Internal Structure

      任务描述 + agent 输出 → 三个 agent 顺序流水线 → 多维度评分 + 一致性检验

      CriticCRITERIA PROPOSER

      给定任务和 agent 输出，提议一组评分维度（例如"正确性 / 效率 / 可读性 / 完备性"）。Critic 是发散器——它可以在线扩展客户没预设的维度。

      QuantifierSCORE ASSIGNER

      按 Critic 提出的每个维度独立打分，并给出量化解释（"因为 X 缺失所以扣 2 分"）。粒度可配为 binary、Likert-5、连续分。

      VerifierCONSISTENCY CHECKER

      校验前两 agent 的输出是否自洽——criteria 是否互斥、分数是否与 rationale 一致、有无 length bias / position bias。发现问题回退 Critic 重议。

      AgentEval 的三个核心工程价值：

      1. 动态维度发现——Critic 可以为 unseen 任务临时构造评分维度，比"固定 rubric"更适合开放式生成任务（写作、UX、生成式对话）。
      2. 可解释性——每个分数附带量化解释（不是"因为好所以 5 分"，而是"因为完成了 X、Y、Z 三条子目标所以 5 分"）。
      3. 自校验闭环——Verifier 相当于给整个 judge system 装了个 QA 层，能显著降低 LLM-as-a-Judge 常见的 bias（论文里在 MATH / HumanEval 上做了实证）。

      AgentEval 的两个短板也同样明显：

      1. Judge bias 传递——三个 agent 都用同族 LLM 有共谋风险（同类型模型对同类错误集体盲）。论文里通过 cross-family verifier 缓解，但没根除。
      2. 不做"哪一步错"——AgentEval 天然是结果导向的（对 agent 的最终输出打分），trace 内部的过程判定不是它的直接目标。这是它与 Agent-as-a-Judge 的最大 gap。

      四Agent-as-a-Judge · Requirements DAG + Judge Loop#

      Agent-as-a-Judge 发表于 2024 年 10 月，是 Meta AI 团队的作品，也是"把评测本身做成一个 agent"这个 idea 的最完整体现。它的核心动作是——先把任务分解为 requirements DAG，再让 judge agent 沿图行走。

      Requirements DAG 构造 + Judge 遍历 Path B · External Structure

      任务自然语言 → LLM 分解为 sub-requirements → 建依赖关系 → judge agent 拓扑序遍历

      Step 1 · Decompose
      任务 → Requirements

      LLM 把任务自然语言分解为原子级 requirements（"数据查询正确" / "维度拆解完整" / "结论有证据支撑"…），每条能被独立判定。

      Step 2 · Wire Edges
      推断依赖 → DAG

      通过 LLM 或规则推断 requirements 间的依赖关系。DAG 而非 tree——同一子 requirement 可以被多个上游依赖（共享子目标）。

      Step 3 · Judge Walk
      拓扑序遍历

      Judge agent 拓扑序访问每个节点、读 trace 找证据、独立判 pass/fail。上游 fail 自动短路下游——归因链免费得到。

      Agent-as-a-Judge 的四个核心工程价值：

      1. DAG 而非 Tree——一个 requirement 可以有多个父节点。例：任务"生成带图表的 BI 报告"里"图表数据正确性"同时依赖"数据查询正确"和"聚合维度正确"，是 DAG 而不是 tree。这个结构选择很重要——共享子目标在企业级任务里普遍存在，tree 建模会强行拆分导致语义丢失。
      2. 上游失败的短路判定 = 免费归因链——如果 requirement A 依赖 B，B 已经 fail，A 不再单独 judge（因 A 的失败无法归因到 A 自身），标记为"blocked by B"。这是 DAG 拓扑给出的零算法归因——拓扑排序就是归因序。
      3. Judge Agent 不是 pure LLM call——它有工具（读 trace、跳步骤、查 spec），能在判定时主动去 trace 里找证据。这一点常被忽视——"agent-as-a-judge" 的 "agent" 是字面意思，不是修辞。
      4. DevAI 上的实证数据扎实——55 个真实开发任务、365 requirements、8 个 baseline agent。Agent-as-a-Judge 与人类标注一致度 ~0.9、比 LLM-as-a-Judge 高约 40%、成本降低 97%（相对 human evaluation）。

      Agent-as-a-Judge 的三个短板：

      1. DAG 定义前置成本高——好的 DAG 是有质量的，靠 LLM 自动分解不够、需要人工校对。企业场景里通常需要工程师 + 业务方一起定义。
      2. DAG 是静态的——一旦任务类型或 rubric 变化，DAG 需要重建。相比 AgentEval 的 Critic 动态发现维度，这在灵活性上是逆风。
      3. Judge agent 的 tool call 成本——每个节点判定都要读 trace / 跳步骤，一次评测的 token 消耗比单次 LLM-as-a-Judge 大。但相对 human eval 仍便宜 97%，所以在实际权衡里这是可接受成本。

      五两条线的对比矩阵#

      把关键维度放在一起对照，能更清楚看到"结构位置"这个根性差异如何生长出所有工程差异：

      维度 AgentEval Agent-as-a-Judge
      结构位置 Judge 内部：3 个 agent 分工 任务外部：requirements DAG
      Judge 数量 3（Critic / Quantifier / Verifier） 1（沿 DAG 遍历）
      前置成本 定义 3 个 agent prompt 定义 requirements DAG（含依赖关系）
      判分粒度 每个 criteria 一个分（Likert / 连续） 每个 requirement 一个 pass/fail
      归因链 需要额外分析 Quantifier 的 rationale 拓扑序自然形成（上游 fail 短路下游）
      动态性 Critic 可在线扩展新维度 DAG 静态、需要重建
      人类对齐 通过 Verifier 校准（论文未大规模测） DevAI 上 ~0.9
      成本 vs LLM-Judge 3 倍 token（三 agent） ~|DAG| 倍 token，但相对 human eval 降 97%
      对客户 rubric 的吸收 客户维度 → Critic 参考；灵活但可能被覆盖 客户 rubric 树 → 直接映射 DAG 骨架；忠实但缺弹性
      典型场景 开放式生成任务（写作、UX、对话） 有明确 spec 的任务（代码、报告、BI）
      可复现性 中：依赖 Critic 的稳定性 高：DAG 固定、judge 只做局部判定

      六维对照 · 一眼看差异

      越远离圆心越"强"。两条线在不同维度上互补。

      AgentEval Agent-as-a-Judge
      • AgentEval 强项：动态性、开放任务适配、维度可解释性。
      • Agent-as-a-Judge 强项：归因链天生、可复现性高、DevAI 上人类对齐已量化。
      • 共同短板：都无法完全消除 judge bias；两者都建议 human-in-the-loop 采样校验。

      六能不能拼在一起？—— 一个原创视角#

      论文都是各写各的、把自己那条线做到极致。但如果把两条线看成一条产品级流水线的两个环节，会发现它们其实是上下游关系而不是竞争关系——

      • AgentEval 的 Critic 擅长回答"该看哪些维度"——它是维度的探索器。
      • Agent-as-a-Judge 的 DAG 擅长回答"这些维度之间的依赖关系"——它是结构的固化器。

      Critic 是发散的、DAG 是收敛的；Critic 靠 LLM 灵活性、DAG 靠图的确定性。把 Critic 的输出喂给 DAG builder、再让 judge agent 沿 DAG 遍历——就得到一个能处理"客户 rubric 不完全 + 需要严谨归因"两个需求的完整系统。

      Fused pipeline · Critic → DAG → Judge → A2P本篇的原创拼接视角
      Input
      Client Rubric
      客户开放的打分维度树
      AgentEval
      Critic
      动态扩展缺失维度（dimension exploration）
      Bridge
      DAG Builder
      推断维度间依赖 · 建立 requirements DAG
      Agent-as-a-Judge

      Attribute

      这不是"想象一下"——每一环都是现有论文已经验证过的能力，缺的只是把它们串成一条流水线的工程实现。对企业归因这个场景来说，这条流水线的价值在于：既保留了 AgentEval 的灵活性（Critic 能动态发现客户没想到的维度），又保留了 Agent-as-a-Judge 的严谨性（DAG 给出免费归因链），最终把 output 直接喂给 A2P 做 L3 溯因。

      七对接三层归因栈：这两条线在我们的产品里各司什么职？#

      把视角拉回到 Agent Badcase 归因方法论调研里那个三层栈——L1 分类 / L2 定位 / L3 归因。两条线在这个栈里的落位如下：

      层 核心任务 AgentEval 的角色 Agent-as-a-Judge 的角色
      L1 · Classify 错的是哪一类 Critic 动态生成分类候选 → 作为 L1 taxonomy 的动态扩展器 DAG 节点类型即分类（Plan / Reason / Tool / Retrieval …）
      L2 · Localize 先在哪一步崩 Quantifier rationale 提供"哪个维度扣分"，但无 step 定位 DAG 天然是 L2 骨架——短路点即定位点
      L3 · Attribute 为什么错、怎么改 Verifier 校验 bias、Quantifier rationale 作为解释素材 失败节点集 → A2P Abduction 的候选假设集

      核心洞察：Agent-as-a-Judge 在 L2 上是不可替代的（DAG 短路 = 免费归因链），AgentEval 在 L1 上是不可替代的（Critic 动态发现 = 客户 rubric 覆盖不到时的兜底）。两者不是二选一——是各占一层。

      给三层栈选武器
      • L1 分类：以固定 taxonomy 为主（AgentErrorTaxonomy 五分类），AgentEval Critic 作为动态补充——当固定 taxonomy 覆盖不了时才让 Critic 出手。
      • L2 定位：Agent-as-a-Judge 的 DAG 是首选——上游 fail 短路机制就是天然的定位算法。
      • L3 归因：DAG 输出 → A2P Abduction 直接消费；AgentEval Verifier 作为 bias 兜底、保证 judge 不会集体盲。

      八局限与工程 tradeoff#

      两条线共同的三个陷阱
      1. Judge bias 传递——同族 LLM 会共谋，同类型模型对同类错误集体盲。两条线都建议跨 family 部署（Critic 用 Claude、Quantifier 用 GPT、Verifier 用 Gemini），但成本翻倍。
      2. DAG / criteria 定义的前置成本——好的结构不能全自动产生，需要工程师 + 业务方共建。这是 process-aware 评测的"启动税"。
      3. 可复现性挑战——LLM 的 non-determinism 让两次评测可能给出不同分数。两条线都建议低温度 + seed fixing + repeat-N 取均值作为工程实践。

      AgentEval 特有的陷阱：Critic 可能过度发散——给一个"写一封邮件"的任务提议 15 个评分维度。工程上需要给 Critic 加维度数上限、或让 Verifier 做维度合并/剪枝。

      Agent-as-a-Judge 特有的陷阱：DAG 中的隐蔽循环依赖——LLM 分解 requirements 时可能构造出实际是循环的"DAG"（A 依赖 B、B 又依赖 A 的某个 side effect）。工程上需要拓扑检验 + 循环告警。

      九在 LIFT 内实现的路径#

      把这两条线落地到我们的 LIFT 框架，分三阶段推进（对应 接入方案 8.4 的落地节奏）：

      阶段 1

      先落 Agent-as-a-Judge

      把客户开放的 rubric 树直接转成 requirements DAG（1:1 映射，不做发散）。judge agent 用一个 vanilla LLM + trace 读取工具。产出每节点 pass/fail + 短路归因。2-3 周可 MVP。

      阶段 2

      叠 AgentEval Critic

      在 DAG builder 前加一个 Critic step——分析客户 rubric 是否有覆盖 gap，动态扩展缺失维度。此时 DAG 是"客户 rubric ∪ Critic 发现"的并集。Verifier 作为 bias 抽查工具。4-6 周叠加。

      阶段 3

      Judge Module 融合

      把两条线固化为 LIFT 的一个 agent_judge analyzer 模块，暴露统一 API：judge(trace, artifact, rubric) → dag_report。dag_report 再喂给 A2P analyzer 做 L3 溯因。与 A2P 集成同期。

      MVP 阶段的关键工程决策：先做 rubric 树 → DAG 的确定性映射（不用 LLM 自动分解），把不确定性延到 judge 阶段——这样早期版本能给客户一个"可预期"的评测体验，之后再逐步引入 Critic 的动态维度。

      十判断印章#

      Verdict
      • 时机 · 6-12 月——两条线都在 2024 年下半年发表、2025-2026 会有大量后续工作。DAG-based judging 是当年趋势，赶早接住能拿到红利。
      • 信心 · 高——Agent-as-a-Judge 在 DevAI 上给出的实证数据扎实（对齐 0.9、成本降 97%）；AgentEval 在 MATH / HumanEval 上做过对照实验，Verifier 的 bias 减少效果可复现。
      • 产品落点：L1 靠 AgentEval Critic 动态兜底、L2 靠 Agent-as-a-Judge DAG 定位、L3 靠 DAG 输出喂 A2P 溯因——三层栈里两条线各占其位、不是二选一。
      • 必须记住的一句：Agent 评测的下一步不是更聪明的 judge，而是让结构显式化——不管你把结构放在 judge 内部还是任务外部，只要它显式了，归因链就顺理成章地出现。
