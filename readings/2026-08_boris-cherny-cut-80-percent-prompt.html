      源：Boris Cherny: We Cut 80% of Claude Code’s Prompt（YouTube · Y Combinator） · YC 官方转录 · 35:51 · 发布 2026-07-27

      核心结论：Boris Cherny 在 YC Startup School 上把「在加速的模型上造产品」讲成了一门经验科学（empirical science）——每出一代模型，就把 harness 的 system prompt 删光再逐行加回（ablation）：Opus 5 一来，Claude Code 删掉了 80% 的系统提示词，因为旧模型需要的纠正性指令新模型已经不需要。他给所有人的建议同样简单粗暴：「every 6 months delete your Claude MD. Delete your skills. Delete your hooks.」 更深的三条主线是——用 product overhang / unhobbling 找模型今天就能做、却没被产品释放的能力；把 dynamic workflows 当成编排 test-time compute 的「agent 代数」；用 loops & routines 让代码库自己维护自己。对 FDE：这套「先删、给难任务、让它自证、别过度规约」的方法论，比任何 prompt 模板都更值得抄。
      一页要点
      • 删 80%：Opus 5 太聪明，旧模型的「纠正性 prompt」成了噪声。隐藏开关 CLAUDE_CODE_SIMPLE=1 连工具 prompt 一起删，模型「反而稍微更聪明」。
      • ablation 是新常态：删光 → 用起来 → 只在反复绊倒同一处时逐行加回。每代新模型都重来一次。evals 也只活 1–3 代，饱和就扔。
      • product overhang / unhobbling：模型今天能做的远超我们意识到的，是产品在挡路。Claude Code 的诞生＝给 Sonnet 3.5 撤掉 IDE 脚手架、丢给它整个终端。
      • 给它比你以为更难的任务 + 让它自证：verification 是「最多人做不对的一件事」。Bun 团队用自带测试套件，让 Claude 把 runtime 从 Zig 一次性重写到 Rust，跑 11 天，已在生产。
      • dynamic workflows = agent 的代数：一句 "use a workflow" 在 Bun 沙箱里编排成百上千 agent（串行/并行/扇出/收敛）——一种新形态的 test-time compute。
      • loops & routines：每天几百–几千 agent 跑「清死代码 / 抽象警察 / ship 满量实验 / 补删测试」，让 CLI·iOS·Android·Desktop 自己维护自己。
      • 别学的：过度规约（把每步写死）是资深工程师最常见的失败模式；「一个诀窍走天下」不存在——don't listen to the LinkedIn influencers。

      一背景：为什么这场对谈值得读#

      Why Now · 一条指数曲线上的产品观

      录制时 Opus 5 刚发布一天，Arc-AGI-3 从「个位数 / 十几分」被拉到 30%。但真正有信息量的不是跑分，而是 Claude Code 创造者 Boris Cherny 对「模型每几个月就换一次性格，产品该怎么造」的完整方法论。他反复强调一句话：这不再是理论科学，而是经验科学——「You have to take a very scientific mindset to it where you try something, you see the result, and then you iterate based on that.」

      他把模型比作活物而非系统：「the way to think about it is almost like a living creature… every model generation, it behaves differently. It has a slightly different personality. And you have to take the time to get to know it.」 这句话是全场的锚——下面每一条战术都从它长出来。

      硬币的另一面 · prompt injection 几乎被解决

      聊「删提示词」之前，Boris 先抛了个更大的信号：Opus 5「不再可被 prompt injection」。这靠三层叠加——① 三年对齐研究得到的良好对齐模型；② 对全部流量跑的 prompt-injection 分类器，基于 mechanistic interpretability「直接看模型脑内被点亮的神经元」（「the model won't even tell you but we can actually see those neurons」）；③ auto-mode 分类器。三层叠起来「已经演示不出注入」。对做 harness / agent 的人：这会改变 harness 与产品的安全设计假设。

      二核心方法论：把模型当活物，用 ablation 驯化#

      Empirical, Not Theoretical · 删了再说

      「删 80%」不是一次性事件，而是一套持续动作。Boris 说 Claude Code 这个产品/harness「一直在变」，每次新模型来就删一批、改一批、换工具。原因是模型差异巨大：三个月前为某个模型写的指令，到下一代可能完全不 translate。Opus 5 太聪明，很多本用来「纠正模型本该会、却没会」的行为的 prompt，现在纯属多余。

      关键在于怎么加回来：不要猜模型需要什么指令，而是用起来、看它在哪反复栽跟头，只有反复栽在同一处才加回——因为「模型每次用都要读这条指令」，加早了就是永久税。他甚至提供了两个实验开关：--system-prompt 自定义、以及未公开的 CLAUDE_CODE_SIMPLE=1（连工具的 prompt 一起删）。团队用后者做 ablation，发现「the model is actually a little bit more intelligent without these prompts」——留 prompt 是为了产品行为符合人的预期，不是为了让模型更聪明。

      ablation ＝ 反向的 eval：删光系统提示词，再逐行加回，量化每一行的净影响。Boris：「an ablation essentially is an eval where you delete things to figure out the impact.」 对不做 harness、只用 Claude Code 的人，等价动作是——每 6 个月删掉你的 CLAUDE.md / skills / hooks，看模型是否还需要它们。

      三Product Overhang：模型能做，产品在挡路#

      Unhobbling · Claude Code 的出生故事

      Boris 用一对研究术语解释「怎么发现新产品」：hobbling＝产品在挡模型的路；product overhang＝模型今天就有、却没被任何产品释放的能力。两者是一枚硬币的两面。Claude Code 本身就是 unhobbling 的样本——一年半前 Sonnet 3.5 已是最好的编码模型，但当时的产品只做单行/多行 autocomplete、只读的 chat。「What if we get rid of all the scaffolding and just give the model the simplest possible harness?」 撤掉 IDE 脚手架、给它整个终端，模型立刻能一次写整个文件、整个 feature。他断言今天「有大量 product overhang，我没看到创业公司抓住」。

      怎么找？他给了两条动作：①给比你以为它能做的更难一点的任务——描述任务、护栏、退出标准，然后「let the model cook」，别把一二三四步写死；②放开手实验——内部最近爆火的是有人给 Opus 5 接上 OpenCV 让它画画（肖像、动物、风景都行），而模型从没被训练画画，纯粹是「solicitation gap」。他的假设：「there's probably dozens, hundreds of opportunities like this with the models of today that no one has yet realized.」

      两个「过去要一年多」的锚点
      • Bun：Zig → Rust 整库重写。Bun（Claude Code 依赖的 JS runtime）原本用 Zig 写、手动管内存。团队先让 Claude fuzz 找内存泄漏，后来 Jared 直接一句 prompt 起 dynamic workflow，靠 Bun/Node 自带的完备测试套件做 verification，跑 11 天重写 10 万+ 行、已在生产。有 steering，但「previous models just couldn't do this, even with steering」。
      • Electron → Swift 桌面客户端重写。Boris 在 Claude Tag（Slack 里的 Claude）上一句 prompt：重写成 Swift、在 Mac 虚拟机里跑起来截图、逐像素对比 Electron 版、不到一致不许停。录制时「still running… 14、15 天」，还自发开了个 Slack 频道每几分钟贴截图 live-blog 进度。

      共同配方是同一句：给难任务 + 给它自证的手段。Boris 直言 「verification I think is probably the single most important thing that people do not get right」——不是更玄的 prompt，而是让模型能像人一样验证自己的产出、不至于卡死。

      四Dynamic Workflows：编排 test-time compute 的「agent 代数」#

      A New Form of Test-time Compute · 第四个旋钮的放大器

      怎么一次跑「成千上万个 agent」？最简单的入口是 dynamic workflows——只要说 "use a workflow"。底层是把 Bun 当沙箱、在其中起虚拟机，让 Claude 起一批 agent 并有序编排：先扇出做第一遍，再用另一批 agent 验证/汇总，可能再扇出第三阶段。Boris 的背景是函数式编程，他把这套设计称为 「an algebra for agents」——有串行、有并行的 primitive，在沙箱里高效用 token 做很复杂的活。

      他把它放进 scaling law 的谱系里看：历史上模型变强是神经网规模 × 训练数据 × 训练 FLOPs 的函数；近来加了 test-time compute（说白了＝生成多少 token）；而 dynamic workflows 是「编排 test-time compute 的新方式」，能把一次难任务用到的推理算力大幅拉高——「a new way to orchestrate test time compute.」

      参数量 · 神经网多大

      训练时 · 旧 训练数据

      喂了多少 token

      训练时 · 旧 训练 FLOPs

      投入多少算力

      推理时 · 新 Test-time Compute

      生成多少 token · dynamic workflows 放大它

      agent 的代数：串行 + 并行 + 扇出/收敛的 primitive，让一次难任务（整库重写、深度数据分析、跨多阶段大 feature）productively 用掉成百上千个 agent。这是把「第四个旋钮」（test-time compute）在推理侧拉满的新手段。

      五Loops & Routines：让代码库自己维护自己#

      Self-maintaining Codebase · 每天几百到几千 agent

      第二种放大方式是 loops & routines：loop 是本地跑的 cron，routine 是云端跑的同一件事（可以关掉笔记本）。它和 dynamic workflow 的区别是——workflow 是「一个任务切成块」，routine 是「一个重复的任务，不共享上下文、但可共享记忆」，每小时/每天跑一遍。Anthropic 因此让 Claude 维护它自己的代码库：一个 Slack 频道里起了一堆 routine，覆盖 CLI、iOS、Android、Desktop。

      数百–数千 agent / 天 20–30 条 routine / 库 单句 prompt 触发 目标：全自动维护 apps

      这些 routine 大多是一句话 prompt：「清理死代码」它自己就学会了用静态+动态分析、每天开 PR；「abstraction police」每天扫全库找近乎重复的抽象并统一。Boris 的结论是——这在做「过去要几十上百个工程师才干得完」的活，于是工程师被释放去做真正想做的事：发新产品、和用户聊天。这也支撑了他那句常被引用的话 —— 「coding is (almost) solved」，但他补了 caveat：只对他做的这类代码成立，深系统 / 分布式 / 像素级 UI 校验仍会让 Claude 栽跟头。

      六FDE / 落地映射#

      What This Means For Us · 抄方法论，不抄模板

      Boris 的做法对 FDE / Agent 工程的映射动作
      每代模型删 80% prompt，逐行 ablation 加回我们的 prompt / skill / hook 也在为旧模型的缺陷打补丁换模型时先跑一次「删光→逐行加回」，量化每行净增益
      给难任务 + 让模型自证（verification 第一）评测里最缺的不是更强 prompt，是可验证的 exit 标准为每个 agent 任务先设计「它怎么自己判断做完/做对」
      dynamic workflows = 编排 TTC 的代数依赖 Claude Code 特有 primitive，迁移别框架要自己造把「串行/并行/扇出/收敛」抽象成我们评测框架的调度层
      loops & routines 自维护代码库「清死代码 / 抽象警察 / 补删测试」都是可日跑的单句任务选 1–2 条低风险 routine 在自己仓库试点，观察 PR 质量
      evals 只活 1–3 代，饱和就扔基准会被新模型迅速刷爆，固定 eval 会给假安全感eval 视为易耗品：持续 append，随模型迭代主动淘汰

      七别学的：反模式清单#

      Unlearn This · 老工程师的失败模式

      风险 · 会拖慢你的直觉
      • 过度规约（over-specification）：把「先做一、再做二、三、四」写死，是资深工程师最常见的失败模式。现代模型要的是高层任务 + 护栏 + 退出标准，然后放手。
      • 加 prompt 太早：模型每次用都要读它。没看到「反复绊倒同一处」之前别加回——每条指令都是永久税。
      • 找「一个诀窍」：「everyone's looking for the one weird trick… that doesn't exist.」 方法只有经验主义：给难任务→看哪栽→用更好的 prompt / skill / MCP 补上下文。
      • 把 eval 当永久资产：它会被新模型刷爆，抱着旧 eval 会误判能力。
      • 迷信影响者：Boris 原话——「don't listen to the LinkedIn influencers. Don't read Twitter.」（全场鼓掌）自己动手做经验。

      对 CS 学生的建议同一逻辑：CS 理论仍值得学，但更该亲手保留的是把 CS 应用到真实问题的能力——设计感、商业感、数据科学、和用户对话。他自己是在 TI-83 计算器上用 BASIC 学会编程的（为了在数学考试上「作弊」），一路被更难的问题逼着学到汇编。「programming has always been very practical.」

      八待验证的问题#

      Open Questions · 我们要盯的

      • 「删光再加回」在没有完备测试套件的业务代码库上还成立吗？Bun/Node 的成功高度依赖 verification 存量。
      • dynamic workflows 的「agent 代数」能否脱离 Claude Code / Bun 沙箱迁移到我们自己的评测框架？成本几何？
      • 「跑 11 天 / 14 天不停」的长任务，成本与可观测性怎么算？中途 steering 的人力投入是多少？
      • 自维护 routine 每天开几千 PR，review 与合并把关由谁做？会不会把技术债转成「PR 洪水」债？
      • prompt injection「三层防御」是 Anthropic 自家闭环（含 mech-interp 分类器），第三方 harness 能复制到几成？
      • 「coding is almost solved」的 caveat（深系统/分布式/像素级 UI）恰好是很多企业客户的核心场景——这条边界什么时候移动？
